# 数据库运维 — 面试参考答案

> 覆盖题单：MySQL（29题）、Redis（20题）、PostgreSQL（21题），共 70 题

## MySQL 运维面试题

### 1. MySQL 有哪些备份方案？

**要点：**
- **逻辑备份**：mysqldump（单线程，中小库）、mydumper（多线程）——`mysqldump --single-transaction --master-data=2`（InnoDB 一致性快照不锁表+记录 binlog 位点）
- **物理备份**：**XtraBackup**（Percona，热备——不阻塞读写，TB 级首选；全量+增量）
- **快照备份**：云盘快照/LVM 快照——秒级，配合 --single-transaction 保证一致性
- **binlog 实时备份**：备份+binlog 才能恢复到任意时间点（PITR）
- 策略组合：每日 XtraBackup 全量+增量+binlog 实时归档+**异地存储+定期恢复演练**——没演练过等于没备份

**一句话答：** 逻辑备份用 mysqldump 带 single-transaction 适合中小库，物理备份用 XtraBackup 热备适合大库，云上直接盘快照。核心认知是"备份文件+binlog"才能恢复到任意时间点，而且异地存放加定期恢复演练——没演练过的备份等于没备份。

### 2. InnoDB 与 MyISAM 存储引擎有什么区别？

**要点：**
- **事务**：InnoDB 支持（ACID），MyISAM 不支持
- **锁**：InnoDB **行级锁**，MyISAM **表级锁**——并发写能力天差地别
- **外键**：InnoDB 支持，MyISAM 不支持
- **崩溃恢复**：InnoDB 有 redo log 崩溃自动恢复；MyISAM 易损坏需 repair
- **聚簇索引**：InnoDB 数据即索引（聚簇），MyISAM 索引与数据分离
- **count(*)**：MyISAM 存总数直接返回，InnoDB 要扫描
- 现代 MySQL 默认 InnoDB，MyISAM 基本淘汰

**一句话答：** 核心四点：InnoDB 支持事务、行级锁、崩溃自动恢复、外键；MyISAM 全不支持且只有表锁。MyISAM 唯一优势是 count 不用扫表，但并发写一上来就崩。现代 MySQL 默认 InnoDB，新项目没有理由选 MyISAM。

### 3. binlog 日志有什么作用？

**要点：**
- binlog（二进制日志）：记录**所有已提交的数据变更**（Server 层，所有引擎共用）
- 三大用途：
  1. **主从复制**：从库拉取主库 binlog 重放
  2. **数据恢复（PITR）**：全量备份+binlog 重放恢复到任意时间点
  3. 数据同步：Canal/Flink CDC 等订阅 binlog 同步到 ES/数仓
- 格式：ROW（推荐——记录行变更，主从安全）、STATEMENT（记 SQL，有函数风险）、MIXED
- 配套参数：expire_logs_days/binlog_expire_logs_seconds（保留期）、sync_binlog（1 最安全）

**一句话答：** binlog 记录所有已提交的变更，三大用途：主从复制的数据源、配合全量备份实现任意时间点恢复、给 Canal 这类工具做数据订阅同步。格式选 ROW 最安全，保留期按恢复窗口设定，生产上 sync_binlog=1 保证不丢。

### 4. SHOW PROCESSLIST 命令有什么作用？

**要点：**
- 查看当前**所有连接线程**的状态：Id/User/Host/db/Command/Time/State/Info
- 排障用途：
  - **慢查询现场**：Time 大且 Command=Query 的——Info 就是正在跑的 SQL（kill Id 止血）
  - **Sleep 堆积**：应用连接池没释放——检查 wait_timeout
  - **锁等待**：State 显示 Waiting for table metadata lock 等
- 进阶：information_schema.processlist 可 SQL 化过滤（批量 kill 慢查询）、5.7+ sys.session 更友好

**一句话答：** SHOW PROCESSLIST 是数据库的实时现场：所有连接在干嘛、跑了多久、卡在哪个状态。最常见的用法是抓 Time 很大的 Query 直接 kill 止血，以及看 Sleep 线程堆积判断应用连接池泄漏。配合 information_schema.processlist 能批量过滤处理。

### 5. Innodb 缓冲池（innodb_buffer_pool_size）有什么作用？

**要点：**
- Buffer Pool = InnoDB 的**内存缓存区**：缓存**数据页+索引页**——读写先走内存，大幅减少磁盘 IO
- 原理：LRU 变体（**冷热分区**——新读入页进 young 区尾部防全表扫描冲刷热点数据）
- 还缓存：change buffer、undo、redo buffer（相邻概念）
- 配置：**专用数据库服务器设为物理内存 60-70%**（默认 128M 是起步值——必调）；实例内多个 buffer pool instance 减少锁竞争
- 监控：命中率（Innodb_buffer_pool_read_requests/reads）——99%+ 才正常

**一句话答：** Buffer Pool 是 InnoDB 的命根子：数据页和索引页都缓存在内存里，读写能不能避免磁盘全看它。配置经验值是专用服务器物理内存的 60-70%，默认 128M 必须调。它的 LRU 做了冷热分区优化，防止一次全表扫描把真正的热点数据冲走。命中率低于 99% 就该报警了。

### 6. performance_schema 数据库有什么作用？

**要点：**
- MySQL 内置的**运行时性能数据采集库**（内存表，低开销实时记录）：
  - 语句执行统计（events_statements_summary_by_digest——**Top SQL、慢 SQL 归因**）
  - 锁等待（data_locks/data_lock_waits——8.0 锁排查主入口）
  - IO/内存/连接/复制各维度
- 与 sys 库关系：sys 是 performance_schema 的**人话视图封装**（sys.schema_table_statistics 等）
- 应用：SQL 洞察（statement digest）、metadata lock 排查、内存占用分析
- 监控接入：exporter 从 P_S 采集指标

**一句话答：** performance_schema 是 MySQL 自带的性能监控数据源：谁跑的 SQL 最多最慢、谁在等谁锁、内存花在哪，全在里面。日常通过 sys 库的人话视图使用它，Prometheus exporter 的指标也大多从这里采。它是"数据库自诊"的基础设施。

### 7. MySQL出现大量 Sleep 线程是什么原因？怎么解决？

**要点：**
- Sleep = 连接**空闲**（无正在执行的查询）——大量堆积说明**连接建立后不干活也不释放**
- 原因：
  1. 应用连接池配置过大（池大小远超实际并发）
  2. 应用代码连接未归还/未关闭（泄漏）
  3. 短连接风暴的反面：长连接闲置
- 影响：耗尽 max_connections → 新连接被拒（Too many connections）
- 解决：
  - 应用侧：连接池 maxPoolSize 调到实际并发量、空闲回收（minEvictableIdleTime）
  - DB 侧：**wait_timeout/interactive_timeout** 调小（如 600s）让空闲连接自动断开
  - 网络层：LVS/防火墙的会话超时与 DB 不匹配也可能引发异常连接

**一句话答：** Sleep 线程就是空闲连接，大量堆积基本是应用连接池开太大或者连接泄漏。危害是占满 max_connections 后新连接直接被拒。处理双管齐下：应用侧把连接池收缩到实际并发量并配置空闲回收，数据库侧把 wait_timeout 调小让闲置连接自动被踢。

### 8. MySQL 慢查询，如何排查？

**要点：**
- **开启慢日志定位 SQL**：slow_query_log=ON、long_query_time（1s/0.5s）、log_queries_not_using_indexes；用 pt-query-digest 分析聚合
- **EXPLAIN 分析执行计划**（核心）：重点看
  - **type**：ALL 全表扫描（坏）→ index → range → ref → const（好）
  - **key/rows**：走没走预期索引、扫描行数
  - **Extra**：Using filesort/temporary（坏信号）
- **常见病因**：无索引/索引失效（函数操作列、隐式转换、前导 %like、or 混用）、统计信息过期（analyze table）、锁等待、参数（buffer pool 太小）
- 优化手段：加/改索引、改写 SQL（分页优化、join 替代子查询）、读写分离、加缓存

**一句话答：** 排查路径是先开慢查询日志用 pt-query-digest 找出最烂的 SQL，然后 EXPLAIN 看执行计划——重点三处：type 是不是 ALL 全表扫、key 走没走索引、Extra 有没有 filesort 临时表。病因清单背几个：索引失效三件套——列上做函数、隐式类型转换、前导百分号 like。

### 9. MySQL root账号密码忘记怎么重置？

**要点：**
- 经典流程（5.7/8.0）：
  1. 停 MySQL（systemctl stop mysqld）
  2. **跳过授权表启动**：`mysqld --skip-grant-tables --skip-networking &`（skip-networking 防外部连接——安全）
  3. 免密登录 → `FLUSH PRIVILEGES;` → `ALTER USER 'root'@'localhost' IDENTIFIED BY '新密码';`（8.0 必须先 flush 才能 alter）
  4. 重启正常模式
- 5.7 与 8.0 差异：5.7 用 update mysql.user set authentication_string；8.0 user 表只读需用 ALTER USER
- 生产更优做法：**有超级管理账号/带 sudo 的 debian-sys-maint**（Debian 系）或云平台控制台重置——避免停库
- 安全注意：操作窗口内数据库无鉴权——务必 skip-networking 单机操作

**一句话答：** 经典三步：跳过授权表启动、免密进去改密码、恢复正常重启。8.0 的坑是 user 表不能直接 update，要先 FLUSH PRIVILEGES 再 ALTER USER。操作期间数据库处于无鉴权状态，必须加 skip-networking 只允许本机连接。云上数据库直接走控制台重置更省事。

### 10. MySQL 插入中文乱码怎么解决？

**要点：**
- 乱码本质：**写入编码与读取编码不一致**——链路上每一环都要统一 utf8mb4
- 检查链路：客户端连接编码（`SET NAMES utf8mb4`/连接串 characterEncoding）→ 数据库/表/字段字符集 → 服务器默认字符集
- 排查：`SHOW VARIABLES LIKE '%character%'`、`SHOW CREATE TABLE` 看表字符集
- 修复：
  - 库/表：ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4
  - 连接：JDBC url 加 useUnicode=true&characterEncoding=utf8mb4
  - 全局：character-set-server=utf8mb4、collation-server=utf8mb4_general_ci
- 坑：utf8 是残缺 3 字节实现——**一律用 utf8mb4**（支持 emoji）

**一句话答：** 乱码就是链路编码不统一：连接、库、表、字段逐层 SHOW VARIABLES 核对，全部统一到 utf8mb4。注意 MySQL 的 utf8 是三字节残次品，存不了 emoji，一律用 utf8mb4。已建错的表用 ALTER TABLE CONVERT TO CHARACTER SET 修复。

### 11. 什么是 MySQL 的表空间？

**要点：**
- 表空间 = InnoDB **数据文件的逻辑组织单位**
- 两类：
  - **系统表空间**（ibdata1）：老默认——数据字典/undo/所有表数据混一起；膨胀后难回收（著名坑）
  - **独立表空间**（innodb_file_per_table=ON，5.6+ 默认）：**每张表一个 .ibd 文件**——独立管理、可空间回收（drop/truncate 直接还盘）、可传输表空间（迁移单表）
- 其他：undo 表空间（8.0 独立）、临时表空间、通用表空间
- 空间回收注意：delete 不会还盘（只有空洞），optimize table/重建表才物理收缩

**一句话答：** 表空间是 InnoDB 存数据的逻辑单位，关键是 file_per_table 开关：开了每张表独立 .ibd 文件，删除表能真还盘，还能做可传输表空间迁移；不开就全挤在 ibdata1 里膨胀了收不回来。另一个常识是 delete 不还盘只留空洞，物理收缩要靠重建表。

### 12. 什么情况下会发生死锁？

**要点：**
- 死锁四条件（数据库场景）：**互相持有并等待**、请求顺序不一致
- 典型场景：
  1. **两事务不同顺序更新同一批行**：A 锁行1要行2，B 锁行2要行1
  2. **间隙锁交叉**（RR 隔离级别）：范围条件更新时 Next-Key 锁互相卡
  3. 外键级联+唯一键插入意向锁组合
- InnoDB 处理：**自动检测**（wait-for graph），回滚代价小的事务（报 Deadlock found 错误），应用重试即可
- 排查：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段；8.0 performance_schema.data_locks 实时看锁
- 预防：**统一加锁顺序**（按主键排序更新）、小事务快提交、低并发要求场景降 RC 隔离级别减少间隙锁

**一句话答：** 死锁的经典模式是两个事务用不同顺序更新同一批行，或者 RR 级别下间隙锁互相卡。InnoDB 会自动检测并回滚代价小的一方，应用层捕获 1213 错误重试就行。排查看 SHOW ENGINE INNODB STATUS 的死锁记录，预防靠统一加锁顺序加小事务。

### 13. MySQL 主流高可用方案有哪些？

**要点：**
- 方案梯队：
  1. **主从复制+MHA/Orchestrator**：传统方案，异步复制+故障自动切换（可能丢数据——异步）
  2. **MGR**（Group Replication）：官方组复制——**Paxos 多数派**、强一致、自动选主（单主/多主模式）
  3. **InnoDB Cluster**：MGR + MySQL Shell + Router 的官方整套方案
  4. **云 RDS 高可用版**：半同步+自动切换（云上省心首选）
  5. **PXC/Galera**：多写强同步集群（写入放大，特定场景）
- 选型考量：RPO 要求（能丢数据吗）、切换速度、运维复杂度、写入模式（单写 vs 多写）
- 现实建议：中小规模用云 RDS 或 MHA，强一致要求上 MGR

**一句话答：** 方案按强一致程度排：传统主从加 MHA 做自动切换但异步可能丢数据；MGR 基于多数派协议强一致自动选主，是官方主推；InnoDB Cluster 是 MGR 加 Router 的全家桶；云上直接用 RDS 高可用版最省心。选型先问一个指标——业务能容忍丢几秒数据吗，答案决定用异步还是半同步还是组复制。

### 14. 简述 MySQL 主从复制工作原理？

**要点：**
- 三线程模型：
  1. 主库 **dump 线程**：把 binlog 事件推送给从库
  2. 从库 **IO 线程**：接收 binlog 写入**relay log**（中继日志）
  3. 从库 **SQL 线程**：重放 relay log 到从库数据
- 复制格式：ROW（推荐）/STATEMENT/MIXED（见 binlog 题）
- 复制方式演进：
  - **异步**（默认）：主库提交即返回——从库延迟/宕机不影响主库，**可能丢数据**
  - **半同步**（semi-sync）：至少一个从库**收到 binlog**（ACK）才返回——折中
  - **组复制**：多数派确认——强一致
- GTID：全局事务标识——复制位点自动定位（vs 手工 file+pos）

**一句话答：** 主从复制是三线程流水线：主库 dump 线程推 binlog，从库 IO 线程收下来写 relay log，SQL 线程重放执行。按一致性分三档：异步最快但主挂可能丢数据，半同步要等至少一个从库确认收到 binlog，组复制要多数派确认才提交。运维标配是 ROW 格式加 GTID，位点管理不再手工。

### 15. MySQL 主从同步延迟原因及解决方法？

**要点：**
- 原因（本质：**从库消费速度 < 主库生产速度**）：
  1. **从库单线程重放**（老版本）追不上多线程写入——主因
  2. 从库硬件差/资源被抢（备份任务、分析查询压从库）
  3. 大事务/大 DDL（一次锁几百万行，重放时间长）
  4. 网络带宽瓶颈（跨机房）
  5. 从库上有长查询阻塞 SQL 线程（MDL 锁）
- 监控：`SHOW SLAVE STATUS` 的 Seconds_Behind_Master（注意其在 IO 线程断时失真）、pt-heartbeat 更准
- 解决：
  - **并行复制**：5.7+ logical clock / 8.0 writeset（replica_parallel_workers）
  - 大事务拆小、DDL 用 pt-online-schema-change/gh-ost
  - 从库独立部署不混部、读写分离时业务容忍或强制读主（关键业务）

**一句话答：** 延迟的本质是从库消费追不上主库生产。头号原因是老版本单线程重放——解法是开并行复制；其次是主库塞过来的大事务大 DDL——拆小或用 gh-ost；还有从库混部被抢资源。监控不能只看 Seconds_Behind_Master，它有失真场景，pt-heartbeat 更可靠。业务侧关键读走主库兜底。

### 16. MySQL 主从复制，从库宕机/故障如何恢复？

**要点：**
- 分场景：
  1. **短暂宕机重启**：IO/SQL 线程自动重连续传（relay log 未丢）——看 Seconds_Behind_Master 追平即可
  2. **数据损坏/日志丢失**：
     - **GTID 模式**：从主库重新拉——RESET REPLICA ALL 后 CHANGE REPLICA SOURCE 重新 START REPLICA，GTID 自动补齐差异事务
     - 传统位点：记录主库当前位点，从库重做全量（备份恢复+从该位点开始复制）
  3. **彻底重建**：XtraBackup 从主库/从库克隆（--slave-info 自动记录位点）→ 恢复 → CHANGE REPLICA 开启复制——最干净
- 云上：RDS 重建从库一键搞定
- 预防：relay log 持久化（relay_log_recovery=ON）、磁盘监控、定期主从数据校验（pt-table-checksum）

**一句话答：** 能自动追平的让它自动追——IO 和 SQL 线程断线重连是常态。追不上或者数据坏了就走重建：GTID 模式下最省事，从库指向主库后自动补齐差异事务；彻底坏了用 XtraBackup 从主库克隆一份重挂。预防三件事：relay_log_recovery 开着、磁盘告警、定期 pt-table-checksum 校验一致性。

### 17. MHA 集群实现原理？

**要点：**
- MHA（Master High Availability）= 主从架构的**故障自动切换管理器**
- 组件：**MHA Manager**（监控节点，独立部署）+ **MHA Node**（每台 MySQL 上）
- 工作流程：
  1. Manager 周期探测主库存活
  2. 主库故障 → 确认死亡 → 从所有从库中**选出数据最新的**（比较 binlog 位点）
  3. **补偿数据**：从挂掉主库（如果 SSH 还能连）或 relay log 中**抢救未传输的 binlog** 补给新主——尽量减少数据丢失
  4. 提升新主 → 其他从库 CHANGE MASTER 指向新主
  5. 可配合 VIP 漂移/中间件切换流量
- 局限：**异步复制基础**——彻底挂掉时可能丢最后一段数据（半同步可缓解）；Manager 单点；切换后原主回集群需手工

**一句话答：** MHA 是主从复制之上的自动切换层：Manager 持续探活主库，故障时挑数据最新的从库做新主，并尝试从旧主的 relay log 里抢救最后一段 binlog 补给新主，把丢数据窗口压到最小，然后重定向所有从库。它的局限是建在异步复制上——主库彻底炸了最后那几秒数据还是可能丢，所以常和半同步配合。

### 18. MGR 集群工作原理？

**要点：**
- MGR（Group Replication）= MySQL 官方**组复制**（5.7+ 基于 Paxos 变体）
- 核心机制：
  1. 事务提交前在组内**广播**，经**多数派（quorum）认证**（冲突检测：认证阶段发现写冲突则回滚后者）后才最终提交
  2. 节点组成复制组，**自动选主**（单主模式默认——primary 挂了组内自动选举）
  3. 故障容忍：N=2f+1——5 节点容忍 2 台故障
- 两模式：**单主**（推荐，写自动路由到 primary）/多主（多点写，冲突检测压力大）
- 要求/限制：**GTID 必须**、表必须有主键、InnoDB、网络稳定低延迟
- 与异步复制对比：**强一致不丢已提交数据** vs 性能开销（认证延迟）
- 运维：监控成员状态（performance_schema.replication_group_members）、多数派丢失时的 group_replication_force_members 应急

**一句话答：** MGR 是官方的强一致组复制：每个事务提交前要在组内广播并拿到多数派认证，认证阶段做写冲突检测，冲突的后到者回滚——所以已提交的数据绝不丢。单主模式下主库挂了自动选新主，5 节点容忍 2 台故障。代价是提交延迟增加和一堆约束：必须 GTID、必须有主键、网络要好。

### 19. InnoDB Cluster 集群的工作原理？

**要点：**
- InnoDB Cluster = 官方**整套高可用方案**，三层组成：
  1. **MGR**（底层）：组复制提供数据强一致与自动选主
  2. **MySQL Shell**（AdminAPI）：dba.createCluster() 一键部署/管理/状态查看——运维接口
  3. **MySQL Router**（接入层）：轻量中间件——**感知集群拓扑**，自动把写路由到 primary、读分到 secondary，主切换时应用无感（bootstrap 引导应用连接）
- 流程：Shell 创建集群 → Router bootstrap 生成应用配置 → 应用连 Router 端口 → Router 持续跟随集群主变化
- 对比自建 MGR：多了标准化管理工具与流量层——省去自研切换脚本与 VIP 管理
- 扩展：ClusterSet（8.0.27+）——主集群向异步复制的副集群级联容灾（跨 DC）

**一句话答：** InnoDB Cluster 就是官方把 MGR 包成产品：Shell 的 AdminAPI 一条命令建集群管集群，MySQL Router 做接入层自动感知谁是主——写进主、读分从，主切换时应用通过 Router 完全无感。对比裸用 MGR，它省掉了自研的切换脚本和 VIP 管理，跨机房容灾还有 ClusterSet 做级联。

### 20. MySQL 如何实现读写分离？

**要点：**
- 实现层次：
  1. **应用内**：代码/ORM 双数据源（读写各自路由）——灵活但侵入
  2. **中间件代理**：**ProxySQL**（功能最全：读写分离/分库/缓存/监控）、MySQL Router、ShardingSphere——应用无感
  3. **云 RDS 代理**：阿里云数据库代理一键开
- 关键问题：
  - **复制延迟与一致性**：重要读强制走主（Hint/事务内读主）、ProxySQL 的 max_replication_lag 摘除延迟大的从库
  - **事务内所有读走主**（半同步下也要注意）
  - 会话一致性：写后立刻读的场景（写主后读主）
- 配套：多从库负载均衡、从库故障自动摘除、权重路由

**一句话答：** 实现三选一：应用里配双数据源最直接但侵入代码，ProxySQL 这类中间件对应用透明功能最全，云上直接开 RDS 代理。核心难题是复制延迟下的一致性——写后立刻读的场景必须强制走主，ProxySQL 还能按延迟自动摘除落后的从库。事务内所有读也要固定走主。

### 21. MySQL 一般会监控哪些指标？

**要点：**
- **可用性/连接**：存活探测、Threads_connected/max_connections（连接使用率 >80% 告警）、Aborted_connects
- **性能**：QPS/TPS、慢查询数（Slow_queries 增速）、Buffer Pool 命中率、临时表到磁盘（Created_tmp_disk_tables）
- **锁与事务**：锁等待、死锁次数、Innodb_row_lock_time、长事务（trx_started 超时——大事务告警）
- **复制**：主从延迟、IO/SQL 线程状态（Slave_IO_Running）
- **资源**：CPU/内存/磁盘（空间增速+剩余天数预估）、IO 利用率、磁盘临时表
- **备份**：备份任务成功/时长、binlog 积压
- 工具链：mysqld_exporter + Prometheus + Grafana + 告警分级

**一句话答：** 六大维度：连接层的连接使用率——逼近 max_connections 就告警；性能层的 QPS、慢查询增速和 Buffer Pool 命中率；锁层的锁等待和长事务——大事务是最容易出事故的隐形杀手；复制层的延迟和线程状态；资源层的磁盘空间按增速预估还能撑几天；最后是备份任务成功率。磁盘和长事务这两项告警价值最高。

### 22. MySQL 数据库与 NoSQL 数据库有什么区别？

**要点：**
- **模型**：MySQL 关系型（表+Schema 严格）vs NoSQL 多模型（KV/MongoDB 文档/ES 搜索/HBase 列式）
- **事务**：MySQL ACID 强事务 vs NoSQL 多为最终一致/单文档事务（BASE）
- **扩展**：MySQL 垂直为主+分库分表改造 vs NoSQL 天然水平扩展（分片内置）
- **Schema**：MySQL 固定 schema vs NoSQL 灵活（文档无预定义结构）
- **SQL/生态**：MySQL 标准生态成熟 vs 各家 API 互异
- 选型：强一致多表事务/复杂查询 → MySQL；高吞吐简单 KV → Redis；海量写入/灵活文档 → Mongo；搜索 → ES；两者共存互补不替代

**一句话答：** 核心差异四条：关系模型和严格 schema 对灵活文档模型，ACID 强事务对最终一致，垂直扩展加分库分表对原生水平扩展，成熟 SQL 生态对各家私有 API。它们是互补不是替代——交易订单这类强一致数据放 MySQL，日志搜索放 ES，会话缓存放 Redis。

### 23. TB级数据库怎么在线迁移？

**要点：**
- 目标：**不停机/少停机**迁移 TB 级库
- 方案：**全量物理迁移 + 增量同步 + 割接**三段式
  1. **全量**：XtraBackup 物理备份传输到目标（TB 级逻辑 dump 不可行）；或云上 DTS/快照克隆
  2. **增量**：源库 binlog 持续同步到目标（自研/OTTER/DTS/主从复制挂上）——追平延迟
  3. **数据校验**：pt-table-checksum 抽样/全量校验一致性
  4. **割接**：业务低峰 → 停写 → 追平延迟归零 → 校验 → 切连接串（DNS/代理/配置中心）→ 观察回退通道保留
- 关键细节：目标库参数与版本预校验、字符集/时区/SQL_MODE 一致、大表传输带宽规划、回滚预案（反向同步预建）
- 时间预估：全量传输+追平可能数天——增量期业务无感，只有割接停写分钟级

**一句话答：** TB 级在线迁移就是三段式：XtraBackup 物理全量打底——逻辑 dump 这个量级不可行，然后 binlog 增量持续追平，业务全程无感，最后低峰期停写几分钟等延迟归零、校验数据、切连接串完成割接。成败关键在校验和回退：pt-table-checksum 验一致性，反向同步通道预建好，切了还能切回来。

### 24. MySQL 数据库分库分表分区的作用？

**要点：**
- 三件不同的事：
  - **分区（Partition）**：**单库内**把一张大表按规则拆成多个物理段（range/list/hash）——SQL 层面还是一张表；作用：查询裁剪（分区剪枝）、归档便利（drop 分区）；不解决单机性能上限
  - **分表**：单库多表（user_0~99）——突破单表行数/索引瓶颈
  - **分库**：数据散到多个 MySQL 实例——**突破单机 IO/连接/CPU 上限**（真正意义的水平扩展）
- 分库分表策略：hash（均匀但扩容难）/range（好扩容但热点）——取模一致性哈希折中
- 引入的复杂度：**跨库事务/跨库 join/全局 ID**（雪花算法）/数据迁移扩容（双写方案）
- 决策顺序：**先索引优化 → 读写分离 → 缓存 → 再分库分表**（最后手段）；中间件：ShardingSphere、MyCat

**一句话答：** 先分清三个概念：分区是单库内一张表拆物理段方便归档和裁剪，分表解决单表行数瓶颈，分库才是真正突破单机性能上限的水平扩展。但要清楚分库分表是最后手段——顺序永远是索引优化、读写分离、上缓存，都不行才拆。拆完的代价是跨库事务、全局 ID 和扩容迁移三座大山。

### 25. 国产数据库了解吗？

**要点：**
- 分类认知：
  - **分布式关系型**：**OceanBase**（蚂蚁，金融级，OceanBase/PolarDB-X/TDSQL/CockroachDB 模式）、**TiDB**（PingCAP——兼容 MySQL 协议，HTAP，K8s 部署友好）、PolarDB（阿里云——云原生存算分离）
  - **传统集中式替代**：达梦（DM，Oracle 兼容路线——政企信创主力）、人大金仓（KingbaseES）、GaussDB（华为）
  - **分析型（OLAP）**：Doris、StarRocks、ClickHouse（国产化使用广）
- 信创背景：政策驱动 Oracle/MySQL 替代——金融政企刚需
- 运维视角差异：TiDB/OB 分布式架构（PD/TiKV、OBProxy）——运维模型与传统主从完全不同；兼容性评估是迁移第一关
- 回答策略：说 1-2 个了解深入的+分类框架，展现视野

**一句话答：** 我按场景分类记：分布式 HTAP 派的 TiDB 和 OceanBase 是头部，兼容 MySQL 协议迁移友好；信创集中式替代看达梦和人大金仓，走 Oracle 兼容路线是政企主流；分析场景 Doris 和 StarRocks 很强。运维认知的关键是分布式库的运维模型和传统主从完全不同——TiDB 是 PD 加 TiKV 的存算分离架构，迁移前先做兼容性评估。

### 26. 高并发场景，MySQL 如何优化？

**要点：**
- **架构层**（优先级最高）：
  1. **缓存挡读**：Redis 缓存热点数据（命中率 90%+ 则 DB 压力骤降）
  2. **读写分离**：读流量分摊到从库
  3. **异步削峰**：写操作 MQ 排队
  4. **连接层**：ProxySQL/连接池（防连接风暴）、应用侧连接池合理配置
- **SQL/索引层**：慢查询治理、覆盖索引、防索引失效、大分页优化（延迟关联）
- **库表层**：冷热分离、归档历史数据、读写分散；最后才分库分表
- **参数层**：buffer pool 调大、sync_binlog/innodb_flush_log_at_trx_commit 权衡（可靠性 vs 性能）
- **保护机制**：限流（应用层/ProxySQL）、慢查询 kill 自动化

**一句话答：** 高并发优化的主战场在数据库外面：缓存挡读、读写分离分摊、MQ 把写削峰，这三招做完数据库压力通常掉一半以上。库内再做索引和慢查询治理，冷热数据分离归档。参数层的 buffer pool 和刷盘策略按业务对可靠性的要求权衡。最后才是分库分表——它带来的是复杂度，能不上就不上。

### 27. 简述 MySQL 索引及其作用？

**要点：**
- 索引 = **加速查询的有序数据结构**（InnoDB 用 **B+ 树**——矮胖多叉，3 层可撑千万行）
- 作用：把 O(n) 全表扫描降到 O(log n) 定位；还支撑排序避免 filesort、分组
- InnoDB 索引组织：
  - **聚簇索引**（主键）：叶子节点存**整行数据**——表即索引
  - **二级索引**：叶子存主键值——查询非索引列需**回表**（回聚簇索引取数据）
- B+ 树选择原因：叶子链表利于范围查询、矮树减少磁盘 IO
- 代价：占空间、**拖慢写入**（每次写要维护所有索引）——不是越多越好

**一句话答：** 索引是有序的数据结构，InnoDB 用 B+ 树，千万级数据三层就能定位，还天然支持范围扫描。核心概念是主键即聚簇索引存整行，二级索引存主键值——查非索引列要回表，所以才有覆盖索引这个优化方向。代价是写入要维护所有索引，索引不是越多越好。

### 28. MySQL 有哪些索引类型？

**要点：**
- 按**数据结构**：B+ 树索引（默认主力）、**哈希索引**（Memory 引擎/InnoDB 自适应哈希 AHI——自动）、全文索引（FULLTEXT）
- 按**物理组织**：聚簇索引（主键）/二级（辅助）索引
- 按**字段特性**：
  - **主键索引**（唯一+非空）
  - **唯一索引**（unique——约束+加速）
  - **普通索引**
  - **联合索引**（多列——**最左前缀原则**；可做覆盖索引）
  - **前缀索引**（长字符串取前 N 位——省空间，count(distinct 前缀) 评估区分度）
- 工程要点：联合索引列顺序（区分度高+等值在前）、覆盖索引设计（避免回表）、索引下推 ICP

**一句话答：** 结构上主力是 B+ 树，哈希和全文是特定场景。工程上按用途分：主键、唯一、普通、联合和前缀五种。必考的是联合索引的最左前缀原则——(a,b,c) 索引 a 能用、a+b 能用、b 单独不能用，设计时等值条件列放前面，配合覆盖索引避免回表。

### 29. MySQL 主从模式，如何保证强一致性？

**要点：**
- 认知前提：**异步复制天生非强一致**——要强一致必须改复制协议
- 手段梯度：
  1. **半同步复制（semi-sync）**：至少一个从库**收到 binlog（ACK）**主库才提交——rpl_semi_sync_master_wait_for_slave_count 可调；更严的 AFTER_SYNC（5.7+ 无损复制——before commit）模式
  2. **MGR 组复制**：多数派认证后才提交——真强一致
  3. **应用层**：写后读走主库（一致性要求读强制主）/会话粘滞；事务内读必走主
  4. 中间件：ProxySQL/云代理的读写一致性路由
- 代价：提交延迟增加（等从库网络往返）、从库故障时可用性影响（需要 rpl_semi_sync_master_timeout 降级策略权衡）
- 监控：Rpl_semi_sync_master_status（是否降级为异步了！）、平均 ACK 时间

**一句话答：** 异步复制就谈不上强一致，要强一致换协议：半同步让至少一个从库确认收到 binlog 主库才提交，5.7 之后的 AFTER_SYNC 模式叫无损复制；要求再高就上 MGR 多数派。应用层配合的是写后读强制走主。运维要点是盯住半同步的降级状态——超时降级回异步后你以为的强一致就悄悄失效了。

## Redis 运维面试题

### 1. Redis 有哪些应用场景？

**要点：**
- **缓存**（最主流）：热点数据挡在 DB 前（旁路缓存模式 Cache Aside）
- **分布式锁**：SETNX+过期时间（RedLock/Redisson）
- **计数器/限流器**：INCR 原子性（接口限流、点赞数）
- **排行榜**：ZSet（分数排序、范围查询）
- **分布式 Session**：多实例会话共享
- **消息队列**：List（LPUSH/BRPOP）/ Stream（消费组）
- 其他：布隆过滤器（防穿透）、地理定位 GEO、签到位图 Bitmap

**一句话答：** 高频七大场景：缓存挡数据库读压力、分布式锁、INCR 做计数器和限流、ZSet 做排行榜、Session 共享、List 或 Stream 做轻量消息队列、Bitmap 做签到打卡。每个场景背后用的都是某个数据结构的特性——排行榜靠 ZSet 的有序、锁靠 SETNX 的原子性。

### 2. Redis 单进程为啥还这么快？

**要点：**
- **纯内存操作**——比磁盘快几个数量级（根本原因）
- **单线程无锁竞争**：无上下文切换/无死锁设计（6.0 前）——CPU 不是瓶颈，内存和网络才是
- **IO 多路复用**（epoll）：单线程管理数万连接
- **高效数据结构**：SDS 动态字符串、跳表（ZSet）、压缩列表/紧凑列表、渐进式 rehash
- 事件驱动模型（Reactor 模式）
- 补充：6.0 引入**多线程 IO**（读写网络包多线程，命令执行仍单线程）——吞吐进一步提升

**一句话答：** 四个原因按权重排：纯内存操作是根本，单线程模型消灭了锁竞争和上下文切换，epoll 多路复用让单线程管住几万个连接，再加上精心设计的数据结构——跳表和渐进式 rehash 这些。瓶颈从来不在 CPU 而在内存和网络，所以 6.0 补的多线程也只针对网络 IO，命令执行依然是单线程。

### 3. Redis 支持哪些数据类型？

**要点：**
- **五大基础**：
  - **String**：缓存对象、计数器（INCR）、分布式锁
  - **Hash**：对象字段存储（购物车：用户ID→{商品:数量}）
  - **List**：消息队列、最新列表（LPUSH+LTRIM）
  - **Set**：去重、共同好友（SINTER 交并差）
  - **ZSet**：排行榜、延时队列（score 存时间戳）
- **三种特殊**：**Bitmap**（签到/在线状态——1bit 存一人）、**HyperLogLog**（UV 统计——0.81% 误差省内存）、**GEO**（附近的人）
- 5.0 **Stream**：专业消息队列（消费组/ACK）

**一句话答：** 基础五种加特殊三种：String 管缓存和计数，Hash 管对象和购物车，List 管队列，Set 管去重和交并差，ZSet 管排行榜和延时任务；BitMap 一位存一个人做签到，HyperLogLog 用 KB 级内存估 UV，GEO 做附近的人，Stream 是带消费组的专业消息队列。面试答出"什么场景用什么结构"比背名字值钱。

### 4. Redis 内存回收（淘汰）策略有哪些？

**要点：**
- **过期删除**（key 到期）：
  - **惰性删除**：访问时检查过期才删
  - **定期删除**：周期性随机抽样清理
- **内存淘汰**（maxmemory 满时，8 种）：
  - **noeviction**（默认）：写拒绝——缓存场景不建议
  - **allkeys-lru**：所有 key LRU——**缓存场景标配**
  - volatile-lru/ttl/random（只在设了过期时间的 key 里淘汰）
  - **allkeys-lfu**（4.0+）：按访问频率淘汰——热点更稳定的场景
  - allkeys-random
- 关键认知：**LRU 是近似实现**（采样淘汰，非全局精确）——maxmemory-samples 调精度

**一句话答：** 分两层：key 过期了靠惰性加定期两种方式删除；内存到 maxmemory 上限后按淘汰策略腾地方，八种里记三个关键的——noeviction 默认写报错、allkeys-lru 是缓存场景标配、allkeys-lfu 适合热点分布稳定的场景。Redis 的 LRU 是采样近似实现，不是教科书式的精确 LRU。

### 5. Redis 两种持久化 RDB 和 AOF 有什么区别？

**要点：**
- **RDB**：**定时快照**（fork 子进程全量二进制dump）——文件小恢复快；**两次快照间的数据会丢**（宕机场景）
- **AOF**：**追加日志**记录每条写命令——丢失窗口小（everysec 每秒刷盘，最多丢 1s）；文件大、恢复慢；4.0+ **AOF 重写/混合持久化**（重写基础+增量）优化体积
- fork 阻塞问题：大实例 fork 时**写时复制**——内存翻倍风险+主进程卡顿（页表拷贝）
- 组合策略：
  - 纯缓存可不开持久化
  - 数据重要：**两者都开**（RDB 冷备+容灾恢复，AOF 保数据）
  - 4.0+ 混合模式：RDB 头+AOF 尾——恢复快+丢失少
- 运维监控：fork 耗时（latest_fork_usec）、AOF 重写期间内存

**一句话答：** RDB 是定时全量快照，文件小恢复快但宕机会丢最后一次快照后的数据；AOF 记录每条写命令，everysec 模式最多丢一秒，但文件大恢复慢，4.0 的混合持久化解决了这个问题。共同的大坑是 fork 写时复制——大实例做持久化时内存可能翻倍还卡主线程。数据重要的实例两个都开。

### 6. Redis 内存持续飙升，该如何排查？

**要点：**
- 排查路径：
  1. **INFO memory**：used_memory vs maxmemory、 fragmentation_ratio（碎片率>1.5 异常）
  2. **大 key 扫描**：`redis-cli --bigkeys`（生产用从库/低峰）——String 百 KB 级、集合万元素级即大 key；更精细用 RDB 离线分析工具（rdb-tools/redis-rdb-cli）
  3. **键空间分析**：DBSIZE 异常增长、过期策略是否生效（可能设置了永不过期的缓存）
  4. **业务归因**：新上线功能写入量、缓存未设 TTL、客户端 bug（重复写入）
- 常见根因：**缓存不设过期时间**、大 value（缓存整个页面/大 JSON）、集合类无限增长、碎片率高
- 处理：加 TTL、大 key 拆分（hash 分片）、清理策略（allkeys-lru）、碎片整理（activedefrag）
- 预防：内存告警（70%）、大 key 治理规范、慢日志联动

**一句话答：** 先 INFO memory 分清是数据真多还是碎片率高，然后 --bigkeys 扫大 key——注意这个命令有阻塞风险要在低峰跑。常见根因排行：缓存没设 TTL 永不过期、大 value 缓存、集合类无限增长。处理就是加过期时间、大 key 拆分、必要时开 activedefrag 整理碎片，预防靠 70% 水位告警。

### 7. 使用 Redis INFO 命令查看哪些关键指标？

**要点：**
- **memory 段**：used_memory（实际用量）、mem_fragmentation_ratio（碎片率，>1.5 异常）、maxmemory
- **stats 段**：**total_commands_processed**（QPS 基础）、instantaneous_ops_per_sec、expired_keys、evicted_keys（**>0 说明内存淘汰在发生**——缓存场景要警惕）、keyspace_hits/misses（**命中率**——缓存核心指标）
- **clients 段**：connected_clients、blocked_clients（阻塞客户端——BLPOP 类）
- **replication 段**：主从角色、master_link_status（up/down）、master_repl_offset 与 slave 差值（复制延迟字节）
- **persistence 段**：rdb_last_bgsave_status（持久化是否成功）、aof_delayed_fsync、latest_fork_usec（fork 耗时）
- 接入：redis_exporter → Prometheus 全自动采集

**一句话答：** 五个段落挑重点：memory 段的用量和碎片率，stats 段的 QPS、命中率和 evicted_keys——出现淘汰说明内存已经紧张，clients 段的连接数和阻塞数，replication 段的主从状态和延迟字节，persistence 段的 RDB 备份状态和 fork 耗时。命中率加内存水位这两个是缓存健康的核心判据。

### 8. 简述 Redis 主从复制工作原理？

**要点：**
- 全量同步（首次/断线过久）：从库发 PSYNC → 主库 **bgsave 生成 RDB** → 传输给从库加载 → 期间新写命令缓存 → RDB 加载完后发送增量 → 持续传播
- 增量同步（短暂断线）：**复制积压缓冲区（repl_backlog，环形）**——从库带 offset 回来，offset 还在缓冲区内则只补差量（repl_backlog_size 要按写入速率×断线容忍时长配置）
- 传播：主库命令异步发给从库（无 ACK 等待——异步复制）
- 命令传播 + 心跳（REPLCONF ACK 上报 offset）
- 级联复制：从库挂从库，减轻主库压力
- 潜在问题：主库写入量>缓冲区速度→全量重同步风暴；主库 fork 卡顿

**一句话答：** 主从复制分两种：首次全量是主库 bgsave 生成 RDB 传过去加载，断线重连如果 offset 还在环形积压缓冲区内就只补差量做增量同步。之后命令持续异步传播。运维要点是 repl_backlog_size 要按写入速率和容忍断线时长来配，配小了断线稍微久一点就触发全量重同步，主库会被 RDB 压垮。

### 9. Redis 主从复制延迟过高怎么解决？

**要点：**
- 原因定位：
  1. **主库写入量暴增**（大 key 频繁写/大事务）
  2. 从库资源不足（CPU 单线程处理重放慢——从库关闭透明大页/调大 repl-timeout）
  3. **网络带宽**（跨机房/大 value 传输）
  4. 主库 fork 卡顿（RDB 持久化）阻塞命令传播
- 解决：
  - 拆分大 key、写入批量化
  - 从库规格升级/独享、**读写分离的读路由按延迟摘除**（客户端/中间件感知）
  - 主从同机房部署（对延迟敏感场景）
  - 关键读走主库（一致性要求场景）
  - repl_backlog_size 加大避免全量重同步恶化
- 监控：master_repl_offset 与 slave offset 差值、从库 QPS 对比主库

**一句话答：** 延迟高先分清是主库写太多、从库处理太慢还是网络带宽不够。处理手段按因下药：拆大 key 减少传播量，从库升级配置独享资源，延迟敏感场景主从放同机房。业务侧兜底是客户端按延迟感知路由——落后的从库暂时摘除，一致性敏感的读强制走主。

### 10. Redis 高可用方案有哪些？

**要点：**
- **主从+哨兵（Sentinel）**：经典方案——3 哨兵+1 主 2 从；自动故障检测与切换；**容量固定单机**（不支持水平扩展）
- **Redis Cluster**：官方分布式方案——**16384 槽位分片**，数据水平拆分；每个分片内主从；故障自动转移；客户端直连（MOVED 重定向/智能客户端）
- **云托管**：云 Redis 高可用集群版（省心）
- **Proxy 层方案**：Codis/Twemproxy（老方案）——客户端透明分片
- **主从+keepalived**（不推荐——脑裂风险，数据丢失场景）
- 选型：数据量 <25GB 且无分片需求 → 哨兵；海量数据/高吞吐 → Cluster

**一句话答：** 两主一备：哨兵方案解决高可用不解决容量——单机内存上限摆在那；Cluster 方案既高可用又水平扩展，16384 个槽位分片加每个分片自带主从。数据量小够用就哨兵，数据量大或者写入高就直接上 Cluster。keepalived 那套在 Redis 上有脑裂风险，别用。

### 11. 什么是 Redis 哨兵模式（Sentinel）？

**要点：**
- Sentinel = Redis 官方**高可用监督组件**（独立进程，至少 3 个奇数部署——防脑裂）
- 四大职责：
  1. **监控**：持续 ping 主从库
  2. **主观下线**（SDOWN）：单个哨兵认为主挂了
  3. **客观下线**（ODOWN）：**quorum 个哨兵**达成共识才算真挂——防误判
  4. **自动故障转移**：选举 **leader 哨兵**（Raft 式）→ 从从库中选**数据最新的**提升为主 → 通知其他从库换主 → 通知客户端
- 选从库标准：优先级、复制 offset（数据最新）、runid
- 配置：sentinel monitor <name> <ip> <port> <quorum>；客户端通过哨兵发现当前主（而非直连）

**一句话答：** 哨兵是 Redis 的自动故障转移组件，部署奇数个至少三个。工作流程四步：监控探活，单个哨兵 ping 不通算主观下线，超过 quorum 个共识才算客观下线，然后哨兵们选出一个 leader 执行切换——挑数据最新的从库转正并通知全集群。防误判靠 quorum 机制，客户端永远问哨兵要主地址而不是写死 IP。

### 12. 哨兵模式（Sentinel）下应用程序如何连接？

**要点：**
- **不直连 Redis**——连哨兵获取当前主库地址：
  - 配置哨兵节点列表（多个）+ master name
  - 客户端流程：问任一哨兵"谁在当主"（SENTINEL get-master-addr-by-name）→ 拿地址连接 → **主切换时哨兵推送/客户端重新发现**
- 客户端支持：Jedis/Lettuce/Spring Data Redis 内置哨兵模式配置；redis-py 的 Sentinel 对象
- 连接池注意：切换期间短暂不可用——**重试+超时**设计；读写分离需客户端自行实现（读连从库）
- 验证：手动 kill 主库演练故障转移、观察应用恢复时间

**一句话答：** 应用不写死 Redis 地址，配置的是哨兵列表加主库名字：启动时问哨兵当前谁是主，主挂掉切换后客户端通过订阅哨兵通知或重试重新发现新主。所以故障转移对应用是无感的，只需要做好切换瞬间的重试。上线前务必手动 kill 主库演练一次，量一下真实恢复时长。

### 13. 简述 Redis Cluster 工作原理？

**要点：**
- **数据分片**：整个键空间分 **16384 个槽（slot）**——key 经 CRC16 % 16384 定位槽；槽分配到节点（cluster addslots）
- **路由**：客户端直连任意节点——不命中时返回 **MOVED** 重定向（智能客户端缓存槽位表直接路由）；ASK（迁移中临时）
- **高可用**：每分片一主多从；节点间 **Gossip 协议**交换状态；主挂→**多数派主节点选举**其从库升主（无需哨兵）
- 扩缩容：**槽迁移**（cluster setslot）——数据在线搬迁
- 限制：**多 key 命令/事务/Lua 需同槽**（hash tag {user1} 强制同槽）；DB0 单库；select 不支持
- 部署：至少 3 主 3 从（6 节点）；集群模式要求所有 key 操作可路由

**一句话答：** Cluster 把键空间切成 16384 个槽分给各节点，key 按 CRC16 取模定位，客户端直连节点打错了就收 MOVED 重定向——智能客户端会缓存槽位表直接路由对端。高可用不需要哨兵：节点间 Gossip 通信，分片的主挂了由其余主节点多数派投票让从库上位。最大的开发限制是多 key 操作必须同槽，要用 hash tag 把相关 key 绑到一起。

### 14. Redis Cluster 集群不可用的常见原因及解决方法？

**要点：**
- 常见不可用场景：
  1. **分片主从全挂**：该槽位段不可用（数据非全丢——仅该分片）；预防：主从跨机部署
  2. **集群状态 fail**（cluster_state=fail）：多数主节点下线/槽未全分配——**需要多数派存活才能选举**；处理：恢复节点/强制 failover
  3. **槽迁移中断**（迁移中节点挂）：槽处于过渡状态——cluster setslot 修复/继续迁移
  4. **网络分区脑裂**：小分区变主的从库丢数据（旧主恢复后同步）——min-replicas-to-write 限制写（牺牲可用性保一致）
  5. 客户端路由缓存失效风暴（大范围主切换后 MOVED 风暴）
- 排查：cluster info（state/slots_assigned）、cluster nodes（拓扑/下线标记）、节点日志
- 预防：主从跨机架、min-replicas-to-write=1、监控 cluster_state

**一句话答：** 不可用三大原因：某个分片主从全挂导致那段槽位不可用——所以主从必须跨机放；多数主节点下线导致集群无法选举直接 fail；还有槽迁移中途出问题卡在过渡态。排查入口是 cluster info 和 cluster nodes 看状态和拓扑。防脑裂的关键参数是 min-replicas-to-write——主库发现没有从库连着就拒绝写，宁停不丢。

### 15. Redis 阻塞、卡顿怎么处理？

**要点：**
- 排查清单（按频率）：
  1. **大 key 操作**：百万级元素的 DEL/全量读取——用 UNLINK（异步删除）/SCAN 分批
  2. **CPU 饱和**：慢命令（KEYS *——禁用/用 SCAN、HGETALL 大 hash）、QPS 超硬件
  3. **持久化 fork 阻塞**：RDB/AOF 重写时 fork 卡顿（大实例）——监控 latest_fork_usec；低峰执行/关闭 RDB 用 AOF
  4. **内存交换**：宿主机内存不足 Redis 被换出（延迟飙升特征）——锁定内存/保证宿主余量
  5. **网络/客户端**：连接数暴增、大 value 传输占带宽
  6. AOF fsync 阻塞（appendfsync always）
- 定位工具：**SLOWLOG GET**（慢命令日志）、LATENCY HISTORY/EVENT（延迟监控框架）、bigkeys/大 key 扫描、perf 火焰图（进阶）
- 预防：禁用危险命令（rename-command KEYS ""）、key 规范、监控 QPS 与延迟 P99

**一句话答：** 排查按频率走：先查慢日志和延迟监控定位是哪类操作卡——大 key 删除用 UNLINK 异步化，KEYS 命令必须禁掉换 SCAN；再查 fork 耗时，大实例 RDB 持久化的 fork 卡顿很典型；最后查宿主机有没有发生内存交换——那是延迟飙升的隐形杀手。预防上把危险命令 rename 禁用、key 设计进规范。

### 16. 如何优化 Redis 的性能？

**要点：**
- **数据设计**：避免大 key（hash 分片）、避免热 key（本地缓存+副本打散）、合理 TTL（防堆积）
- **命令层**：批量化（MGET/pipeline——省 RTT）、禁用慢命令（KEYS/全量 SMEMBERS）、SCAN 替代
- **连接层**：连接池（避免每次新建）、合理超时
- **架构层**：读写分离（读扩从库）、分片扩容（Cluster）、冷热分离
- **服务端配置**：TCP backlog、maxclients、activedefrag（碎片）、透明大页**关闭**（THP 导致 fork 卡顿）
- **监控驱动**：慢日志定期分析、QPS/延迟基线、命中率优化（缓存逻辑）
- 硬件：高内存频率/内核参数（somaxconn、netdev backlog）

**一句话答：** 性能优化从数据到命令到架构三层：数据层避免大 key 热 key 并统一设 TTL；命令层用 pipeline 和 MGET 批量化省网络往返，KEYS 这类全量命令坚决禁用；架构层读写分离加分片。服务端必做的两件事是关闭透明大页和用连接池。所有优化都要由慢日志和延迟监控的数据驱动。

### 17. Redis 6.0 多线程有了解过吗？

**要点：**
- 6.0 引入**多线程 IO**（默认关闭）：
  - **范围**：**网络读写与协议解析**多线程化——**命令执行仍单线程**（保持原子性与无锁设计）
  - 动机：网络 IO 成为大实例瓶颈（10G 网卡跑不满）——并行处理网络包
- 配置：io-threads 4、io-threads-do-reads yes；建议 2-4 核开 2-4 线程（>8 收益小）
- 收益：大流量高 QPS 场景吞吐显著提升；小实例/低 QPS 无感甚至有调度开销
- 争议澄清：**不是把 Redis 改成多线程执行命令**——数据结构操作的线程安全模型不变
- 其他 6.0 特性顺带：ACL 权限、RESP3、客户端缓存

**一句话答：** 6.0 的多线程只用在网络读写和协议解析上，命令执行依然是单线程——所以原子性模型完全没变，这是和 Memcached 多线程的本质区别。它解决的是大网卡高吞吐场景下网络 IO 成瓶颈的问题，配置 io-threads 一般开 2 到 4。小实例低负载开着反而有调度开销。

### 18. Redis 慢查询日志是什么？

**要点：**
- 慢查询日志：**执行时长超过阈值**的命令记录（**只记命令执行时间**，不含网络/排队）
- 配置：slowlog-log-slower-than（默认 10000 微秒=10ms——建议 1-5ms）、slowlog-max-len（内存中保留条数，默认 128——建议 512+）
- 使用：SLOWLOG GET [n] 查看耗时+命令+客户端、SLOWLOG LEN、SLOWLOG RESET
- 特点：内存环形列表（不落盘）——重启丢失；定期采集到监控系统
- 分析价值：定位大 key、慢命令（全量集合操作）、优化数据结构
- 注意：查慢日志本身要快；配合 LATENCY 命令看整体延迟事件

**一句话答：** 慢查询日志记录执行超阈值的命令——注意只算命令本身执行时间不算网络排队。默认阈值 10ms 太宽松建议调到 1-5ms，日志是内存环形列表重启就丢，所以要定期采集进监控系统。它的最大价值是揪出大 key 和全量集合操作这类性能杀手。

### 19. Redis 一般会监控哪些指标？

**要点：**
- **性能**：QPS（instantaneous_ops）、**延迟 P99**（关键体验指标）、慢查询数增速
- **内存**：used_memory/maxmemory 比例（70% 告警）、**碎片率**、淘汰数（evicted_keys>0 告警）
- **命中率**：keyspace_hits/misses——缓存有效性核心（<90% 检查缓存逻辑）
- **连接**：connected_clients（逼近 maxclients 告警）、blocked_clients
- **复制**：主从状态、**复制延迟**（offset 差值）、从库数量
- **持久化**：RDB 最后备份状态/耗时、AOF 状态、fork 耗时
- **集群**：cluster_state、槽覆盖完整性、节点下线
- 工具：redis_exporter + Prometheus + Grafana 模板；关键告警：内存 70%/淘汰发生/延迟阈值/主从断开

**一句话答：** 七组指标按优先级：延迟 P99 和 QPS 是体验面，内存水位和淘汰数是容量面——出现淘汰就说明该扩了，命中率是缓存有效性的核心判据，再配连接数、主从延迟、持久化状态和集群健康度。告警阈值建议内存 70% 起步，主从断开和延迟超阈是最高级别。

### 20. Redis 如何提高安全性？

**要点：**
- **网络隔离**（第一道墙）：**绑内网 IP**（bind 127.0.0.1/内网）、**禁用公网访问**（公网裸奔 Redis = 挖矿植入重灾区）、防火墙/VPC 安全组白名单
- **认证**：requirepass/ACL（6.0 用户级权限——按命令前缀/key 模式授权）、TLS 加密传输（6.0+）
- **危险命令管控**：rename-command 禁用（FLUSHALL/KEYS/CONFIG）或 ACL 拒绝
- **运行安全**：非 root 运行、protected-mode、禁用或慎用危险模块加载
- **注入风险**：Lua 脚本注入控制、客户端输入校验（防命令注入拼接）
- 审计与备份：慢日志/监控、定期备份（RDB 异地）
- 经典事故反例：公网 6379+ 无密码 = 被写 crontab 植入挖矿——运维必知案例

**一句话答：** 安全四层：网络层绑内网加安全组白名单——公网裸奔的 Redis 是挖矿木马重灾区，这是运维必知案例；认证层 requirepass 或 6.0 的 ACL 用户级权限；命令层把 FLUSHALL、KEYS 这类危险命令 rename 禁用；运行层非 root 加 TLS 加密传输。最痛的教训往往是有人为了图方便把 6379 映射到了公网。

## PostgreSQL 运维面试题

### 1. PostgreSQL 与 MySQL 的核心区别有哪些？

**要点：**
- **功能丰富度**：PG 有**更完整的 SQL 标准实现**——CTE/窗口函数（MySQL 8.0 才有）、**JSONB 原生强类型查询**、数组/范围类型、GIS（PostGIS）、自定义类型
- **MVCC 实现差异**：PG 旧版本行保留在表内（**需 VACUUM 清理**）vs MySQL undo log 回滚段——PG 有**表膨胀**问题，MySQL 有长事务问题
- **复制**：PG **物理流复制**（主从字节级一致）+ 逻辑复制（10+）；MySQL binlog 逻辑复制
- **架构**：PG **进程模型**（每连接一进程）vs MySQL 线程模型——PG 单连接开销大，需要连接池（PgBouncer）
- **扩展性**：PG **扩展生态**强（TimescaleDB/Citus/PostGIS）；MySQL 插件少
- 选择：复杂查询/JSON/分析 → PG；简单 web 场景生态 → MySQL；两者都是优秀关系库

**一句话答：** 差异抓四点：PG 的 SQL 标准实现和扩展生态更完整——JSONB、窗口函数、PostGIS；MVCC 实现不同导致 PG 有表膨胀要 VACUUM、MySQL 有长事务问题；PG 是进程模型单连接开销大需要配 PgBouncer，MySQL 是线程模型；复制上 PG 主打物理流复制字节级一致。选型上复杂查询和分析场景 PG 优势明显。

### 2. 简述 PostgreSQL 进程架构？

**要点：**
- **每客户端连接 = 一个独立后端进程**（fork 模型，非线程）
- 常驻后台进程：
  - **postmaster**：主进程——监听、fork 后端、管理子进程
  - **checkpointer**：检查点刷脏页
  - **bgwriter**：后台写脏页（平滑 IO）
  - **walwriter**：WAL 日志刷盘
  - **autovacuum launcher/worker**：自动清理
  - **WAL sender**（主库）/**WAL receiver**（从库）：流复制
  - stats collector：统计信息
- 影响：**连接很贵**（进程内存+创建开销）→ 生产必配**连接池**（PgBouncer——事务级池化最佳）
- max_connections 不能盲目调大（每连接内存）

**一句话答：** PG 是进程模型：每个客户端连接 fork 一个独立后端进程，后台常驻的有 postmaster 总管、checkpointer、bgwriter、walwriter 和 autovacuum 这些守护进程。工程结论就是连接很贵——生产必须上 PgBouncer 做连接池，max_connections 别盲目调大，每个连接都是真金白银的内存。

### 3. WAL 机制的核心作用是什么？

**要点：**
- WAL（Write-Ahead Logging）：**先写日志，后写数据页**——变更先顺序追加到 WAL，脏页延后刷
- 三大作用：
  1. **崩溃恢复**：宕机后重放 WAL 把已提交事务恢复——**保证持久性（D）**
  2. **性能**：顺序写 WAL 替代随机写数据页——吞吐大幅提升（数据页在内存改，后台批量刷）
  3. **复制基础**：**物理流复制就是传 WAL**——从库重放即同步；PITR 归档恢复
- 关键参数：wal_level（replica/logical）、synchronous_commit、checkpoint 调度（max_wal_size）
- 对比 MySQL：WAL ≈ redo log（物理层）；PG 没有独立 binlog——WAL 兼职复制与恢复

**一句话答：** WAL 的原则是先写日志再写数据：变更先顺序追加到 WAL 文件，数据页留在内存延后批量刷盘。它一石三鸟——宕机后重放 WAL 保证事务持久性，顺序写替代随机写提升性能，流复制直接传 WAL 给从库重放。可以理解为 PG 把 MySQL 的 redo log 和 binlog 合成了一个。

### 4. 新部署的PGSQL，如何优化配置？

**要点：**
- **内存**：**shared_buffers = 25% 内存**（PG 缓存）、**effective_cache_size = 50-70%**（优化器估值用）、work_mem（排序/哈希——按连接数算，不能太大）
- **WAL/检查点**：max_wal_size 调大（默认 1GB 太小——频繁 checkpoint 抖动）、checkpoint_completion_target=0.9
- **连接**：max_connections 适度 + **PgBouncer**（进程模型决定）
- **VACUUM**：autovacuum 基础上按表调（高频更新表 max autovacuum workers）
- **规划器**：default_statistics_target=100~500、random_page_cost=1.1（SSD）
- **持久化权衡**：synchronous_commit（金融 on、一般 off/remote_write）
- 工具起步：**PGTune**（pgtune.leopard.in.ua）按硬件生成基线——再压测微调
- 系统层：transparent_hugepages off、vm.overcommit_memory=2、共享内存参数

**一句话答：** 新装 PG 用 PGTune 生成基线再压测微调。重点参数五组：shared_buffers 给 25% 内存加 effective_cache_size 报告真实缓存，max_wal_size 调大避免频繁 checkpoint 抖动，work_mem 按连接数谨慎给，连接层配 PgBouncer，SSD 上 random_page_cost 降到 1.1 让优化器走对索引。系统层记得关透明大页。

### 5. Autovacuum 是什么？有什么作用？

**要点：**
- PG MVCC 的 DELETE/UPDATE 不物理删旧行——旧版本（死元组）留在表内；**autovacuum 就是自动清理死元组的后台进程**
- 作用：
  1. **回收死元组空间**（供表内复用——不是还盘）
  2. **冻结旧事务 ID（XID wraparound 防护）**——20 亿事务 ID 回卷保护（强制 vacuum）
  3. **更新统计信息**（analyze）——优化器依赖
  4. FSM 维护
- 触发：死元组超阈值（autovacuum_vacuum_scale_factor × 行数+阈值）
- 高频更新大表需手动调低 scale_factor（如 0.01）加速清理

**一句话答：** PG 的 MVCC 删除和更新不物理删旧行，死元组全留在表里，autovacuum 就是负责打扫的进程：清理死元组供空间复用、冻结事务 ID 防止 20 亿回卷灾难、顺带更新统计信息。它默认触发阈值对大表太宽松，高频更新的表要单独调小 scale_factor。

### 6. Autovacuum 失效会有什么后果？

**要点：**
- 后果链：
  1. **表膨胀**：死元组堆积——表/索引体积虚增、查询扫描变慢、缓存效率降
  2. **XID 回卷（wraparound）**：事务 ID 耗尽 → PG **强制停库只读**（"database is not accepting commands to avoid wraparound"）——**最严重后果**
  3. 统计信息过期 → 优化器选错执行计划
  4. 磁盘空间虚高
- 失效原因：autovacuum 被手动关闭、worker 被**长事务阻塞**（死元组不能越过最早活跃事务清理）、锁冲突、max_worker 太少忙不过来
- 处理：查 pg_stat_user_tables 的 dead_tup 比例、kill 长事务、手动 VACUUM (VERBOSE)/VACUUM FULL（锁表慎用）、pg_repack 在线收缩

**一句话答：** autovacuum 失效的直接后果是表膨胀越扫越慢，最致命的是事务 ID 回卷——PG 会强制停库变只读保护自己。失效常见原因是被长事务卡住：死元组不能早于最老活跃事务清理，所以揪出长事务是第一动作，然后用 pg_repack 在线收缩膨胀的表。

### 7. MVCC 是什么？有什么作用？

**要点：**
- MVCC（多版本并发控制）：**每行保存多个版本**——读写不互相阻塞
- 实现：每行带 xmin（创建事务 ID）/xmax（删除事务 ID），快照判断哪个版本对当前事务可见
- 作用：
  1. **读不阻塞写、写不阻塞读**——并发性能核心
  2. 一致性读：事务内看到一致快照（RC/RR 隔离级别）
- 副作用：旧版本堆积 → **VACUUM 的存在原因**（PG 特色）；长事务拖住版本清理
- 对比：MySQL InnoDB 也是 MVCC（undo 版本链）——旧版本在 undo 而非表内

**一句话答：** MVCC 就是给每行数据留多个版本，靠事务 ID 判断哪个版本对当前事务可见，实现读不阻塞写、写不阻塞读。PG 的特色是旧版本直接留在表里靠 VACUUM 清理，所以才有表膨胀问题——这是它与 MySQL 把旧版本放 undo 段的实现差异。

### 8. PGSQL 查询慢，如何排查？

**要点：**
- 工具链：
  1. **pg_stat_statements**（必装扩展）：聚合 Top SQL（总耗时/调用/均值）——定位慢 SQL 清单
  2. **EXPLAIN (ANALYZE, BUFFERS)**：真实执行计划+实际耗时+IO——重点看
     - **Seq Scan 大表**（缺索引/统计过期）
     - Nested Loop 行数估算爆炸（统计信息问题）
     - **Buffers: shared read** 高（缓存未命中）
  3. 统计信息：ANALYZE 更新；pg_stat_activity 看当前执行（wait_event 区分 IO/锁等待）
- 常见病因：缺索引、**统计信息过期导致计划错误**、work_mem 不足（磁盘临时）、表膨胀（死元组多）、锁等待
- 优化：加索引、调 work_mem、VACUUM 收缩、hint 扩展（pg_hint_plan）或改写 SQL

**一句话答：** 先装 pg_stat_statements 找出最耗时的 Top SQL，再用 EXPLAIN ANALYZE BUFFERS 看真实执行计划——重点三处：大表 Seq Scan 是缺索引，估算行数和实际差几个数量级是统计信息过期要 ANALYZE，Buffers read 高说明缓存没命中。PG 特有的病因还有表膨胀，VACUUM 状况也要查。

### 9. PGSQL 有哪些备份方案？

**要点：**
- **逻辑备份**：**pg_dump/pg_dumpall**（单库/全实例，一致性快照不锁写——MVCC 保证）；pg_restore 并行恢复
- **物理备份+归档**（生产标准）：**pg_basebackup**（基础备份）+ **WAL 归档**（archive_command）——实现 **PITR 任意时间点恢复**
- **成熟工具**：**pgBackRest**（并行/增量/压缩/校验——生产首选）、barman、wal-g
- **快照**：云盘快照（配合 pg_start_backup 或直接快照一致性）
- 策略：每日基础备份+持续 WAL 归档+异地存储+**恢复演练**；RPO 决定 WAL 归档频率
- 主从即热备：延迟从库（recovery_min_apply_delay）做防误删保险

**一句话答：** 逻辑备份用 pg_dump 适合中小库，生产标准方案是 pgBackRest 这类工具做基础备份加 WAL 持续归档——两者配合才能实现任意时间点恢复。云上直接盘快照也行。额外推荐一个低成本保险：配一个延迟回放的从库，误删表时还能从延迟从库里捞回来。

### 10. PGSQL 当前连接数如何查看？

**要点：**
- **pg_stat_activity**：`SELECT count(*) FROM pg_stat_activity;`——按 state 分组（active/idle/idle in transaction）
- 关注点：
  - **idle in transaction**：事务开着不提交——**阻塞 vacuum、锁持有者**（有害状态，设 idle_in_transaction_session_timeout）
  - 连接来源（application_name/client_addr）——定位哪个应用占连接
  - 超限：`FATAL: sorry, too many clients already`（max_connections 满）
- 配套：max_connections 查看、pg_stat_activity 的 wait_event 判断在等什么
- 管理手段：pg_terminate_backend(pid) 杀连接、PgBouncer 收口连接

**一句话答：** 查 pg_stat_activity 按 state 分组统计，重点盯 idle in transaction 这个有害状态——事务开着不提交会阻塞 vacuum 还持有锁，要配超时参数自动掐掉。按 client_addr 分组能定位是哪个应用把连接占满了，临时救急用 pg_terminate_backend 杀会话，根治还是上 PgBouncer。

### 11. PGSQL 怎么查看锁等待与死锁？

**要点：**
- **锁等待查询**（经典 SQL）：pg_locks join pg_stat_activity——找 granted=false 的等待者，按 lock 关联到持有者
- 系统视图：pg_blocking_pids(pid)（PG 9.6+——直接给阻塞者 PID，最简单）
- 死锁：PG **自动检测**（deadlock_timeout 默认 1s）自动回滚一方并记日志——日志关键字 "deadlock detected" 带完整锁链
- 锁类型认知：**表级锁**（ACCESS EXCLUSIVE——DDL 阻塞一切；ALTER TABLE 要小心）、**行级锁**、 advisory lock
- 排查工具：pg_stat_activity 的 wait_event_type=Lock；pg_locks 的 mode 与 granted 列
- 预防：DDL 用 lock_timeout、短事务、统一加锁顺序

**一句话答：** 查锁等待最省事的是 pg_blocking_pids 函数，直接告诉你谁被谁堵着；配合 pg_locks 和 pg_stat_activity 看锁模式和等待事件。死锁 PG 会自动检测回滚，日志里有完整的锁等待链。特别要小心 DDL 拿的是表级排他锁，生产上改表结构必须带 lock_timeout。

### 12. PGSQL 出现 OOM 有哪些常见原因及解决方案？

**要点：**
- 原因：
  1. **work_mem × 并发连接** 爆炸（每个排序/哈希节点可申请一份 work_mem——并行下更多）
  2. **连接数过多**（进程模型——每连接数 MB 内存）
  3. **maintenance_work_mem** 过大（VACUUM/建索引时）
  4. **内核 overcommit**：vm.overcommit_memory=0 宽松承诺——真用时 OOM killer 杀 postmaster（最惨场景：**PG 全家桶被杀**）
- 解决：
  - 参数预算：work_mem 谨慎（按 排序并发×复杂查询 估算）、joint/maintenance 分开设
  - **内存上限**：cgroup/容器 limit 对齐、PG 13+ hash_mem_multiplier 调节
  - **内核**：vm.overcommit_memory=2 + vm.overcommit_ratio（禁止超卖）——防止 OOM killer 杀 postmaster
  - cgroup 优先保护 PG（oom_score_adj）
- 排查：dmesg OOM 记录、日志 "out of memory"、pg_stat_activity 时点分析

**一句话答：** PG 的 OOM 基本三类：work_mem 乘上并发连接数爆了、连接太多进程模型扛不住、还有内核 overcommit 放水导致 OOM killer 直接杀 postmaster——这是最惨的，整个实例全挂。解法是 work_mem 按并发量谨慎估、内核把 overcommit_memory 设成 2 禁止超卖，容器里再给 PG 配上 oom_score_adj 保护。

### 13. PGSQL 主流高可用方案有哪些？

**要点：**
- **Patroni + etcd**（事实标准）：流复制+分布式选主（DCS）+自动故障转移+配置统一管理（pg_ctl 托管）
- **流复制+手动/脚本切换**：简单场景，配合 repmgr（管理工具）
- **pgpool-II**：中间件层——连接池+读写分离+看门狗 VIP
- **云 RDS**：托管高可用
- **Stolon**：云原生（K8s 友好）
- 搭配件：PgBouncer（连接池）+ HAProxy（探活分流）
- 选型：自建首选 Patroni（社区生态、文档、案例最多）；K8s 环境 Patroni Operator 或云原生方案

**一句话答：** 事实标准是 Patroni 加 etcd：底层流复制保证数据同步，etcd 做分布式选主防脑裂，Patroni 管故障转移和配置统一。简单场景可以用 repmgr 轻量管理，K8s 里用 Patroni 的 Operator 形态。无论哪个方案，连接层都要配 PgBouncer，这是 PG 架构的固定搭配。

### 14. 简述 PGSQL 流复制工作原理？

**要点：**
- 流复制（Streaming Replication）= **主库实时把 WAL 记录流式传给从库**（物理复制——块级字节一致）
- 流程：
  1. 从库 walreceiver 连主库 wal sender
  2. 主库产生 WAL → **同步传 WAL 流**（异步/半同步由 synchronous_commit 控制）
  3. 从库先写本地 WAL → **startup 进程重放**恢复数据页
- 模式：**异步**（默认——主不等从）、**同步复制**（synchronous_standby_names——至少一个从库确认收到 WAL 才提交）
- 复制槽（replication slot）：防止 WAL 在从库落后时被主库回收（防追不上）；**风险：从库长期宕机会撑爆主库磁盘**——监控 slot 落后
- 查询延迟：pg_stat_replication 的 replay_lag；热备从库可只读查询（hot_standby=on）

**一句话答：** 流复制是主库把 WAL 字节流实时推给从库，从库先落本地 WAL 再由 startup 进程重放——这是物理复制，从库和主库块级一致。默认异步，配 synchronous_standby_names 可升级为半同步。必配复制槽防止 WAL 被提前回收，但要盯着槽的落后量——从库长期宕机会把主库磁盘撑爆。

### 15. PGSQL 主从延迟原因及优化方法？

**要点：**
- 原因：
  1. **重放单进程**（从库 startup 进程单线程重放——PG 的天然瓶颈；13+ 恢复并行化部分场景）
  2. **热备冲突**：从库上长查询与 WAL 重放冲突（max_standby_streaming_delay）——重放被延迟
  3. 网络/主库写入洪峰（大批量导入、大事务）
  4. 从库硬件差
- 解决：
  - 热备冲突：hot_standby_feedback（从库向主库报活跃事务——代价是主库膨胀风险）或调整 delay 参数权衡
  - 大事务拆小、批量导入错峰
  - **分区表**（13+ 并行重放按分区）
  - 从库升级/网络优化
- 监控：pg_stat_replication（write/flush/replay_lag 三段延迟）
- 应用兜底：读写分离时一致性敏感读走主、中间件按延迟路由

**一句话答：** PG 从库重放是单进程的，主库写入洪峰时天然追不上，这是架构性瓶颈。特有原因还有热备冲突——从库上的长查询会拖住 WAL 重放，靠 hot_standby_feedback 换取重放流畅但代价是主库膨胀。缓解手段包括分区表让新版并行重放生效，业务侧一致性敏感的读走主库兜底。

### 16. 实际工作中遇到过表膨胀吗？如何定位和解决？

**要点：**
- 定位：
  - `pg_stat_user_tables`：n_dead_tup（死元组数）/n_live_tup 比例——>20% 警惕
  - 表体积 vs 实际数据量对比（pg_relation_size vs count 估算）
  - pgstattuple 扩展：精确死元组占比
- 根因：autovacuum 追不上（阈值太松/worker 不足）、**长事务阻塞清理**、高频 UPDATE 表
- 解决：
  - 常规：调低该表 autovacuum_vacuum_scale_factor、加 worker、ANALYZE
  - **在线收缩**：**pg_repack**（不长时间锁表——生产推荐）
  - VACUUM FULL：锁表重建——只允许维护窗口
  - 根治长事务：idle_in_transaction_session_timeout、应用代码审查
- 预防：监控死元组率、大表定制 vacuum 参数、长事务告警

**一句话答：** 用 pg_stat_user_tables 看 dead_tup 和 live_tup 的比例，超过两成就算膨胀。根因九成是 autovacuum 追不上或者被长事务卡住。处理首选 pg_repack 在线重建不锁表，VACUUM FULL 那个锁表版本只敢在维护窗口用。预防要给大表定制更激进的 vacuum 参数加长事务告警。

### 17. PGSQL 如何实现读写分离？

**要点：**
- 架构：主写 + 流复制从库（多台）读——**从库只读**（hot_standby）
- 路由实现：
  1. **应用侧**：双数据源（读写各自 DSN）
  2. **中间件**：**pgpool-II**（自动读写分离+连接池）、HAProxy+探活分流、PgBouncer（只做池化不做路由——需搭配）
  3. **DNS/服务发现**轮询
- 关键问题（与 MySQL 类似）：
  - **复制延迟一致性**：写后立刻读——应用强制主/pgpool 的复制一致性判断
  - **从库只读限制**：写语句报错（transaction read-only）
  - 序列号/时序场景注意
- 配套：从库健康检查（SELECT 1+延迟阈值摘除）、连接池收口

**一句话答：** PG 读写分离的架子是主写加流复制从库读，路由三选一：应用双数据源、pgpool-II 自动分离、HAProxy 按健康检查分流。注意 PgBouncer 只管连接池不做读写路由，要配着用。和 MySQL 一样，写后立刻读的一致性场景必须强制走主库。

### 18. PGSQL 一般会监控哪些指标？

**要点：**
- **可用性/连接**：存活、连接数/max_connections（80% 告警）、idle in transaction 数量（有害状态）
- **性能**：QPS/事务数、**慢查询**（pg_stat_statements Top）、缓存命中率（shared buffer 命中 >99%）、临时文件使用（work_mem 不足信号）
- **复制**：主从延迟（replay_lag）、WAL sender 状态、**复制槽落后量**（防主库磁盘撑爆——关键告警）
- **vacuum/膨胀**：dead_tup 比例、autovacuum 运行状况、**最老事务年龄**（XID wraparound 前兆——超 15 亿告警）
- **锁**：锁等待数、死锁频率
- **WAL/磁盘**：WAL 产生速率、磁盘空间（WAL 积压、表增长）
- 工具：postgres_exporter + Prometheus；定制 SQL 监控（pg_stat_statements 定期采集）

**一句话答：** 六大维度里 PG 特有的三个必须点名：最老事务年龄——逼近 20 亿就是 XID 回卷停库的前兆，复制槽落后量——从库宕机会撑爆主库磁盘，还有死元组比例和 idle in transaction 这两个膨胀与阻塞信号。加上常规的连接数、命中率、主从延迟和磁盘水位，用 postgres_exporter 接 Prometheus 全覆盖。

### 19. PGSQL 物理流复制与逻辑复制有什么区别？

**要点：**
- **物理流复制**：传输 **WAL 字节流**——从库是主库的**块级镜像**
  - 优点：完全一致、性能开销小、支持所有 DDL、可做 HA 主库
  - 缺点：**版本必须一致**（大版本升级不可用）、从库只能整体只读（不能改结构）、无法选择性同步
- **逻辑复制**（10+）：**解码 WAL 为逻辑变更**（按表/行的 INSERT/UPDATE/DELETE）传输
  - 优点：**跨版本**（大版本升级利器——逻辑迁移）、**选择性订阅**（部分表）、目标库可写（双向/汇聚）、跨异构（到 Kafka/其他库）
  - 缺点：不复制 DDL（要手工）、大事务内存压力、性能开销大、序列/大对象不复制
- 用途区分：**HA/读扩展用物理**；**版本升级/部分同步/异构分发用逻辑**

**一句话答：** 物理复制传的是 WAL 字节流，从库是主库的块级镜像，一致性最好但版本必须相同，适合做 HA 和读扩展。逻辑复制把 WAL 解码成逻辑变更按表订阅，能跨版本、能选表、目标端还能是异构系统——所以大版本升级靠它。代价是不复制 DDL，加字段两边要手工同步。

### 20. PGSQL 从库复制出错常见原因及解决方法？

**要点：**
- 常见错误场景：
  1. **WAL 缺失**（"requested WAL segment has already been removed"）：主库已回收从库要的 WAL——**配复制槽**预防；补救：重新 basebackup
  2. **主从数据冲突**（逻辑复制：目标已有主键冲突行）——清除冲突数据/跳过事务（逻辑复制槽 advance）
  3. 网络中断：自动重连（正常——看是否频繁）
  4. 磁盘满（从库 WAL 堆积）、权限问题
  5. **参数不匹配**：max_connections/wal_level 主小于从（恢复场景）——热备配置要求主≤从
- 排查路径：日志（ERROR 段）→ pg_stat_replication/`pg_stat_wal_receiver` 状态 → 磁盘/网络检查
- 恢复兜底：**重建从库**（pg_basebackup/pgBackRest）——最干净
- 预防：复制槽+槽监控、参数变更走配置管理、磁盘水位告警

**一句话答：** 最高频的错误是 WAL 已经被主库回收了从库追不上——用复制槽预防，没配槽就只能重建从库。逻辑复制常见的是主键冲突，要么清理数据要么跳过事务。还有一类隐蔽错误是恢复场景下主库的 max_connections 比从库小导致起不来。都搞不定就 pg_basebackup 重建，最干净。

### 21. 简述 Patroni 高可用集群的工作原理？

**要点：**
- Patroni = **Python 编写的 PG 高可用模板**（Zalando 开源）——进程级守护+编排
- 架构三件套：
  - **Patroni 进程**：每节点一个——管理本地 PG 启停/配置/角色
  - **DCS 分布式配置存储**（etcd/Consul/ZooKeeper）：**选主与共识核心**——Leader lease（TTL）持有
  - **PG 流复制**：底层数据同步
- 工作机制：
  1. 各 Patroni 竞争在 DCS 写 **Leader key（带 TTL）**——抢到者引导本节点为主库
  2. 主节点持续续约（heartbeat）；宕机 → TTL 过期 key 消失 → 其他节点竞选
  3. 新主选出前**检查复制位点**（选数据最新的从——防数据丢失，async 模式有 lost 窗口）
  4. Patroni 自动改 PG 配置（恢复/切换时统一配置——避免脑裂参数不一致）
  5. **watchdog**（softdog）：Patroni 假死时内核层自杀——**双主防护核心**
- 接入层：HAProxy 按 Patroni REST API（8008 健康检查）分流读写；VIP（keepalived）
- 优势对比 repmgr：DCS 强一致选主、参数统一管理、watchdog 防脑裂、K8s Operator 生态

**一句话答：** Patroni 的核心是拿 etcd 这类 DCS 做分布式选主：每个节点的 Patroni 抢 Leader key 带租约，主库持续续约，挂了租约过期其他节点竞选——竞选时会检查复制位点挑数据最新的从库。防脑裂两件武器：watchdog 让假死的主库被内核强制自杀，DCS 保证同一时刻只有一个主。接入层用 HAProxy 读 Patroni 的健康检查接口做读写分流。
