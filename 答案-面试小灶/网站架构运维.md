# 网站架构运维 — 面试参考答案

> 覆盖题单：网站运维（29题）、消息中间件（17题）、Nginx（34题）、微服务（12题），共 92 题

## 网站运维面试题

### 1. 简述 HTTP/1.0、1.1、2、3 区别？

**要点：**
- **1.0**：短连接（每请求一个 TCP 连接），无 Host 头
- **1.1**：默认**长连接**（keep-alive 复用连接）、Host 头支持虚拟主机、管道化（pipeline，实践中因队头阻塞少用）、分块传输 chunked
- **2**：**二进制分帧**、**多路复用**（一个连接并发多个流，解决 1.1 的 HTTP 队头阻塞）、头部压缩 HPACK、服务端推送、一个域名一个连接即可
- **3**：底层从 TCP 换 **QUIC（基于 UDP）**，解决 **TCP 层队头阻塞**（2 的多路复用仍受 TCP 丢包阻塞全局）、连接建立更快（0-RTT）、连接迁移（换网络不断线）
- 主线逻辑：1.1 解决连接复用，2 解决应用层并发，3 解决传输层队头阻塞

**一句话答：** 1.0 每个请求都要建 TCP 连接；1.1 默认长连接复用但同一时刻一个连接只能处理一个请求，存在队头阻塞；2 用二进制分帧加多路复用让一个连接并发跑多个请求；3 干脆把底座从 TCP 换成基于 UDP 的 QUIC，连 TCP 层的队头阻塞和握手延迟也一起解决了。

### 2. HTTP 有哪些常见的状态码？

**要点：**
- **2xx 成功**：200 OK、204 No Content
- **3xx 重定向**：301 永久、302 临时、304 Not Modified（协商缓存命中）、307/308（保持方法的重定向）
- **4xx 客户端错**：400 请求语法错、401 未认证、403 拒绝（权限）、404 不存在、413 请求体过大、429 请求过多（限流）
- **5xx 服务端错**：500 内部错误、**502 Bad Gateway**（上游挂了/返回无效）、503 服务不可用、**504 Gateway Timeout**（上游超时）
- 运维重点：301/302/304 缓存语义、502/504 定位到 Nginx 与上游之间

**一句话答：** 按类记：200 成功，301/302 重定向，304 缓存命中，403 权限拒绝，404 不存在，429 被限流，500 应用内部错误，502 是 Nginx 拿不到上游的有效响应——通常后端挂了，504 是上游超时——通常后端太慢。运维排障 502/504 出现频率最高，方向分别是"挂了"和"慢了"。

### 3. 浏览器访问域名经历了哪些流程？

**要点：**
- 完整链路：**URL 解析** → **DNS 解析**（缓存逐级：浏览器→系统→hosts→本地 DNS 递归）→ **TCP 三次握手** → （HTTPS 再加 **TLS 握手**）→ **发送 HTTP 请求** → 服务端处理（CDN/LB/Nginx/应用/DB）→ 返回响应 → 浏览器**解析渲染**（HTML→DOM，CSS→CSSOM，JS 执行，图片加载）→ 连接复用或关闭
- 面试考察点：每一环都可能出问题——DNS 缓存 TTL、握手耗时、TLS 版本、CDN 命中

**一句话答：** 一句话串起：查 DNS 拿 IP，和服务器三次握手，HTTPS 的话再协商 TLS 密钥，然后发 HTTP 请求，请求经过 CDN、负载均衡、网关落到应用，应用查库组装响应原路返回，浏览器解析 HTML 渲染页面。排障时这就是地图：哪一步慢就查哪一层。

### 4. HTTP 请求头和响应头有哪些内容？

**要点：**
- 常见**请求头**：Host（目标主机）、User-Agent、Accept（可接受类型）、Accept-Encoding（gzip/br）、Cookie、Authorization（Bearer token）、Content-Type（application/json）、Content-Length、Referer、If-None-Match/If-Modified-Since（协商缓存）
- 常见**响应头**：Content-Type、Content-Length、Content-Encoding、Cache-Control/Expires（强缓存）、ETag/Last-Modified（协商缓存标识）、Set-Cookie、Server、Location（重定向目标）、X-Request-Id（排障）
- 运维视角：排查缓存看 Cache-Control/ETag，排查跨域看 Access-Control-*，排查压缩看 Content-Encoding

**一句话答：** 请求头记五个高频：Host、Cookie、Authorization、Content-Type、Accept-Encoding；响应头记四个：Content-Type、Cache-Control、ETag、Set-Cookie。运维排障时最有用的是缓存三件套 Cache-Control/ETag/Last-Modified 和跨域的 Access-Control-Allow-Origin。

### 5. 网站显示中文乱码会是什么原因？

**要点：**
- 根源：**编码不一致**——页面声明、文件实际编码、响应头、服务器处理各环节不统一
- 排查链：
  1. 页面 `<meta charset="utf-8">` 与文件实际保存编码是否一致（UTF-8 文件被声明成 GBK）
  2. 响应头 `Content-Type: text/html; charset=xxx` 是否与内容匹配
  3. 应用与数据库编码：MySQL 库/表/连接字符集（utf8mb4）是否统一
  4. 模板引擎/框架输出编码
- 修复原则：全链路统一 UTF-8；已入库的乱码数据要按错误编码路径回转修复

**一句话答：** 乱码就是编码对不上：页面声明的 charset、文件真实编码、响应头、数据库字符集，四个环节任何一个不一致就乱。处理思路是全链路统一成 UTF-8，MySQL 用 utf8mb4，逐层核对声明和实际存储是否一致。

### 6. 网站访问很慢，该如何排查？

**要点：**
- **先定位慢在哪一段**（分层）：
  1. **客户端/网络**：`ping`/`mtr` 延迟丢包、CDN 是否命中（curl -I 看 X-Cache）、DNS 解析耗时（dig time）
  2. **接入层**：Nginx 日志的 $request_time（总耗时）与 $upstream_response_time（上游耗时）对比——差值大=问题在 Nginx/网络，值都大=问题在应用
  3. **应用层**：慢日志、线程池满、GC 停顿、下游依赖超时
  4. **数据层**：慢查询、锁等待、连接池耗尽
- 浏览器侧用 F12 的 Network 瀑布图拆 TTFB/下载/渲染；server_timing 头
- 静态资源慢：缓存策略、压缩、图片大小
- 系统层交叉验证：load/IO/CPU 是否异常（结合 Linux 排查套路）

**一句话答：** 排查关键是分段归因：Nginx 日志里 request_time 和 upstream_response_time 一对比，就能把问题切到"接入层"还是"应用/数据库"；浏览器 F12 看是 TTFB 慢还是资源下载慢；再用 ping、mtr、CDN 命中率排网络因素。应用内部再顺藤摸瓜到慢查询和线程池。切忌一上来就怀疑数据库。

### 7. QPS、TPS、PV、UV 是什么？怎么统计？

**要点：**
- **QPS**：每秒查询/请求数；**TPS**：每秒事务数（一个事务可能含多个请求）；**PV**：页面浏览量（每次加载计一次）；**UV**：独立访客数（按去重的用户/IP/设备）
- 统计：
  - Nginx 日志统计：`awk '{print $1}' access.log | sort -u | wc -l`（UV 近似）、按时间窗 count（QPS）
  - 实时统计：接入层计数（nginx stub_status、prometheus nginx-exporter）、应用埋点、埋点 SDK（PV/UV）
  - 精确 UV：客户端 ID/登录 ID 去重，或 Redis HyperLogLog（近似省内存）
- 关联公式：QPS 峰值 ≈ 日 PV × 80% /（86400×20%）——二八原则估算容量

**一句话答：** QPS 是每秒请求数，TPS 是每秒事务数，PV 是页面访问总量，UV 是去重后的访客数。日志离线统计用 awk 加 sort -u，实时监控靠接入层指标和埋点，大规模 UV 用 Redis 的 HyperLogLog 省内存。容量规划时用日 PV 二八原则估算峰值 QPS。

### 8. 简述 HTTP 和 HTTPS 区别？

**要点：**
- **安全性**：HTTP 明文传输可被窃听/篡改/冒充；HTTPS = HTTP + **TLS**，提供加密（防窃听）、完整性（防篡改）、身份认证（证书防冒充）
- **端口**：HTTP 80，HTTPS 443
- **开销**：HTTPS 多一次 TLS 握手（1-2 RTT，TLS1.3 一次），加解密消耗 CPU（现代硬件可忽略，可配 TLS 硬件加速/会话复用）
- **证书**：HTTPS 需要 CA 签发的证书（付费/免费 Let's Encrypt），到期要续期（运维监控点）
- URL 形态：http:// vs https://

**一句话答：** 区别就三层：HTTPS 在 HTTP 和 TCP 之间加了 TLS，做到加密防窃听、签名防篡改、证书防冒充；端口从 80 变 443；代价是多一次握手和加解密 CPU 开销，以及一张要记得续期的证书。现在默认全站 HTTPS，性能影响已经可以忽略。

### 9. Session 共享是什么？有哪些实现方式？

**要点：**
- 背景：多台应用服务器集群时，用户的 Session 存在单机上，下次请求被 LB 分到另一台就"丢登录态"——需要让所有节点能访问同一份 Session
- 方案：
  1. **Session 粘滞**（ip_hash/cookie 插标）：同一用户固定打到同一台——简单但破坏负载均衡，节点挂了丢会话
  2. **集中存储**：Session 存 **Redis**（Spring Session）/Memcached，各节点读写共享——主流方案
  3. **Session 复制**：节点间同步复制全量 Session（Tomcat cluster）——集群大了广播风暴，少用
  4. **无状态化**：不用 Session，改 **JWT/Token**，服务端不存状态——微服务主流方向

**一句话答：** Session 共享解决的是集群下登录态丢失。四种路子：LB 层做 ip_hash 粘滞最省事但牺牲均衡性；Session 放 Redis 集中存是经典做法；节点间互相复制只适合小集群；终极方案是无状态化——改用 JWT，服务端干脆不存会话，横向扩容彻底自由。

### 10. Tomcat 8005、8009、8080 端口分别作用？

**要点：**
- **8080**：HTTP 连接器（Connector）——对外提供 Web 服务的端口
- **8005**：Shutdown 端口——向它发送字符串 SHUTDOWN（telnet localhost 8005 后输入）可关闭 Tomcat；**安全隐患**：改 Server port="-1" 禁用
- **8009**：AJP 连接器——与前端 Apache HTTPD（mod_jk/mod_proxy_ajp）二进制协议对接；不用 Apache 前端就关掉；**Ghostcat（CVE-2020-1938）文件读取漏洞**就在 AJP
- server.xml 里三个 <Connector>/<Server> 配置对应

**一句话答：** 8080 是对外 HTTP 服务端口，8005 是本机管理端口——telnet 过去发 SHUTDOWN 字符串就能关进程，安全上建议 port 设 -1 禁掉；8009 是 AJP 协议端口，给 Apache 前端用的，现代架构基本不用，留着还有 Ghostcat 漏洞风险，建议关闭。

### 11. Tomcat 如何性能优化？

**要点：**
- **连接器（Connector）调优**：protocol 用 NIO/NIO2（默认）；`maxThreads`（默认 200，按 IO 等待比调）、`acceptCount`（等待队列）、`maxConnections`、`connectionTimeout`
- **JVM 调优**（大头）：堆大小 -Xms=-Xmx 防抖动、垃圾收集器选型（G1/ZGC）、Metaspace 上限、GC 日志
- **应用层**：数据库连接池大小、禁用 DNS 查询（enableLookups=false）、静态资源不经过 Tomcat（交给 Nginx/CDN）
- **架构**：动静分离、Tomcat 集群 + 前端 LB、压测验证（JMeter）
- 依据：先压测拿基线，观察线程池和 GC，逐项调优对比

**一句话答：** 三层下手：连接器开 NIO、按压测结果调 maxThreads 和 acceptCount；JVM 是大头——堆固定大小防抖、换 G1 收集器、开 GC 日志观察停顿；架构上做动静分离，静态资源根本不进 Tomcat。原则依旧是先压测找瓶颈再调，不背参数。

### 12. 简述 LVS 的三种模式及其工作原理？

**要点：**
- **NAT 模式**：Director 改写报文**目标 IP**（DNAT）转给 RealServer，RS 回包必须经过 Director（SNAT 回去）→ Director 是流量进出瓶颈；RS 可以是任意 OS；支持端口映射
- **DR 模式**（Direct Routing，最常用）：Director 只改**MAC 帧**（不改 IP）把请求丢给 RS，**RS 直接回包给客户端**（回包不过 Director）→ 性能最好；要求 Director 与 RS **同二层网段**，RS 上配 VIP 到 lo 并抑制 ARP（arp_ignore/arp_announce）
- **TUN 模式**：IP 隧道封装，Director 把报文套 IP 隧道发 RS，RS 解封装后直接回客户端 → RS 可跨机房/广域网；RS 需支持隧道协议
- 选型：常规高并发用 DR，跨网段用 TUN，需要端口映射/简单场景用 NAT

**一句话答：** 三种模式的本质区别是"回包走不走 LVS"：NAT 模式改目标 IP，进出都过 Director，最容易成瓶颈；DR 模式只改 MAC 地址，请求经 Director、响应直连客户端，性能最高但要求同网段，是生产默认选择；TUN 模式用 IP 隧道封装，RealServer 可以跨机房，适合广域网部署。DR 模式细节考点是 RS 要把 VIP 绑在 lo 上并抑制 ARP 响应。

### 13. LVS 支持哪些调度算法？

**要点：**
- 静态（不看连接状态）：**rr** 轮询、**wrr** 加权轮询、**dh** 目标地址哈希（会话保持到缓存）、**sh** 源地址哈希（同一来源固定同一 RS）
- 动态（看实时连接数）：**lc** 最少连接、**wlc** 加权最少连接（**默认**）、lblc/lblcr（基于局部性，缓存场景）、sed/nq
- 运维常配：无差别性能配 wrr，长连接/性能差异大配 wlc，需要来源会话保持配 sh

**一句话答：** 分静态动态两族：静态的 rr 轮询和 wrr 加权轮询，sh 源地址哈希做会话保持；动态的 lc/wlc 按实时连接数调度，wlc 是默认算法——考虑了机器权重和当前负载。面试说得出 wrr、sh、wlc 三个名字加各自场景就够了。

### 14. 简述 HTTP Cookie 和 Session 区别和联系？

**要点：**
- **Cookie**：存在**客户端**（浏览器），随每次请求自动携带，大小约 4KB、数量有限，可设过期；可被用户查看/篡改（敏感数据不能裸放，要签名/加密）
- **Session**：存在**服务端**，通过 Cookie 里的 **SessionID** 关联用户；容量不受限；分布式环境需要 Session 共享（第 9 题）；有生命周期（超时）
- 联系：Session 通常依赖 Cookie 传递 SessionID（Cookie 被禁可用 URL 重写兜底）
- 安全：Session 固定攻击、Cookie 的 HttpOnly/Secure/SameSite 属性

**一句话答：** Cookie 存在浏览器、每次请求自动带上；Session 存在服务器，靠 Cookie 里的 SessionID 认人。所以它们的联系是 Session 通常寄生在 Cookie 上。运维注意两点：Cookie 设 HttpOnly 和 Secure 防偷防传，集群下 Session 要么共享要么无状态化。

### 15. 网站跨域报错 Access-Control-Allow-Origin 怎么解决？

**要点：**
- 同源定义：协议+域名+端口任一不同即跨域；浏览器同源策略拦截的是 **JS 发起的响应读取**（CORS），不是请求本身
- 解决：
  1. **服务端/网关加 CORS 响应头**：`Access-Control-Allow-Origin: https://a.com`（带凭证时不能是 *）、`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers`、`Access-Control-Allow-Credentials: true`
  2. Nginx 统一加：`add_header Access-Control-Allow-Origin $http_origin always;` + OPTIONS 预检直接 204
  3. 同域化：反向代理把 API 挂到主域路径下（/api → 后端），从根上消除跨域
  4. 开发期：前端 devServer proxy
- 注意预检请求（OPTIONS）必须正确响应，否则 POST/JSON 请求直接挂

**一句话答：** 跨域是浏览器同源策略拦了响应读取，解法三层：后端或 Nginx 加 Access-Control-Allow-Origin 等响应头，注意带 cookie 时 Origin 不能写星号且要回显具体来源，OPTIONS 预检请求要正确返回；更省心的架构办法是 Nginx 反代把 API 同域化，跨域问题直接消失。

### 16. 简述 CDN 工作原理？

**要点：**
- 本质：**内容分发网络**——把静态资源复制到离用户最近的边缘节点，就近服务
- 核心机制：域名 CNAME 到 CDN 的智能调度 DNS → 按用户位置/网络运营商/节点负载返回**最近边缘节点 IP** → 边缘节点有缓存直接返回（HIT），没有则**回源**拉取并缓存（MISS）
- 缓存控制：源站通过 **Cache-Control/Expires** 告诉 CDN 缓存多久；URL 刷新（purge）主动失效、预热主动拉取
- 类型：静态加速、动态加速（路由优化）、下载/视频大文件分发
- 收益：降低源站压力、降低延迟、抗流量峰值/DDoS

**一句话答：** CDN 干两件事：智能调度——CNAME 加调度 DNS 把用户指到最近的边缘节点；边缘缓存——命中直接回，没命中回源拉并缓存。源站用 Cache-Control 控制缓存时长，配合刷新和预热 API 管内容更新。对源站的直接收益是流量被边缘吃掉、压力和延迟双降。

### 17. 四层与七层负载均衡有什么区别？

**要点：**
- **四层**（传输层）：基于 **IP+端口**转发，不解析应用协议——报文拿到就转；代表 **LVS**、F5、云 SLB 四层实例；性能高（不碰 payload）、能转发任意 TCP/UDP
- **七层**（应用层）：解析 **HTTP 协议**（URL/Header/Cookie），可按内容路由、改写、压缩、缓存、限流；代表 Nginx/HAProxy（mode http）、网关；灵活但开销大
- 架构组合：四层在前扛量（LVS），七层在后做策略（Nginx）——经典 LVS+Nginx 两级 LB
- 会话保持差异：四层靠源地址哈希，七层可按 Cookie 插入

**一句话答：** 四层只看 IP 和端口，报文不拆开直接转发，LVS 是代表，扛得住海量连接；七层要解析 HTTP 内容，能按 URL、Header 做路由、缓存和限流，Nginx 是代表，灵活但单机性能低一层。大型架构是两层叠加：前面 LVS 扛量，后面 Nginx 做内容策略。

### 18. 网站报错 502 Bad Gateway 怎么解决?

**要点：**
- 502 = Nginx/网关**从上游收到无效响应或连接失败**——"上游挂了或不正经说话"
- 排查链：
  1. Nginx error.log 看具体错误：`connect() failed`（上游没监听/防火墙）、`Connection refused`（进程挂）、`recv() failed`（上游异常断开）
  2. 上游进程活着吗：`ss -tlnp | grep 端口`、进程状态
  3. 上游是否过载崩掉：OOM（dmesg）、php-fpm 进程数满、应用线程池满
  4. 超时配置不匹配：proxy_read_timeout 太短，上游处理慢被掐
- 处理：恢复上游进程 → 调整超时与上游容量 → 加上游健康检查自动摘除坏节点

**一句话答：** 502 是网关到上游的连接出了问题。先看 Nginx error.log 里的具体报错，十有八九是上游进程挂了或没监听——connect refused 查进程，timeout 查上游是不是过载。解决路径：拉起上游、匹配超时参数、加健康检查把坏节点自动摘掉。

### 19. 网站 QPS 突降，如何快速定位问题？

**要点：**
- 突降说明"流量进不来或请求处理不了"，分段查：
  1. **入口流量还在吗**：LB/CDN 带宽和请求数曲线——入口就掉了查 DNS/CDN/带宽/线路/运营商
  2. **接入层**：Nginx 连接数、限流配置（limit_req 误伤）、证书过期、worker 被打满
  3. **应用层**：线程池满、Full GC 频繁、下游依赖超时拖垮（数据库/Redis/第三方）
  4. **依赖故障**：DB 慢查询激增、Redis 挂、MQ 堆积——链路上谁病了谁拖累全局
- 工具支撑：全链路监控（Grafana 分层曲线对比）、日志错误率突变、变更记录核对（**最近有没有发版/变更**——第一嫌疑）
- 止血优先：先回滚变更/切换流量，再慢慢查

**一句话答：** 先看流量断在哪一层的曲线：入口掉了查 DNS 和线路，接入层掉了查 Nginx 和证书，应用层掉了查线程池、GC 和下游依赖。同时第一反应核对最近变更——QPS 突降八成和最近的发布或配置变更有关系，能回滚先回滚止血，再慢慢查根因。

### 20. 简述 HTTPS 工作原理？

**要点：**
- 组合拳：**非对称加密交换密钥 + 对称加密传数据**
- TLS 1.2 握手流程：
  1. ClientHello：客户端发随机数+支持的套件
  2. ServerHello + **证书**：服务端回随机数、选定算法、出示证书（含公钥）
  3. 客户端验证证书（CA 链、域名、有效期、吊销状态）→ 生成**预主密钥**用公钥加密发给服务端
  4. 双方用三个随机数算出**会话密钥**，之后数据用对称加密（AES 等）传输
- **TLS 1.3**：一次 RTT 完成（0-RTT 恢复），删弱算法，握手更快
- 证书验证三要素：CA 签名链、域名匹配、有效期/吊销
- 补充：ECDHE 套件提供前向安全

**一句话答：** HTTPS 的核心是非对称和对称加密的组合：握手阶段用证书里的公钥安全地交换出对称会话密钥，数据传输用对称加密保证性能；证书由 CA 签发，客户端验证签名链、域名和有效期来确认"对方真是它声称的网站"。TLS1.3 把握手压缩到一次往返，安全算法还更精简。

### 21. 如何设计高可用的 Web 服务架构？

**要点：**
- **消除单点**（每一层都要冗余）：DNS 多记录/智能解析 → CDN → LVS+Keepalived VIP → Nginx 集群 → 应用集群（无状态）→ 缓存集群（Redis 哨兵/Cluster）→ 数据库（主从+自动切换/MGR）
- **故障转移**：健康检查+自动摘除/切换；切换要演练
- **降级与限流**：非核心功能可降级（关闭推荐/评论），入口限流保护核心链路，熔断防雪崩
- **数据可靠性**：备份+恢复演练、多可用区部署
- **预案与演练**：故障预案文档化、混沌工程定期验证高可用真的"高"
- 量化：SLA 目标（99.95% = 全年约 4.4 小时不可用）倒推冗余度

**一句话答：** 高可用的本质是消除单点加预案兜底：从 DNS、LB、应用到数据库每一层至少双节点，靠健康检查自动切换；非核心链路可降级，入口限流防过载雪崩，数据有备份有演练。最后强调演练——没有真实演练过的 HA 方案，故障来了才知道是纸糊的。

### 22. 秒杀系统，怎么优化?

**要点：**
- 核心矛盾：瞬时超高 QPS × 有限库存 × 不超卖
- **层层削峰**：
  1. 前端：按钮防重复提交、静态资源 CDN、答题/验证码拉平请求
  2. 网关：限流（令牌桶）、黑名单、防刷（风控）
  3. **预热进 Redis**：库存放 Redis，**原子扣减**（DECR/Lua 脚本）挡住绝大多数请求，扣到 0 直接拒绝
  4. **异步下单**：扣减成功进 MQ，后端慢速消费落库——数据库只承受 MQ 的平稳流量
  5. 库存兜底：数据库层 `UPDATE ... WHERE stock > 0` 保证不超卖
- 其他：热点数据隔离（独立集群/独立库）、降级预案、防黄牛（设备指纹/风控）

**一句话答：** 思路是层层漏斗削峰：前端和网关先挡掉大部分无效请求，库存预热到 Redis 用原子扣减做第一道闸，扣成功的进 MQ 异步下单，数据库只吃平稳流量并用条件更新兜底防超卖。一句话总结：让数据库永远不见洪峰，洪峰在到达它之前就被消化掉。

### 23. 在高并发情况下，如何避免数据库的性能问题？

**要点：**
- **让数据库少干活**：缓存前置（Redis 挡读）、静态化、读写分离（读走从库）
- **让数据库干得快**：索引优化（覆盖索引、防失效）、SQL 优化（慢查询治理）、分库分表（水平拆分）应对数据量
- **让数据库慢慢干**：写削峰（MQ 异步、批量写）、连接池合理配置（防连接风暴）
- **保护数据库**：限流熔断、超时快速失败、防大事务/长事务、备份与只读副本隔离报表查询
- 监控：慢查询日志、连接数、锁等待、buffer pool 命中率

**一句话答：** 围绕"少、快、稳"三个字：少——热数据进缓存、读写分离，让数据库只处理必须的请求；快——索引和 SQL 优化，数据量太大就分库分表；稳——写操作走 MQ 削峰、连接池控制并发、限流熔断保护，绝不让洪峰直接砸到数据库。

### 24. 如何设计高并发的 Web 服务架构？

**要点：**
- **扩容三方向**：
  1. **垂直扩展**：升配（有上限，先不做）
  2. **水平扩展**：无状态应用集群、LB 分发——主力
  3. **分层优化**：每层减少到达下一层的流量
- 分层手段：CDN 静态分流 → 多级缓存（本地缓存+Redis）→ 应用无状态横向扩 → 异步化（MQ 削峰）→ 数据库读写分离/分库分表
- 配套：连接池与线程池调优、限流熔断降级、全链路压测验证容量、弹性伸缩
- 度量指标：QPS、RT P99、错误率（黄金三指标）

**一句话答：** 高并发设计就是流量层层递减的漏斗：CDN 和缓存把读流量挡在外面，应用无状态化随便水平扩，高峰写流量进 MQ 异步消化，数据库读写分离加分库分表做最后保障。能力上限要靠全链路压测说话，运行中靠限流熔断守住底线。

### 25. 网站会监控哪些指标？

**要点：**
- **资源层**（USE 方法）：CPU、内存、磁盘 IO 与水位、网络带宽、连接数
- **服务层**：QPS、RT（P95/P99）、错误率（4xx/5xx 比例）——RED 方法；进程存活、端口监听
- **中间件层**：MySQL（慢查询、连接数、主从延迟）、Redis（命中率、内存）、MQ（堆积量）
- **业务层**：订单量、支付成功率、登录量——业务指标是最灵敏的"用户视角"探针
- **体验层**：页面 TTFB/白屏时间、CDN 命中率（真实用户监控 RUM）
- 告警原则：按 SLI/SLO 定阈值，分级通知

**一句话答：** 四层监控体系：资源层的 CPU 内存磁盘网络，服务层的 QPS、P99 延迟和错误率——这三个是黄金指标，中间件层的连接数、命中率、堆积量，最上层是业务指标比如订单量和支付成功率。业务指标最能代表用户真实感受，跳票了再漂亮的资源曲线都没意义。

### 26. 请介绍下你之前维护的网站整体架构？

**要点：**（面试话术模板，按真实经历替换）
- 讲述框架（从外到内）：**流量入口**（DNS/CDN/域名数量级）→ **接入层**（LB 类型、SSL 卸载）→ **应用层**（技术栈、集群规模、发布方式）→ **数据层**（DB 类型、主从、缓存）→ **配套**（监控、日志、CI/CD、备份）

### 27. HTTP 长连接和短连接有什么区别及适用场景？

**要点：**
- **短连接**：每次请求建一次 TCP（三次握手）→ 传输完断开；开销大（握手+慢启动+TIME_WAIT），实现简单
- **长连接**（HTTP/1.1 默认 keep-alive）：一条 TCP 复用多次请求，Connection: keep-alive；减少握手延迟、避免 TIME_WAIT 风暴；占用服务端连接资源（要设合理 keepalive_timeout 防连接堆积）
- 适用：短连接——低频访问、爬虫容忍；长连接——**网站页面多资源、API 高频调用、反代到上游（upstream keepalive）**；实时推送用 WebSocket（另一维度的长连接）

**一句话答：** 区别就是 TCP 连接要不要复用：短连接每次请求都重新握手，开销大但管理简单；长连接复用连接省握手还避免 TIME_WAIT 堆积。现代 Web 默认长连接，注意服务端要配 keepalive_timeout 和连接数上限防止闲置连接堆积，反代到后端更要开 upstream keepalive。

### 28. HTTPS 中 CA 证书在客户端还是在服务端？

**要点：**
- **证书在服务端**：握手时服务端把证书（含公钥、域名、CA 签名）发给客户端验证
- **客户端存的是 CA 根证书**（信任锚）：操作系统/浏览器内置受信任 CA 列表，用根证书的公钥验证服务端证书链
- 所以更准确：服务端持有**自己的证书+私钥**，客户端持有 **CA 根证书**（预装）
- 双向 TLS（mTLS）：客户端也出证书（如服务间调用、支付回调），证书在两边

**一句话答：** 站点证书在服务端，握手时下发；客户端内置的是 CA 根证书，用来验证服务端证书的签名链。一句话：证书跟身份走——服务端证明自己是谁，客户端负责验。特殊场景如 mTLS 双向认证时客户端也要装自己的证书。

### 29. 打开 APP 后页面空白，怎么排查问题？

**要点：**
- 分端定位：
  1. **客户端**：版本兼容（新 APP 配旧接口）、本地缓存损坏（清缓存重装对比）、DNS/代理问题
  2. **网络**：弱网/超时、DNS 劫持、运营商问题——抓包看请求是否发出/返回
  3. **服务端**：接口返回什么——curl 直接打接口、看 5xx/空响应/慢响应；网关 502/504；证书过期（APP 内嵌 H5 常见）
  4. **数据**：接口 200 但返回空数据——下游服务/数据库异常、配置发布错误
- 工具链：APM（全链路追踪 traceID）、服务端日志时间点对齐、灰度范围核对（是否新版本特定人群问题）
- 止血思路：回滚最近发布、切流、降级静态兜底页

**一句话答：** 先分辨是"请求没发出去"还是"服务端没回好"：客户端抓包看请求和响应，服务端 curl 直接打接口验证，再看日志和 APM 链路定位到具体环节。空白页高频根因是接口报错、证书过期、下游数据为空和版本兼容——先核对最近发布，能回滚先止血。

## 消息中间件面试题

### 1. 消息中间件有哪些应用场景？

**要点：**
- **异步**：主流程外的耗时操作（发短信、发券、记日志）扔给 MQ，接口 RT 直降
- **解耦**：生产者不关心谁消费——订单系统发消息，库存/积分/物流各自订阅，新增系统不动老代码
- **削峰填谷**：洪峰写入 MQ，消费端按自己的节奏处理，保护下游（数据库）
- 其他：广播通知、延迟消息（订单超时关单）、数据管道（日志流进 Kafka→Flink）
- 代价：系统复杂度上升、最终一致性（不再是强一致）、要处理消息丢失/重复/堆积

**一句话答：** 三大经典场景：异步——把发短信这种耗时操作从主流程剥离；解耦——订单系统只管发消息，下游谁要谁订阅；削峰——洪峰先入队，消费端匀速处理保护数据库。代价是要接受最终一致性和额外运维一套中间件。

### 2. 你用过哪些消息中间件？简单介绍下各自适用场景

**要点：**
- **Kafka**：超高吞吐（百万级）、分布式分区、日志/埋点流式管道首选，生态（Flink/Spark 对接）最强；不适合复杂路由和延迟消息
- **RocketMQ**：阿里系，金融级事务消息、延迟消息、顺序消息功能全，Java 技术栈电商常用
- **RabbitMQ**：Erlang，路由模型灵活（exchange 类型丰富），管理界面友好，万级吞吐适合业务系统间通信；Erlang 二开难度大
- **Redis（list/stream）**：轻量简单场景/已依赖 Redis 时顺手用，可靠性弱于专用 MQ
- 选型一句话：日志流选 Kafka，业务解耦加高级特性选 RocketMQ，中小规模灵活路由选 RabbitMQ

**一句话答：** 我按场景分：要吞吐量——日志和埋点管道用 Kafka，百万级 QPS 没对手；要功能——事务消息、延迟消息、顺序消息用 RocketMQ；要灵活路由和好上手——RabbitMQ 的 exchange 模型最丰富；已有 Redis 的轻量异步需求直接用 Redis Stream，别为小场景多养一套中间件。

### 3. Kafka 核心组件有哪些？

**要点：**
- **Producer**：生产者，按 key 或轮询把消息发到 partition
- **Broker**：服务节点，组成集群；由 **Controller**（从 broker 中选出）负责分区 leader 选举和集群管理（新版用 KRaft 模式替代 ZooKeeper）
- **Topic**：逻辑消息主题；**Partition**：topic 的物理分片（并行度单位）；**Replica**：每个 partition 的副本（1 leader + N follower），leader 读写、follower 同步
- **Consumer / Consumer Group**：消费者组内**分摊 partition**（一个分区同一时刻只被组内一个消费者消费），组间广播
- **ZooKeeper/KRaft**：元数据与协调（新版本 KRaft 内置）
- 存储细节：消息按 **offset** 追加进 segment 日志文件

**一句话答：** 记住四级结构：Topic 是逻辑主题，Partition 是物理分片也是并行度单位，每个分区有 leader 和 follower 副本分布在多个 broker 上，生产者按 key 写分区，消费者组内瓜分分区消费。协调层老版本靠 ZooKeeper，新版本 KRaft 已内置。

### 4. Kafka 中 Topic、Partition、Replica 三者之间的关系是什么？

**要点：**
- 层级：**一个 Topic 包含 N 个 Partition**（水平拆分、并行单位）；**每个 Partition 有 N 个 Replica**（1 leader + N-1 follower，冗余单位）
- 分区规则：producer 按 key hash 或轮询选 partition；同 key 消息进同分区（**分区内有序**）
- 副本分布：不同副本**必须分属不同 broker**（容灾）；leader 所在 broker 处理读写，follower 只同步不服务读（Kafka 特性）
- 数量经验：分区数≈目标并行度（消费者数上限=分区数），副本数通常 3（容忍 1-2 台 broker 故障）

**一句话答：** Topic 是逻辑容器，往下切成多个 Partition 提供并行度，每个 Partition 又复制多个 Replica 保容错——每个分区一个 leader 负责读写，follower 只做同步且必须落在不同 broker 上。运维记两条：分区数决定最大消费并行度，副本数决定容错能力，生产默认 3 副本。

### 5. Kafka 为什么能够支持高吞吐量和高并发？

**要点：**
- **顺序写**：消息追加到分区日志文件末尾，磁盘顺序写速度接近内存（对比随机写差百倍）
- **页缓存**：读写都走 OS page cache，不依赖 JVM 堆，减少 GC 压力
- **零拷贝**：sendfile 系统调用，数据从页缓存直接到网卡，不过用户态
- **批量与压缩**：生产者攒批发送（batch.size/linger.ms），批量压缩（gzip/lz4/zstd）省网络
- **分区并行**：多分区多消费者横向扩展，吞吐随分区/机器数近似线性增长
- 稀疏索引：segment 按 offset 索引定位快

**一句话答：** 核心是四件套：消息顺序追加写磁盘——顺序 IO 接近内存速度；读写字全走操作系统页缓存加零拷贝，数据不进用户态；生产端批量加压缩摊薄网络开销；分区结构让吞吐随机器数线性扩展。这些设计共同把"磁盘消息系统"做到了内存级的速度。

### 6. Kafka 的消息存储机制是怎样的？

**要点：**
- 每个分区对应一个目录，消息**顺序追加**写入 segment 文件（默认 1GB 或按时间滚动）
- 文件组织：`xxx.log`（消息数据）+ `xxx.index`（offset→物理位置稀疏索引）+ `xxx.timeindex`（时间索引）——按 offset 查找：二分定位 segment，再走 index 定位
- 消息批量存储、压缩格式可配置（producer 压缩、broker 原样存）
- **保留策略**：按时间（默认 7 天）或按大小删除旧 segment，与消费进度无关（消费靠 offset，删了就是收不到）
- 读取：consumer 拉取（pull）指定 offset，broker 从 log+index 快速定位

**一句话答：** 每个分区是一串顺序追加的 segment 日志文件，配稀疏索引按 offset 二分定位，写入永远是文件尾部追加所以极快。保留策略按时间或大小滚动删除整个 segment，和消费者是否读完无关——Kafka 只管存，消费者自己记 offset。

### 7. Kafka 如何保证消息不丢失？

**要点：**
- 消息链路三环节，全链路加固：
  1. **生产端**：`acks=all`（所有 ISR 副本确认才算成功）+ `retries=INT_MAX` + 发送失败回调处理/本地重试；不要发后即忘
  2. **Broker 端**：`replication.factor>=3`、`min.insync.replicas>=2`（至少 2 副本同步才算写入成功）、禁止 unclean leader 选举（`unclean.leader.election.enable=false`）
  3. **消费端**：**先处理完业务再手动提交 offset**（关闭自动提交 enable.auto.commit=false）——处理与提交的原子性方向
- 代价：ack=all + min.insync.replicas=2 牺牲部分吞吐与延迟——按业务重要性分级配置
- 补充：真正的兜底是业务侧对账/重试队列

**一句话答：** 分三段背：生产端 acks=all 加重试，不确认成功不罢休；broker 端 3 副本加 min.insync.replicas=2，同步副本不够就拒绝写入，禁掉 unclean 选举防丢数据；消费端关自动提交，处理完业务再提交 offset。这三条同时满足才能说不丢，代价是吞吐下降——按业务分级取舍。

### 8. Kafka ACK 机制有哪三种取值？分别什么特点？

**要点：**
- `acks=0`：发出去就算成功，不等确认——最快，**可能丢**（网络抖动即丢）
- `acks=1`：**leader** 写入本地日志即确认——折中；leader 落盘后、follower 同步前宕机且发生选举 → 丢
- `acks=all`（-1）：**ISR 里所有副本**都写入才确认——最可靠；配合 `min.insync.replicas>=2` 防"ISR 只剩 leader 自己"的假安全
- 运维建议：日志类可 0/1，交易类必须 all

**一句话答：** acks=0 只管发不等回，最快但可能丢；acks=1 主副本落盘就确认，leader 挂掉瞬间可能丢；acks=all 等所有同步副本确认，最可靠——但必须配 min.insync.replicas=2，否则 ISR 缩水到只剩 leader 时 all 退化成 1。生产消息类业务用 all，纯日志可放宽。

### 9. Kafka 消息堆积，如何排查和解决？

**要点：**
- **先量化**：`kafka-consumer-groups.sh --describe --group xxx` 看 LAG（未消费数）、消费速率
- **定位根因**（消费能力 < 生产能力，或消费停摆）：
  1. 消费者挂了/重平衡风暴（频繁 rebalance 日志）
  2. 单条消息处理慢（下游 DB/接口阻塞）→ 消费线程打不出吞吐
  3. 消费并行度不足：消费者实例数 < 分区数，加机器就提吞吐
  4. 毒消息（poison message）卡死某分区——反复失败重试
- **解决**：
  - 短期：加消费者实例（≤分区数）、提高单条处理并发、跳过毒消息（记死信队列）
  - 长期：处理逻辑异步化/批量化、下游扩容、消费限流保护、监控 LAG 告警前置

**一句话答：** 先看 consumer group 的 LAG 和速率确认堆积规模，再找原因：消费者挂了、rebalance 风暴、单条处理太慢还是并行度不够。短期手段是加消费者实例到分区数上限、批量化处理、毒消息进死信队列；长期要治下游依赖的吞吐，并把 LAG 告警阈值前置到堆积成灾之前。

### 10. Kafka 中 Leader 选举流程是怎么样的？

**要点：**
- 区分两个"选举"：
  1. **分区 Leader 选举**（broker 内，常态）：controller（老版经由 ZooKeeper，新版 KRaft）从分区的 **ISR** 列表选新 leader——优先选 ISR 中存活且数据最新的副本；ISR 全挂且开启 unclean 选举才会从非同步副本选（**会丢数据**，生产关闭）
  2. **Controller 选举**（集群级）：老版靠 ZooKeeper 临时节点抢占；KRaft 模式由 raft 元数据仲裁（quorum）选出
- 相关参数：`unclean.leader.election.enable=false`、副本 placed 尽量跨机架
- 运维关注：broker 宕机后 leader 迁移产生的瞬时抖动、preferred leader 平衡（`auto.leader.rebalance.enable=true`）

**一句话答：** 分区 leader 选举由 controller 从 ISR 里挑存活且最新的副本，优先保证数据不丢；ISR 全军覆没时如果开了 unclean 选举会从落后副本选——能自动恢复但丢数据，生产必须关。controller 本身老版本走 ZooKeeper 抢占，新版本 KRaft 集群自己选。

### 11. Kafka 中 ISR 有什么作用？

**要点：**
- ISR（In-Sync Replicas）= 与 leader **保持同步**的副本集合（含 leader 自己）
- 判定：follower 落后 leader 超过 `replica.lag.time.max.ms`（默认 30s）被踢出 ISR；追上后自动加回
- 作用：
  - **数据安全边界**：acks=all 只需 ISR 内确认（不是全部副本）——性能与安全的平衡点；min.insync.replicas 保证 ISR 最小规模
  - **选举范围**：新 leader 只从 ISR 中产生（保证不丢已确认消息）
- ISR 收缩的运维含义：某台 broker 磁盘/网络慢 → follower 反复进出 ISR → 抖动告警要看 replica.lag 指标

**一句话答：** ISR 是"跟得上 leader 的副本名单"，落后的 follower 超时会被临时踢出、追上再加回。它是 Kafka 可靠性的基石：acks=all 只等 ISR 确认、新 leader 只能从 ISR 选——所以 min.insync.replicas 设 2 才有意义，ISR 缩到 1 时 all 形同虚设。

### 12. Kafka Rebalance 是什么？哪些场景会触发？

**要点：**
- Rebalance = 消费者组**重新分配分区**的过程：成员变化时把 partition 重新指派给存活消费者
- 触发场景三类：
  1. **成员变化**：消费者加入（扩容/重启）、离开（宕机、处理超时被踢——`max.poll.interval.ms`）
  2. **订阅的 topic 数变化**（新增 topic/分区）
  3. 订阅正则匹配到的 topic 变化
- 危害：rebalance 期间**全组停止消费**（STW）→ 堆积；频繁 rebalance 常见于长事务处理超时
- 优化：`session.timeout.ms`/`heartbeat.interval.ms` 合理、`max.poll.interval.ms` 大于最长单批处理时间、用**静态成员资格**（group.instance.id，重启不触发）、CooperativeStickyAssignor 增量 rebalance

**一句话答：** Rebalance 是消费组重新瓜分分区，触发条件就三个：消费者进出了、订阅的 topic 变了、分区数变了。它的坑在于期间整个组停止消费，长事务处理超时被踢会导致 rebalance 风暴。治理手段：调大 max.poll.interval.ms、开静态成员资格让重启不触发、用增量式分配器减少 STW 范围。

### 13. RabbitMQ 集群方案有哪些？

**要点：**
- **普通集群**：元数据（exchange/queue 定义）全节点共享，但**消息实体只存在创建它的节点**——其他节点收到请求要跨节点拉取；节点挂了其上消息不可用（未镜像）→ 只提高可用性路由，不做容灾
- **镜像队列集群**（classic mirrored）：queue 在节点间**主从复制**，master 挂自动切——高可用经典方案；但性能损耗大，**3.9 起标记废弃**
- **仲裁队列**（Quorum Queue，3.8+）：基于 **Raft** 的复制队列，官方主推替代镜像队列，强一致自动选主
- 节点类型：disc（磁盘节点，存元数据，至少 1 个）/RAM 节点；配合 HAProxy/LB 做接入

**一句话答：** 三代方案演进：普通集群只共享元数据不复制消息，节点挂了消息就没了；镜像队列主从复制保高可用但性能损耗大已被官方废弃；现在主推仲裁队列——基于 Raft 的多数派复制，一致性和自动选主都更强。集群接入前面加 LB 分发连接。

### 14. 简述 RabbitMQ 仲裁队列架构？

**要点：**
- 基于 **Raft 共识算法**：每个仲裁队列是一个 Raft 组，队列副本分布在多个节点上（replication factor 通常 3 或 5）
- 读写流程：所有写入必须经 **leader**，复制到**多数派** follower 才确认（强一致）；leader 宕机，多数派存活即自动选新 leader（秒级）
- 对比镜像队列：明确的一致性语义（宁可拒绝写入也不丢数据）、失败恢复更可预测、无镜像队列的"边界情况"
- 代价：延迟高于普通队列（要等多数派确认）、不适合超低延迟场景；声明队列时指定 `x-queue-type: quorum`
- 建议：3 副本容忍 1 节点故障，5 副本容忍 2 个

**一句话答：** 仲裁队列就是 RabbitMQ 里的 Raft 实现：队列副本组成多数派组，写必须 leader 落地并复制到过半节点才算成功，leader 挂了秒级自动切换，绝不丢已确认消息。代价是延迟比普通队列高——所以它取代镜像队列成为高可用首选，但超高性能场景还要权衡。

### 15. RabbitMQ 消息堆积，如何排查和解决？

**要点：**
- **看管理界面/API**：queue 的 messages 数量、consumers 数（**consumers=0 是红灯**——消费者全挂了）、unacked 数、消费速率曲线
- **根因方向**：
  1. 消费者宕机/连接断（heartbeat 超时）
  2. prefetch 设置过低（吞吐上不去）或过高（内存爆/超时重投）
  3. 单条消息处理慢（下游阻塞）、毒消息反复 nack 重入队死循环
  4. 生产激增（大促/事故流量）
- **解决**：
  - 短期：扩消费者实例（水平加）、临时高 prefetch 批量消费、毒消息移出（设死信/跳过）
  - 兜底方案：队列消息**转移**（ shovel 插件搬到备用队列慢慢消化）
  - 长期：消费异步化、限流生产端、堆积告警、死信队列规范化

**一句话答：** 管理台先看两件事：队列里堆积多少、consumers 是不是 0——消费者全挂是最常见的突发堆积。有消费者但消化不动就查 prefetch 和单条处理耗时、有没有毒消息死循环。短期扩消费者或用 shovel 把消息搬去备用队列慢慢消化，长期治理靠堆积告警加死信队列。

### 16. RocketMQ 集群方案有哪些？

**要点：**
- 角色先分清：**NameServer**（无状态注册中心，轻量）+ **Broker**（存储与转发）+ Producer/Consumer
- Broker 部署形态：
  1. **单 Master**：风险自担，测试用
  2. **多 Master**：无副本，性能最高，单机挂丢数据（文件刷盘策略决定）
  3. **多 Master 多 Slave（异步复制）**：主写、从异步复制——主挂可读不可写，可能丢少量消息
  4. **多 Master 多 Slave（同步双写）**：主从都落盘才确认——不丢消息，延迟略增
  5. **DLedger（Raft）集群**：多副本 Raft 自动选主——4.5+ 主推，自动容灾
- NameServer 多节点互不通信（无状态），客户端轮询连

**一句话答：** RocketMQ 从弱到强五种部署：单 Master 测试用、多 Master 极致性能但有丢数据风险、异步复制主从折中、同步双写不丢但慢、DLedger 基于 Raft 自动选主是现在的标配方案。NameServer 是无状态的，随便多节点。

### 17. 简述多主多从 + DLedger 集群架构工作流程？

**要点：**
- DLedger = RocketMQ 基于 **Raft** 的副本组：一组 broker 内自动选 leader（主），其余为 follower（从）
- **写流程**：producer 找到组内 leader → leader 写本地日志并**并行复制给 follower** → **过半**（含 leader）落盘即向 producer 确认 → 保证已确认消息在多数派存活
- **读流程**：consumer 从 leader 读（保证已提交数据可见）
- **故障切换**：leader 宕机 → follower 心跳超时 → 任期+1 发起投票 → 多数派同意选出新 leader（秒级自动，**无需人工介入**——对比传统主从切换要运维动手或依赖外部组件）
- 传统"多主多从"由 broker 主从关系静态配置，DLedger 把主从关系动态化、选举自动化——这就是它取代前者的原因
- 客户端无感知：NameServer 路由刷新后指向新 leader

**一句话答：** DLedger 把传统静态主从升级成 Raft 动态选举：写入走组内 leader，消息复制到过半节点才对生产者确认，天然不丢；leader 宕机后存活 follower 秒级投票选出新主，客户端经 NameServer 路由刷新自动切过去，全程无人值守。这正是它比"多主多从+人工切换"先进的地方。

## Nginx Web面试题

### 1. Nginx 有哪些应用场景？

**要点：**
- **反向代理/负载均衡**：七层（http upstream）与四层（stream）分发，健康检查
- **静态资源服务器**：图片/CSS/JS 直出，gzip、缓存头
- **API 网关/接入层**：SSL 卸载、限流、黑白名单、鉴权转发
- **缓存**：proxy_cache 缓存后端响应
- 其他：灰度分流、URL 重写、动静分离、带 Lua（OpenResty）做自定义逻辑

**一句话答：** Nginx 五大角色：反向代理和负载均衡、静态资源服务、接入层网关做 SSL 卸载和限流、响应缓存、配合 Lua 做自定义逻辑。实践中它通常是所有流量的第一站。

### 2. Nginx 为什么能抗高并发？

**要点：**
- **事件驱动 + 异步非阻塞**（epoll）：worker 单线程处理数千连接，不像传统"一连接一线程/进程"模型被线程开销拖死
- **多进程 + 多路复用**：master 管理多个 worker，worker 间独立（避免线程锁竞争），每 worker 监听 socket 用 epoll 管理海量连接
- **轻量**：C 实现，内存占用小、上下文切换少
- 配套：sendfile 零拷贝、磁盘 IO 异步化（aio）、精简的模块化设计

**一句话答：** 核心是并发模型：worker 用 epoll 事件驱动加异步非阻塞，一个线程就能管理上万条连接，告别一连接一线程的开销；master-worker 多进程架构避免锁竞争；再加上 sendfile 零拷贝这类内核特性。所以 Nginx 能用极少资源扛住十万级并发连接。

### 3. Nginx 的 master 进程和 worker 进程分别负责什么工作？

**要点：**
- **master**：读配置并校验、**绑定监听端口**、fork/管理 worker（收旧养新实现平滑重载 `reload`）、响应信号（stop/quit/reload）、Worker 异常退出自动拉起
- **worker**：**实际处理请求**——accept 连接（惊群由内核 SO_REUSEPORT/锁缓解）、解析 HTTP、反代、读写缓存、记日志
- 平滑重载原理：master 重新读配置 → 起新 worker → 通知旧 worker 处理完存量连接后退出——不中断服务
- 数量经验：worker_processes auto = CPU 核数

**一句话答：** master 是管理者：绑端口、读配置、管理 worker 生命周期，reload 时它先起新 worker 再让旧的优雅退出，实现不中断升级；worker 是干活的：每个 worker 用 epoll 处理成千上万的连接。配置里 worker 数通常设成 CPU 核数。

### 4. Nginx 处理请求的流程是怎样的？

**要点：**
- worker 事件循环：epoll 等待连接/读写事件 → 收到可读事件后：
  1. 解析请求行和头部（HTTP 11 个 phase）
  2. 匹配 **server 块**（按 listen + server_name）→ 匹配 **location**
  3. 按 location 配置执行各 phase：rewrite → access（限流/鉴权）→ **content**（static/proxy_pass/fastcgi_pass）
  4. 上游返回或文件读出 → 过滤模块（gzip、sub、header）→ 发给客户端 → 记 access_log
- 异步非阻塞贯穿全程：等上游响应时 worker 去处理别的连接

**一句话答：** worker 收到事件后解析请求头，先按 IP 端口选 server 块、再按 URI 选 location，然后按阶段执行：rewrite 重写、access 做限流鉴权、content 决定是回静态文件还是 proxy_pass 给上游，最后过 gzip 等过滤层返回并记日志。全程异步，等上游时线程去忙别的连接。

### 5. Nginx 中 worker_processes 和 worker_connections 参数的作用是什么？

**要点：**
- `worker_processes`：worker 进程数——设 **auto**（=CPU 核数）；CPU 密集（大量 SSL/gzip）按核数，IO 密集可略高
- `worker_connections`：**每个 worker** 可同时维持的连接数（含前后端双向）——如 10240
- 系统总连接上限 ≈ worker_processes × worker_connections（反向代理场景每个客户端占 2 个连接：客户端侧+上游侧，实际承载 ≈ 一半）
- 配套系统参数：`ulimit -n`/`worker_rlimit_nofile` 必须不小于 worker_connections，否则报 too many open files

**一句话答：** worker_processes 决定开几个 worker，一般设 auto 跟 CPU 核数走；worker_connections 是每个 worker 能同时握的连接数，两者相乘是理论总连接数，反代场景要除二因为一个客户端占两条连接。重点提醒：worker_rlimit_nofile 和系统 ulimit 必须配套调大，不然白配。

### 6. Nginx 的 keepalive 连接作用是什么？

**要点：**
- 两处 keepalive，要分开说：
  1. **对客户端**（keepalive_timeout/keepalive_requests）：复用浏览器到 Nginx 的连接，省三次握手和慢启动，减少 TIME_WAIT
  2. **对上游**（`upstream { keepalive N; }` + `proxy_set_header Connection "";`）：Nginx 到后端的长连接池——**高频考点**：不开就是每个请求都新建到后端的连接，高 QPS 下后端端口耗尽、TIME_WAIT 爆炸
- 超时权衡：keepalive_timeout 过长积累空闲连接，过短复用率低（常见 60-75s）

**一句话答：** keepalive 就是连接复用。对客户端那段省握手降延迟；重点是 upstream 里的 keepalive——Nginx 到后端的长连接池，不开的话每个请求都新建后端连接，QPS 一高后端 TIME_WAIT 就爆了，还要配 proxy_set_header Connection 空值才能生效。

### 7. location 匹配优先级是怎样的？

**要点：**
- 优先级从高到低：
  1. `location = /exact`（**精确匹配**，命中即停）
  2. `location ^~ /prefix/`（前缀匹配后**不再查正则**）
  3. `location ~ /regex` 和 `~*`（**正则**，区分/不区分大小写，按文件顺序取第一个命中）
  4. `location /prefix`（普通前缀，选**最长**匹配）
  5. `/` 兜底
- 记忆口诀：**先精确、再 ^~ 前缀短路、再正则顺序、最后普通前缀取最长**
- 实战：静态目录用 ^~ 防止被正则意外截胡

**一句话答：** 优先级顺序背下来：等号精确匹配最高，命中直接结束；然后 ^~ 开头的前缀匹配会跳过正则；接着按书写顺序匹配正则；最后才是普通前缀匹配取最长的。实际配置里静态资源目录我都用 ^~ 锁定，防止被后面的正则规则截胡。

### 8. root 和 alias 指令有什么区别？

**要点：**
- `root`：把路径**拼接到** location 后面——`location /img/ { root /data; }` 请求 /img/a.png → 实际文件 `/data/img/a.png`
- `alias`：把 location 匹配的**部分替换掉**——`location /img/ { alias /data/images/; }` 请求 /img/a.png → `/data/images/a.png`
- 细节坑：alias 的路径末尾必须带 /；root 的路径末尾带不带 / 都行

**一句话答：** root 是拼接——location 路径附加在 root 后面；alias 是替换——location 匹配的部分被 alias 路径顶掉。比如 /img/ 配 root /data 找的是 /data/img/，配 alias /data/images/ 找的是 /data/images/。面试常见坑：alias 结尾不带斜杠会拼错路径。

### 9. 什么情况下会用 rewrite？

**要点：**
- 典型场景：
  - **URL 美化/SEO**：/product.php?id=1 → /product/1
  - **旧路径迁移**：301 到新地址保权重
  - **多端适配**：按 User-Agent rewrite 到 m. 移动站
  - **规范化**：强制 https、统一域名（www→裸域）、补末尾斜杠
- 语法：`rewrite regex replacement [flag]`；flag：last（重走 location 匹配）、break（停止重写继续当前处理）、redirect（302）、permanent（301）
- 能用 `return 301` 解决的重定向就不要用 rewrite（更轻）

**一句话答：** rewrite 用在 URL 改写场景：SEO 美化、老地址迁移 301、强制 https、按设备跳移动端。四个 flag 必须能说清：last 重新走 location 匹配，break 就地停，redirect 和 permanent 分别是 302 和 301。补充一句：单纯跳转优先用 return 301，比 rewrite 更轻量。

### 10. try_files 指令有什么作用？

**要点：**
- 作用：**按顺序检查文件是否存在**，存在就返回，都不存在落到最后一个兜底（内部重定向或错误码）
- 经典用法：
  - **前端路由（SPA）**：`try_files $uri $uri/ /index.html;`——文件没有就回 index.html，交给前端路由
  - **静态文件兜底动态**：`try_files $uri @backend;`——有静态文件直接给，没有转后端
  - 防目录穿越：`try_files $uri =404;`
- 对比 if+rewrite：try_files 是官方推荐方式，性能更好无副作用

**一句话答：** try_files 按顺序找文件，找到就返回，找不到走最后那个兜底。最经典的是前端 SPA 路由：$uri $uri/ /index.html，让所有路径都落到 index.html 交给前端路由；还有静态文件优先、缺了才回源后端的动静兜底。官方也推荐用它替代 if 判断。

### 11. sendfile、tcp_nopush 指令有什么作用？

**要点：**
- `sendfile on`：**零拷贝**——文件数据从内核页缓存直接发到网卡，绕过用户态拷贝，静态文件传输 CPU 大降
- `tcp_nopush on`：配合 sendfile，数据包**攒满一个 MSS 再发**（相当于开 TCP_CORK），减少小包数量，提高网络利用率
- 配套：`tcp_nodelay on`（禁 Nagle，小包立即发）——针对长连接的交互性，和 nopush 方向相反但作用域不同（nopush 管文件传输，nodelay 管长连接响应）

**一句话答：** sendfile 是零拷贝：静态文件从内核缓存直接送网卡，省掉用户态来回拷贝；tcp_nopush 让它攒够一个 MSS 包再发减少小包。这俩是静态资源加速的标准组合，再加上长连接场景的 tcp_nodelay 保证交互不延迟。

### 12. expires 指令有什么作用？

**要点：**
- 设置 **Expires/Cache-Control: max-age** 响应头，指示**浏览器强缓存**时长
- `expires 7d;`：7 天内浏览器不发请求直接用本地缓存（配合 nginx 设置的 ETag/Last-Modified，过期后走 304 协商）
- 最佳实践：带 hash 的静态资源（app.a1b2c3.js）设超长 expires（如 1y）；HTML 入口设短或不缓存——**内容变了 URL 一定变**
- 收益：静态资源请求被挡在浏览器外，回源流量大降，用户二次访问近乎秒开

**一句话答：** expires 就是给浏览器下发强缓存时间，期间请求根本不会到服务器。实践口径：带文件指纹的 js css 设一年，HTML 设 no-cache 保证入口新鲜。这样静态流量被浏览器吃掉，CDN 和源站压力骤降。

### 13. gzip 指令有什么作用？

**要点：**
- 作用：对响应**压缩**后传输，文本类压缩率 60-80%，省带宽、降 TTFB 后的传输时间
- 标准配置：`gzip on; gzip_comp_level 5; gzip_min_length 1k; gzip_types text/css application/javascript application/json ...;`（默认只压 text/html，**必须补 types**）；对已压缩类型（jpg/mp4）不要压
- 进阶：**brotli**（ngx_brotli 模块）压缩率再优 15-20%，现代浏览器支持；HTTP/2 场景配合更好
- 权衡：CPU 换带宽——压缩等级 4-6 性价比最高，接入层做，别让应用层重复压缩

**一句话答：** gzip 是用 CPU 换带宽：文本资源压缩率七成左右。配置必记三点：gzip_types 默认只有 html，要手动补 css js json；min_length 1k 防止压小文件负优化；等级选 5 左右别拉满。能上 brotli 更好，压缩率再高一截。

### 14. 反向代理与正向代理的区别是什么？

**要点：**
- **正向代理**：**代理客户端**——服务端不知道真实客户端是谁（科学上网、爬虫代理、公司出口）；客户端配置代理
- **反向代理**：**代理服务端**——客户端不知道后端是谁，以为 Nginx 就是服务（LB、SSL 卸载、缓存）；对客户端完全透明
- 记忆：隐藏**客户端**是正向，隐藏**服务端**是反向

**一句话答：** 方向问题：正向代理站在客户端这边，替用户去访问，服务端看不到真实用户；反向代理站在服务端这边，替服务器接收请求，用户看不到真实后端。Nginx 在生产里干的是反向代理，正向代理的经典例子是公司出口和爬虫 IP 池。

### 15. proxy_pass 指令后加/和不加/有什么区别？

**要点：**
- 规则核心：**有没有 URI 部分**（哪怕只是一个 /）
- `proxy_pass http://backend;`（无 /）：**原样透传**完整 URI——/api/x → 后端收到 /api/x
- `proxy_pass http://backend/;`（有 /）：**替换** location 匹配的前缀——location /api/ { proxy_pass http://backend/; } → /api/x → 后端收到 /x
- 混合写法陷阱：`proxy_pass http://backend/static/;` 拼接规则更绕（location /api/ 时 /api/x → /static/x）——建议只用两种干净写法
- 记忆：带斜杠=重写路径（剥前缀），不带=原样转交

**一句话答：** 区别在路径处理：proxy_pass 不带斜杠，请求路径原样转给后端；带斜杠就是把 location 匹配的前缀剥掉再转发——location /api 配 backend/ 的话，/api/user 到后端就变成 /user。实际配置我建议固定用这两种干净写法，混合带路径的写法容易拼出诡异 URL。

### 16. Nginx 怎么配置负载均衡？

**要点：**
- 基本配置：

```nginx
upstream backend {
    server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080 backup;
}
server {
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_next_upstream error timeout;   # 失败重试下一台
    }
}
```

- 关键点：weight 权重、backup 备节点、max_fails+fail_timeout 被动摘除、proxy_next_upstream 故障转移、keepalive 长连接池

**一句话答：** upstream 块定义服务器组，proxy_pass 引用即完成负载均衡。生产必配四样：weight 控制权重分配、max_fails 和 fail_timeout 让故障节点被动摘除、proxy_next_upstream 让失败请求自动重试下一台、keepalive 长连接池保护后端端口。

### 17. Nginx 负载均衡支持哪些调度算法及应用场景？

**要点：**
- **round-robin**（默认）：轮询；weight= 加权轮询（机器性能不均）
- **least_conn**：最少连接——请求处理时长差异大（长连接、文件上传）
- **ip_hash**：按客户端 IP 固定到一台——简单会话保持（缺点：破坏负载均衡、NAT 后多用户同 IP 集中）
- **hash $xxx**：自定义 key 哈希（如 hash $cookie_jsessionid consistent）——一致性哈希，增删节点影响面小，缓存服务常用
- 场景速记：均匀负载默认轮询，耗时悬殊 least_conn，要会话 ip_hash 或 cookie hash，缓存命中一致性哈希

**一句话答：** 四个算法四个场景：默认轮询适合同质服务；请求耗时差异大用 least_conn 避免长请求压垮个别节点；需要会话保持用 ip_hash 但注意 NAT 用户集中问题，更优雅的是按 cookie 哈希；缓存类后端必须上一致性哈希，扩容缩容才不会导致缓存大面积失效。

### 18. Nginx 如何实现后端服务的健康检查？

**要点：**
- **开源版：被动检查**——`max_fails=3 fail_timeout=30s`：连续 3 次失败标记不可用 30 秒再试；配 `proxy_next_upstream` 把失败请求转到健康节点。缺点：已经有真实请求失败才感知
- **主动检查**：商业版 Nginx Plus 的 health_check（定期发探测请求）；开源替代：**nginx_upstream_check_module**（淘宝 patch）、自建脚本探测+动态改 upstream（API/Consul）
- K8s 场景：Endpoint 由 kubelet 探针管理，Nginx ingress 自动同步——探针职责交回平台

**一句话答：** 开源版 Nginx 只有被动检查：max_fails 加 fail_timeout，真实请求连续失败就摘除超时再放回，缺点是拿用户请求当探针。要主动探测得上 nginx_upstream_check_module 补丁或 Nginx Plus。在 K8s 里这层职责交给平台的探针机制，Ingress 只管同步 Endpoint。

### 19. proxy_cache 与 fastcgi_cache 的作用分别是什么？

**要点：**
- 同一套缓存机制，作用于不同上游类型：
  - **proxy_cache**：缓存 **proxy_pass 反代**的响应（HTTP 上游）——最常用
  - **fastcgi_cache**：缓存 **fastcgi_pass**（PHP-FPM）的响应
- 配套四要素：`proxy_cache_path` 定义存储区（keys_zone、max_size、inactive）；`proxy_cache myzone` 启用；`proxy_cache_valid 200 10m` 定 TTL；`proxy_cache_key` 定键（含 $request_uri）
- 进阶：proxy_cache_bypass/$upstream_cache_bypass 穿透、PURGE 清缓存、X-Cache-Status 响应头调试（MISS/HIT/BYPASS）

**一句话答：** 两者是同一套缓存机制挂在不同协议上：proxy_cache 缓存反代响应，fastcgi_cache 缓存 PHP 动态执行结果。配置四件套：cache_path 定义存储、cache 指令启用、cache_valid 定有效期、cache_key 定唯一键。调试时加 X-Cache-Status 头看命中状态最直观。

### 20. stream 模块作用是什么？

**要点：**
- Nginx 的 **四层（TCP/UDP）代理模块**：不解析 HTTP，纯字节流转发
- 场景：MySQL/Redis 代理入口、SSH 跳转、MQ 代理、UDP（DNS/游戏）转发；四层负载均衡（补 http 反代不能管的协议）
- 配置示例：

```nginx
stream {
    upstream mysql {
        server 10.0.0.1:3306;
        server 10.0.0.2:3306;
    }
    server {
        listen 3306;
        proxy_pass mysql;
        proxy_connect_timeout 5s;
    }
}
```

- 编译需 --with-stream；与 LVS 对比：单机性能低于 LVS，但配置灵活、带日志

**一句话答：** stream 模块让 Nginx 变成四层 TCP/UDP 代理，不理解协议纯转发——数据库入口、Redis、SSH 跳板这类非 HTTP 服务都靠它。配置和 http 块平行，upstream 加 server 一样能用负载均衡。需要 --with-stream 编译支持，轻量四层场景比上 LVS 简单得多。

### 21. Nginx 如何实现限流？

**要点：**
- **limit_req_zone / limit_req**（请求速率，漏桶算法）：

```nginx
limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
server {
    location /api/ {
        limit_req zone=one burst=20 nodelay;
        limit_req_status 429;
    }
}
```

  rate 10r/s 允许 burst=20 的突发，nodelay 不排队直接放行突发额度
- **limit_conn_zone / limit_conn**（并发连接数）：单 IP 最大并发连接限制
- **limit_rate**（带宽）：单连接下载限速（大文件分发）
- 补充：全局防刷结合 ngx_lua（OpenResty + Redis 计数）做分布式限流；云上 WAF/网关层限流

**一句话答：** 三种粒度：limit_req 控请求速率，漏桶算法配 burst 和 nodelay 允许受控突发；limit_conn 控单 IP 并发连接数；limit_rate 控下载带宽。这些是单机限流，分布式场景要 OpenResty 加 Redis 集中计数，或者干脆上专门的网关层。

### 22. 如何实现 URL 重定向，同时保持浏览器URL不变？

**要点：**
- "URL 不变"= **内部跳转/反向代理**，不是 30x 重定向（30x 会改浏览器地址栏）
- 方案：
  1. **proxy_pass 反代**：浏览器请求 /old-path，Nginx 内部转给后端不同路径——浏览器只看到原 URL
  2. **rewrite ... last/break**（无 redirect/permanent flag）：Nginx 内部重写到新 location 处理
  3. 静态文件场景 try_files 兜底到指定文件
- 反之"改地址栏"才用 301/302

**一句话答：** 关键是区分内部跳转和外部重定向：地址栏要不变就不能发 301/302，得用 proxy_pass 反代或 rewrite 加 last 标志在 Nginx 内部把请求转给真实路径——浏览器全程只看到原 URL。加了 redirect 或 permanent 标志才变成外部跳转，地址栏会变。

### 23. 301 和 302 重定向有什么区别？Nginx 如何配置？

**要点：**
- **301** Moved Permanently：**永久**重定向——浏览器/搜索引擎会**缓存**，之后直接跳新地址不再问源站；SEO 权重转移到新 URL
- **302** Moved Temporarily：临时——每次都请求原地址再跳，不缓存
- 配置：

```nginx
# 301: 强制 https + 域名规范化
server {
    listen 80;
    server_name old.com www.new.com;
    return 301 https://new.com$request_uri;
}
# 302: 临时跳转(如维护页)
return 302 /maintain.html;
```

- 运维坑：误用 301 后改回 302，浏览器和 CDN 缓存还会继续跳——301 慎用且要能清理缓存

**一句话答：** 301 永久会被浏览器和搜索引擎缓存，权重也跟着转移，适合域名迁移和强制 https；302 临时每次都问源站，适合活动跳转。配置用 return 301 https://new.com$request_uri 一行搞定，$request_uri 保住路径参数。坑在 301 收不回——配错了缓存会记很久。

### 24. Nginx 环境，提示上传文件过大如何解决？

**要点：**
- 报错：413 Request Entity Too Large
- 主因：`client_max_body_size`（**默认 1M**）——在 http/server/location 设置，如 `client_max_body_size 100m;`
- 配套调整：`client_body_buffer_size` 适当加大（大文件少落临时盘）、`proxy_request_buffering off`（大文件流式转发不缓存到 Nginx 磁盘）
- **多级代理每层都要改**：CDN/WAF/LB（如 SLB 也有上限）/Nginx/应用框架（PHP upload_max_filesize、Spring max-file-size）任一层小于文件大小都会 413
- 超时配套：大文件上传调大 proxy_read_timeout / client_body_timeout

**一句话答：** 413 就是 body 超过 client_max_body_size，默认只有 1M，location 里按需调大。关键认知是这条链路上每一层都有上限——CDN、负载均衡、Nginx、应用框架，改一处没用要逐层放开，大文件还要配 proxy_request_buffering off 让它流式转发，不然 Nginx 磁盘先扛不住。

### 25. Nginx 如何实现动静分离？

**要点：**
- 原则：**静态资源 Nginx 直接返回，动态请求才转后端**——后端不做静态服务（Tomcat 静态性能差、占线程）
- 配置：

```nginx
location ~* \.(jpg|png|css|js|woff2)$ {
    root /data/static;
    expires 30d;
    access_log off;
}
location / {
    proxy_pass http://tomcat;
}
```

- 进阶：静态资源再上 CDN；带 hash 文件名长缓存；独立静态域名（防 Cookie 污染）
- 收益：后端连接数释放、静态命中快、缓存策略独立

**一句话答：** 就是让 Nginx 按文件后缀分流：静态的 root 直出加长缓存，剩下的全转后端。收益是后端线程不被静态请求占用、静态访问直接命中内核缓存。规模大了再推一层——静态资源甩给 CDN，源站只出动态。

### 26. Nginx 如何实现灰度发布？

**要点：**
- **按权重分流**：upstream 两版 server 配 weight（10% 新版 90% 旧版）——最简单
- **按用户特征**（更精准）：
  - Cookie：`if ($cookie_gray = "on") { proxy_pass http://new_ver; }`——内部员工先体验
  - Header/IP：按 $http_x_gray 或特定 IP 段路由
  - 双 upstream + map 判断：

```nginx
upstream stable { server 10.0.0.1:8080; }
upstream canary { server 10.0.0.2:8080; }
map $cookie_gray $pool {
    default stable;
    "on"    canary;
}
server {
    location / { proxy_pass http://$pool; }
}
```

- 生产更常见：网关层（APISIX/ingress 注解）或服务网格做灰度，Nginx 适合单体接入层
- 配套：灰度期监控对比错误率/RT，放量节奏 1%→10%→50%→100%

**一句话答：** 两档做法：粗粒度用 upstream 权重分流，比如新版本 weight 1 旧版本 9；细粒度按用户路由——map 读 cookie 或 header 决定 proxy_pass 到哪个 upstream，让内部员工先上新版。灰度期间盯着两版的错误率和延迟对比，按 1%、10%、50% 节奏放量。

### 27. 简述 Nginx 版本升级流程？

**要点：**
- **平滑升级**（不停服）：`make upgrade` 或手动流程：
  1. 备份旧二进制 → 编译新版本（注意模块 --with 参数与旧版一致：`nginx -V` 对照）
  2. 替换二进制文件（mv 旧的、cp 新的）
  3. `kill -USR2 <master_pid>`：master 起新 master（新版本）+ 新 worker，旧的改名 pid.oldbin 继续服务
  4. `kill -WINCH <旧master>`：优雅退出旧 worker（处理完存量连接）
  5. 验证正常后 `kill -QUIT <旧master>`；异常则 `kill -HUP 旧master` 回滚
- 生产替代：yum/apt 包升级自动走平滑、或 LB 摘节点逐台重启
- 前置：nginx -t 测新配置、备份配置与二进制

**一句话答：** 平滑升级靠信号组合拳：USR2 让 master 拉起一套新 master 加新 worker 新旧并存，WINCH 让旧 worker 优雅退出，确认没问题 QUIT 掉旧 master，出问题 HUP 就能回滚。前提是新版本编译参数要和旧版一致——nginx -V 抄作业，升级前 nginx -t 验配置。

### 28. Nginx 出现499状态码的常见原因是什么？

**要点：**
- 499 = **Nginx 自定义状态码：客户端在 Nginx 返回响应前主动断开连接**
- 常见原因：
  1. **客户端超时**：App/前端 axios timeout 比后端处理快——客户端等不及先断（最常见）
  2. 用户主动取消：关页面、取消请求、爬虫放弃
  3. 中间层超时掐断：网关/SDK 超时小于后端 RT
  4. 后端真的慢：499 多发往往伴随后端性能劣化——是"慢"的信号不是错误本身
- 处理：对齐客户端与网关超时阈值（客户端 > 网关 > 上游）、优化慢接口、区分"合理取消"与"异常慢"（看后端处理耗时分布）

**一句话答：** 499 是 Nginx 发明的码：客户端等不到响应自己先断了。根因排序：客户端超时设置比后端处理快——最常见；用户取消；或者后端确实变慢。所以 499 陡增不是 Nginx 的错，它是后端变慢的信号灯，处理思路是把超时链对齐成客户端大于网关大于上游，再治慢接口。

### 29. Nginx 出现502 Bad Gateway的常见原因是什么？

**要点：**
- 502 = Nginx 与**上游的连接/响应失败**：
  1. **上游进程挂了**（崩溃/OOM/未启动）——connect refused
  2. 上游**监听端口不对**/防火墙拦截
  3. 上游过载：php-fpm 进程全忙、Tomcat 线程满、accept 队列满（somaxconn）——连接被拒
  4. 上游返回**非法 HTTP 响应**或提前断开（响应头超大、崩溃在处理中）
  5. 长连接池污染：upstream keepalive 配了但 header 处理不当（Connection 头没清）
- 排查：error.log 具体错误（connect() failed / recv() failed / upstream sent invalid header）→ 对应进程/端口/资源 → 修上游或调参（worker_processes、listen backlog）

**一句话答：** 502 分三类记：上游死了——进程崩溃或没启动，报 connect refused；上游忙不过来——fpm 和线程池占满、队列溢出拒绝新连接；上游说了不该说的话——返回非法响应头或中途断开。排查入口永远是 Nginx error.log，它会告诉你具体是哪一类。

### 30. Nginx 出现403 Forbidden的常见原因是什么？

**要点：**
- 403 = Nginx **拒绝提供文件/转发**（和 404 不同：文件在但不给）：
  1. **文件权限**：静态文件对 nginx worker 用户（www-data/nginx）无读权限——含目录 x 权限（沿路径逐级都要）
  2. **autoindex 未开**：访问目录且无默认索引文件（index.html）→ 403
  3. **deny 规则/allow 白名单**拒绝：IP 黑白名单命中
  4. SELinux 上下文问题（RHEL 系常见：`restorecon -R` 或 chcon）
  5. 缺 index 且请求目录、location 被 return 403
- 排查：error.log 里 "Permission denied" vs "directory index forbidden" 区分根因

**一句话答：** 403 是"文件在但我不给"，按频率排：worker 用户读不了文件——检查整条路径的权限；访问了目录又没有 index 文件也没开 autoindex；配置里有 deny 规则命中；RHEL 系别忘了 SELinux。看 error.log 的具体描述一秒定位是权限还是规则。

### 31. 如何优化 Nginx 性能？

**要点：**
- **系统层**：ulimit -n、`net.core.somaxconn`、tcp_tw_reuse、网卡多队列/RPS（软中断均衡）
- **Nginx 层**：
  - worker_processes auto、worker_connections 调大（配合 worker_rlimit_nofile）
  - sendfile + tcp_nopush（静态）、gzip（text 类）
  - upstream keepalive 长连接池
  - SSL 优化：ssl_session_cache/ssl_session_timeout 复用、TLS1.3、OCSP stapling、必要则 ssl_prefer 开 ECC 证书
  - access_log 缓冲：`access_log path buffer=64k flush=5s`；无必要目录 access_log off
  - 超时收短（keepalive_timeout 适度）防连接堆积
- **架构层**：动静分离、缓存、限流保护、不要在 Nginx 里堆过重 if/Lua 逻辑
- 验证：ab/wrk 压测对比

**一句话答：** 我按三层给答案：系统层调大句柄和 somaxconn、均衡软中断；Nginx 层 worker 数跟核走、连接数放开、开 sendfile 和 gzip、upstream 上长连接、SSL 会话复用、日志缓冲写入；架构层做动静分离和缓存。最后必须压测验证——没有对比数据的优化都是自我安慰。

### 32. 如何监控 Nginx 的运行状态？

**要点：**
- **stub_status**（内置）：active connections、accepts、handled、requests、Reading/Writing/Waiting——nginx -V 确认带 http_stub_status_module：

```nginx
location /nginx_status {
    stub_status;
    allow 10.0.0.0/8; deny all;
}
```

- **Prometheus 采集**：nginx-exporter 抓 stub_status → Grafana 面板；更细指标（各 upstream 状态、响应码分布）用 **nginx-lua-prometheus** 自定义
- **日志分析**：access_log 错误率/RT 分布（P99）、error_log 盯 502/worker_connections 耗尽
- 进程级：master/worker 存活（process exporter）、worker 异常重启次数

**一句话答：** 基础用 stub_status 模块暴露连接数和请求计数，记得加 IP 白名单；标准做法是 nginx-exporter 接 Prometheus 出面板，要细分到 upstream 和状态码就用 lua-prometheus 自己埋点；日志侧盯错误率和 P99 延迟。告警重点：worker 重启、502 突增、连接数逼近 worker_connections。

### 33. Nginx 如何实现高可用性（HA）？

**要点：**
- **Keepalived VIP 方案**（同机房经典）：两台 Nginx 互为主备，VRRP 心跳，MASTER 持 VIP；配合脚本检测 Nginx 进程（check nginx 存活，挂了降权让 VIP 漂移）；防脑裂注意心跳链路
- **云 LB 方案**：云 SLB/ALB 前置，Nginx 多台挂后面——弹性伸缩+自动摘除，省心（推荐云上用）
- **DNS 轮询**：多 A 记录（简单但故障切换慢、依赖 TTL）
- **架构完整版**：LVS+Keepalived（四层）→ Nginx 集群（七层）→ 后端；任一节点故障健康检查自动摘除
- 双活演进：跨机房双 VIP/Anycast，避免单机房故障

**一句话答：** 同机房经典方案是 Keepalived：两台 Nginx 抢一个 VIP，心跳断了备机接管，脚本里加上 Nginx 进程检测防止"Nginx 挂了 VIP 却不漂"。云上更推荐直接用 SLB 挂多台 Nginx，健康检查和摘除都是平台自带。再往上是 LVS 加 Nginx 两级加多机房双活的完整形态。

### 34. 你使用 Nginx 集成过 Lua 脚本吗？做过哪些事情？

**要点：**（按真实经历组织，给常见方向）
- 底座：**OpenResty**（Nginx + lua-nginx-module）或原生 ngx_http_lua_module；Lua 协程非阻塞，与 Nginx 事件模型天然契合
- 常见落地场景：
  1. **动态限流/风控**：连 Redis 计数，按用户/IP 精细限流（比 limit_req 灵活）
  2. **WAF 规则**：请求特征拦截（SQL 注入特征、CC 攻击）
  3. **动态 upstream**：从 Redis/Consul 实时取后端列表，服务上下线免 reload
  4. **自定义鉴权**：JWT 校验、签名验证在网关层完成
  5. **灰度路由**：按复杂业务逻辑选 upstream
- 注意事项：Lua 代码异常处理（防 500）、Redis 连接池复用、避免阻塞操作（用 cosocket 非阻塞 API）、代码热更新机制

**一句话答：** 基于 OpenResty 做过几类：网关层动态限流——Lua 连 Redis 做分布式计数，比原生 limit_req 灵活得多；JWT 鉴权前移到 Nginx 层；upstream 从注册中心动态拉取实现服务上下线免 reload。开发时要记住 Lua 是协程非阻塞模型，必须用 cosocket 这类非阻塞 API，否则一个阻塞调用就卡住整个 worker。

## 微服务运维面试题

### 1. 微服务架构你怎么理解的？

**要点：**
- 定义：把单体应用按**业务边界**拆成一组小服务，独立开发、部署、扩缩容，服务间通过轻量通信（HTTP/RPC/MQ）协作
- 收益：独立部署（一个服务上线不牵全身）、独立扩容（只扩瓶颈服务）、技术栈自由、团队自治（康威定律对齐）
- 代价：分布式复杂性（网络抖动、数据一致性）、运维复杂度暴增（几十上百个服务要监控/发布/排障）、链路长故障点多
- 前提条件：自动化基建成熟（CI/CD、监控、注册发现）——没这些基建强行微服务=自杀
- 单体 vs 微服务：小团队小业务先单体模块化，业务复杂到瓶颈再拆

**一句话答：** 微服务是按业务边界拆成可独立部署的小服务，换来的是独立发布、精准扩容和团队自治；代价是分布式的一系列麻烦——链路长、数据一致性弱、运维面扩大。我的观点是微服务是运维密集型架构，CI/CD 和可观测性基建不成熟就别拆，单体模块化撑到业务复杂到必须拆为止。

### 2. 微服务中的注册中心作用是什么？

**要点：**
- 解决问题：服务实例**动态变化**（IP 不固定、弹性扩缩、故障下线）——调用方如何找到可用实例
- 机制：服务启动时**注册**自身地址 → 注册中心维护服务列表 → 调用方**订阅/拉取**列表 → 客户端负载均衡选实例
- **健康检查/心跳**：实例失联自动摘除——调用方拿到的永远是活的列表（配合客户端重试）
- 附加：元数据（版本、机房、灰度标签）支持路由策略
- 没有注册中心的远古做法：写死 IP 列表——扩缩容全靠改配置

**一句话答：** 注册中心解决"服务地址动态变化"：实例启动注册、调用方订阅列表、心跳保活自动摘除故障节点。它是微服务的通讯录加健康监控——没有它，弹性伸缩和故障转移都无从谈起。

### 3. 主流注册中心有哪些？

**要点：**
- **Nacos**：阿里开源，注册+**配置中心二合一**，AP/CP 可切换，国内 Spring Cloud 生态主流
- **Consul**：HashiCorp，CP，K/V 配置+服务发现+健康检查，多数据中心，运维生态好
- **Eureka**：Netflix，AP（自我保护机制防网络分区误杀），Java 系经典但社区进入维护期
- **ZooKeeper**：CP（ZAB），老牌分布式协调，Kafka 老版依赖；做注册中心延迟敏感场景有短板
- **Kubernetes 原生**：Service/Endpoint + CoreDNS 本身就是注册中心——云原生时代很多团队不再引入独立组件
- 选型一句话：Spring Cloud 国内选 Nacos，K8s 体系直接用原生 Service

**一句话答：** 常见四加一：Nacos 注册配置二合一是国内主流，Consul CP 强一致适合多数据中心，Eureka 是 AP 老将但已维护模式，ZooKeeper 偏协调场景做注册中心不算顺手；云原生体系里 K8s 的 Service 加 CoreDNS 本身就是注册中心，很多团队因此省掉独立组件。

### 4. 微服务架构实现有哪些技术？

**要点：**
- **Java 系**：Spring Cloud（Nacos/Gateway/OpenFeign/Sentinel 全家桶）、Dubbo（RPC 高性能）
- **云原生**：Kubernetes（部署/服务发现/弹性）+ Service Mesh——**Istio**（Sidecar 接管流量：灰度、熔断、加密，语言无关）
- **网关**：Spring Cloud Gateway、APISIX、Kong
- **配套**：注册中心（Nacos/Consul）、配置中心（Nacos/Apollo）、链路追踪（SkyWalking/Jaeger）、监控（Prometheus）
- 语言无关方案：gRPC（RPC 通信标准）、Envoy

**一句话答：** 技术栈分两派：Java 传统派用 Spring Cloud 或 Dubbo，从注册到网关到熔断全家桶齐活；云原生派用 K8s 加 Istio 服务网格，Sidecar 接管流量治理，业务代码语言无关。两派都需要配置中心、链路追踪、监控这些配套设施——技术选型差异在流量治理层，基建要求是一样的。

### 5. 微服务之间是如何通讯的？

**要点：**
- **同步**：
  - **HTTP/REST + JSON**：简单通用，性能一般
  - **RPC**：Dubbo、gRPC（HTTP/2 + Protobuf，二进制序列化性能高，跨语言）——内部高频调用首选
- **异步**：MQ（Kafka/RocketMQ）——解耦、削峰、最终一致；事件驱动架构
- 同步 vs 异步选型：强依赖实时结果用同步（下单查库存），可异步的处理用消息（下单后发积分）
- 治理配套：超时、重试（幂等前提）、熔断降级——同步调用的三件保护

**一句话答：** 同步两条路：REST 简单通用，gRPC/Dubbo 二进制高性能适合内部高频调用；异步走消息队列做解耦削峰。选型原则是看实时性要求——需要立即拿结果的同步，能晚点处理的扔 MQ。同步调用必须配超时重试加熔断，不然一个服务慢就能拖垮整条链路。

### 6. 微服务架构中的配置中心作用是什么？

**要点：**
- 解决：多环境（dev/test/prod）×多服务实例的配置**统一管理与下发**——告别改配置挨个登机器、打包时配置写死
- 核心能力：**集中管理**、**环境隔离**（namespace/group）、**动态刷新**（改配置推送到运行中实例，不用重启）、**版本回滚**、权限与审计、灰度发布配置
- 主流：**Nacos**（国内主流）、**Apollo**（携程，配置治理功能最强）、Consul K/V、Spring Cloud Config（Git 存储较重）
- 敏感配置：对接 KMS/Vault 加密存储

**一句话答：** 配置中心把散在各机器的配置收拢起来：环境隔离管理、运行中动态刷新不用重启、改错能回滚、变更可审计。国内选型就是 Nacos 和 Apollo 二选一。运维价值巨大——配置变更从"登 N 台机器改文件"变成"平台改一处，秒级全量生效"。

### 7. 微服务架构中的 API 网关的作用是什么？

**要点：**
- **统一入口**：所有外部流量先到网关——客户端只见一个域名
- 核心职能：
  - **路由转发**：按路径/Host 分发到后端微服务
  - **认证鉴权**：JWT/OAuth 校验在网关完成，后端专注业务
  - **限流熔断**：全局限流、按 API 限流保护后端
  - **灰度发布**：按 header/用户分流
  - **日志与观测**：统一 access 日志、traceID 注入
  - 协议适配、缓存、请求改写
- 主流：Kong、APISIX、Spring Cloud Gateway、云厂商 API Gateway
- 位置注意：网关自身要高可用（多实例+LB），网关挂=全站挂

**一句话答：** 网关是全站唯一入口，干四类事：路由转发、认证鉴权前移、全局限流熔断、统一观测埋 traceID。价值在于把安全和管理逻辑从几十个微服务收敛到一个地方。运维要记住网关是全站单点风险，自身必须多实例高可用，限流策略要留余量防误伤。

### 8. 怎么实现微服务灰度发布？

**要点：**
- **按流量比例**：网关/Service Mesh 权重分流（1%→10%→50%→100%）
- **按用户特征**：header/cookie/用户标签路由——内部员工/白名单用户先体验（金丝雀）
- **按部署单元**：K8s 双 Deployment + Ingress 注解（nginx ingress 的 canary 注解：weight/header）；Istio VirtualService 精细路由
- **全链路灰度**（进阶）：灰度标签贯穿网关→各服务→MQ，染色流量全程走灰度实例——需要注册中心/网关/MQ 联动
- 配套：灰度期监控对比（错误率/RT/业务指标）、一键回滚、数据兼容（新旧版本读同一套库要 schema 向后兼容）

**一句话答：** 基础做法是网关按比例分流加白名单用户先上；K8s 里就是双 Deployment 配 Ingress canary 注解，或 Istio 的 VirtualService。进阶是全链路灰度——给请求染色，让灰度标签贯穿所有服务和消息队列。两条纪律：灰度期两版本监控对比，数据库 schema 必须向后兼容。

### 9. 微服务部署时如何管理多环境配置（dev、test、prod）？

**要点：**
- **配置中心按环境隔离**：Nacos 的 namespace（dev/test/prod 各一个）、Apollo 的环境和集群概念——同一份代码不同环境自动取对应配置
- **12-Factor 原则**：配置与代码分离，配置全部外部化（环境变量/配置中心），镜像一份多环境通用
- **密钥分离**：数据库密码等敏感配置走 KMS/Vault/加密项，不进 Git 明文
- **流水线联动**：CI/CD 按部署环境注入配置中心 namespace；发布到 prod 的配置变更加审批
- 防呆：prod 配置修改权限收紧、变更审计、错误配置的快速回滚能力

**一句话答：** 标准做法是配置中心按 namespace 隔离环境，镜像只构建一份、按部署目标自动关联对应环境配置，做到配置与代码分离。敏感信息单独走 Vault 加密，生产配置变更走审批留审计。运维要守住的底线是：谁都能改 dev，但改 prod 必须有权限控制和回滚手段。

### 10. 当某个微服务调用链出现延迟时，你会如何定位问题？

**要点：**
- **链路追踪系统**（SkyWalking/Jaeger/Zipkin）：按 traceID 看完整调用树——**哪个 span 耗时**一目了然（这是微服务排障的核心武器）
- 无 traceID 时的分层排查：
  1. 网关日志：哪个下游服务慢
  2. 该服务指标：线程池满？GC 频繁？CPU 高？
  3. 下游依赖：DB 慢查询、Redis 慢命令、第三方接口 RT——**依赖拖累是高频根因**
  4. 资源层：容器 CPU 限流（throttling）、宿主机争抢、网络重传
- 常见根因榜单：慢 SQL、连接池耗尽、Full GC、线程池排队、下游超时重试风暴
- 治理确认：修复后 P99 曲线回落，加对应慢查询/RT 告警防复发

**一句话答：** 有 APM 就直奔 traceID 看调用树，哪段 span 长哪段就有问题——这是最快路径。没有追踪系统就看分层指标：网关定位到服务，服务内查线程池、GC 和下游依赖，特别警惕慢 SQL 和连接池耗尽这两个惯犯。还有个隐蔽根因是容器的 CPU limit 被限流，指标看起来"不高"但实际被 cgroup 卡着。

### 11. 微服务出现 500 错误时，你通常会先排查哪些环节？

**要点：**
- 排查顺序（从"是谁的错"出发）：
  1. **网关/调用方日志**：确认是哪个服务返回的 500、请求参数、traceID
  2. **目标服务日志**：异常堆栈是最直接答案（NPE、超时、连接拒绝）
  3. **变更核对**：最近发布/配置变更——**第一嫌疑**，能回滚先回滚
  4. **依赖健康**：数据库/Redis/MQ/下游服务状态——500 常是下游异常传染
  5. **资源层**：OOM 重启记录、容器重启次数、磁盘水位
- 区分：500（服务内部错误）vs 502/504（网关层面连接问题）vs 499（客户端等不及）——状态码先分流
- 止血优先级高于根因：回滚、降级、切流先行

**一句话答：** 先看异常堆栈——服务日志里的 stack trace 就是答案本身；同时核对最近变更，500 突增八成和发布有关。堆栈里如果是下游连接异常，就顺着查依赖健康状态。整条纪律是止血优先：先回滚降级恢复业务，再慢慢定位根因。

### 12. 在使用微服务架构时，运维会面临哪些挑战？

**要点：**
- **可观测性**：几十上百服务、链路交错——没有分布式追踪和集中监控就是黑盒；日志量爆炸
- **发布管理**：每天多次发布、服务间版本兼容（接口向后兼容纪律）、灰度与回滚自动化
- **故障定位**：一个用户请求穿 10 个服务，故障传播（雪崩）——需要熔断限流和全链路 trace
- **配置与一致性**：多环境配置管理、服务发现、证书轮转
- **资源管理**：容器资源配额、弹性伸缩策略、成本核算
- **安全**：东西向流量（服务间）认证加密（mTLS）、最小权限
- 应对思路：平台化（K8s+Mesh+可观测体系）+ 自动化一切——微服务的运维复杂度必须靠平台消化，不能靠人堆

**一句话答：** 五大挑战：可观测性——没有 traceID 的微服务排障是灾难；发布——高频发布要全自动化加兼容性纪律；故障传播——雪崩防护靠熔断限流；配置和资源——多环境管理和弹性策略；安全——服务间通信从"内网可信"转向 mTLS 零信任。我的总结是：微服务把运维复杂度从"维护几台机器"升级成"建设一个平台"，没有自动化基建的团队撑不住这个复杂度。
