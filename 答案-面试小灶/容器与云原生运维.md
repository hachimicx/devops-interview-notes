# 容器与云原生运维 — 面试参考答案

> 覆盖题单：Docker（20题）、K8s 100 道（101题）、云原生（21题）、公有云（16题）、边缘计算（16题），共 174 题

## Docker 容器运维面试题

### 1. 简述 Docker 核心实现原理？

**要点：**
- 三大内核机制：
  - **Namespace**：隔离视图——pid（进程）、net（网络栈）、mnt（文件系统挂载点）、uts（主机名）、ipc、user——每个容器看到独立的世界
  - **Cgroups**：资源限额——限制 CPU/内存/IO 用量（--memory、--cpus）
  - **UnionFS 联合文件系统**（overlay2）：镜像分层只读叠加，容器层可写（写时复制 COW——改文件先从镜像层拷到容器层再改）
- 容器 = **受限视图 + 受限资源的普通进程**，由容器运行时（containerd→runc）创建

**一句话答：** Docker 没有魔法，本质是内核三件套：Namespace 负责隔离视野让容器以为自己是独立系统，Cgroups 负责限额防止一个容器吃光宿主机，OverlayFS 联合文件系统实现镜像分层和写时复制。所以容器就是被这三层约束的普通 Linux 进程。

### 2. 容器与虚拟机有什么区别？

**要点：**
- **隔离层级**：VM 虚拟化整套硬件+独立内核（Guest OS）；容器共享宿主内核，只隔离视图
- **体量**：VM 以 GB 计、启动分钟级；容器镜像以 MB 计、启动秒级
- **密度**：同硬件容器密度远高于 VM；**开销**：容器近乎无虚拟化损耗，VM 有 hypervisor 开销
- **隔离性**：VM 强（内核都独立）；容器弱（共享内核，内核漏洞可能逃逸）——强隔离要求用 VM/Kata/Firecracker
- 互补关系：VM 管安全边界，容器管交付密度；云上常见 VM 里跑容器

**一句话答：** 虚拟机虚拟硬件带完整 Guest OS，重但隔离彻底；容器共享宿主内核只隔离视图，轻到秒起秒删、同机高密度。代价是隔离性弱——内核漏洞就可能逃逸，所以多租户强隔离场景会套 VM 或用 Kata 这类轻量虚机。实际架构是两者叠加：物理机或 VM 之上跑容器编排。

### 3. Docker 存储引擎有什么作用？

**要点：**
- 存储引擎 = 联合文件系统实现：把**多个只读镜像层 + 一个可写容器层**叠加成容器看到的统一文件系统
- 作用：镜像分层共享（多层镜像同一文件只存一份，省磁盘）、写时复制（容器改文件才复制副本）、快速创建容器（不复制整个镜像）
- 镜像分层元数据：每层有 diff 目录和元信息，pull 时只下载本地没有的层

**一句话答：** 存储引擎负责"分层叠加"：镜像各层只读、容器一个可写层，联合视图给进程看。价值三点——分层让镜像和层文件全局共享省空间，写时复制让新容器秒开，层共享让 pull 增量下载。

### 4. Docker 支持哪些存储引擎？

**要点：**
- **overlay2**：现行标准，性能好、支持页缓存共享，所有主流内核（4.x+）默认
- 旧引擎（了解即可）：aufs（历史默认，已淘汰）、devicemapper（RHEL 老内核方案，已废弃）、btrfs、zfs、vfs（无分层，性能差，兜底用）
- 查看当前引擎：`docker info | grep -i storage`
- 内核 5.x+ 基本不用纠结——都是 overlay2

**一句话答：** 记住 overlay2 一个就够——现代内核的默认标准，性能和稳定性都最优。aufs 和 devicemapper 是历史方案已淘汰，vfs 是无分层的兜底。docker info 里能看到当前用的是哪个。

### 5. Docker 有哪些核心组件及其作用？

**要点：**
- **docker CLI**：客户端，发命令
- **dockerd**（docker daemon）：守护进程，对外 API、管理镜像/容器/网络/卷
- **containerd**：容器生命周期管理（被 dockerd 调用，也是 K8s 运行时）
- **containerd-shim + runc**：真正创建容器进程（runc 按 OCI 规范启动）
- **镜像仓库**（Registry）：存镜像（Docker Hub、Harbor 私有仓库）
- 架构演进：K8s 1.24 弃用 dockershim 直连 containerd——排障时 crictl/ctr/docker 三种客户端的对应关系

**一句话答：** 链路是：docker 客户端发请求给 dockerd，dockerd 调 containerd，containerd 通过 shim 调 runc 按 OCI 规范拉起容器进程；镜像存在 Registry 里。理解这条链很重要——K8s 跳过 dockerd 直连 containerd 之后，排障用的客户端工具都变了。

### 6. Docker 网络模式有哪些？

**要点：**
- **bridge**（默认）：docker0 网桥 + veth pair + NAT 出网；容器间用内网 IP，--link 已废弃用自定义网络代替（带内置 DNS）
- **host**：容器直接用宿主网络栈——性能最好、无隔离；K8s 里通常禁用
- **container:<name>**：共享另一个容器的 netns（K8s pause 容器的原理）
- **none**：无网络，自定义场景
- **overlay / macvlan**：跨主机方案（swarm overlay、直接给容器 MAC）
- 端口映射 -p 8080:80 走 iptables DNAT

**一句话答：** 五种模式：默认 bridge 用网桥加 NAT，建议用自定义网络获得内置 DNS 服务发现；host 模式共享宿主栈性能最好但没隔离；container 模式共享别的容器的网络栈——K8s Pod 就是这么干的；none 无网络；跨主机用 overlay 或 macvlan。

### 7. 为什么容器内执行 free 命令看到的是宿主机内存？

**要点：**
- free 读的是 **/proc/meminfo**——宿主机全局信息，**不感知 cgroup 限额**；容器没自己的 meminfo
- 后果：容器限 512M，free 显示宿主 64G——JVM 等按"机器内存"调堆的应用会失控
- 正确姿势：
  - `cat /sys/fs/cgroup/memory/memory.limit_in_bytes`（cgroup v1）或 `/sys/fs/cgroup/memory.max`（v2）
  - 新版 coreutils 的 free 已支持 cgroup 感知；K8s 里看 `kubectl top pod`
- 同理：/proc/cpuinfo 也是宿主的，lscpu 看到的核数不可信

**一句话答：** 因为 free 读的 /proc/meminfo 是宿主机全局的，cgroup 的内存限额不体现在那里。容器里判断内存限额要读 /sys/fs/cgroup 下的文件，K8s 里直接 kubectl top。这个坑的经典受害者是 JVM——老版本不感知容器限额会按宿主机内存算堆大小，OOM 收场。

### 8. 容器网络是怎么实现的？

**要点：**
- bridge 模式下的组装：
  1. docker0 Linux 网桥（容器们的二层交换机）
  2. 每个容器一对 **veth pair**——一端在容器 netns 里（eth0），一端插在 docker0 上
  3. 容器内配 IP（docker0 同网段）和默认路由指向 docker0
  4. 出网：经过 docker0 → 宿主机 → **iptables SNAT/MASQUERADE** 改源 IP 出去；入站 -p 端口映射走 **DNAT**
- 自定义网络额外有嵌入式 DNS（127.0.0.11）做容器名解析
- 验证：`ip link` 宿主机上能看到 vethxxx；`iptables -t nat -L` 看 DNAT 规则

**一句话答：** 单机 bridge 网络就是"网桥加 veth 网线"：每个容器一条 veth pair 一头插在自己网络命名空间、一头插在 docker0 网桥上，出网靠 iptables 的 SNAT，外部访问靠 -p 的 DNAT 端口映射。自定义网络再加个内置 DNS 按容器名解析——这就是 K8s Pod 网络的原型。

### 9. Docker 如何实现数据持久化？

**要点：**
- 容器可写层：随容器删除而**消失**——不能持久化
- 两种持久化方式：
  1. **volume**（推荐）：docker 管理的存储区（/var/lib/docker/volumes/），`docker run -v mydata:/data`；生命周期独立于容器，支持驱动（本地/NFS/云盘）
  2. **bind mount**：`-v /host/path:/container/path` 挂宿主目录——开发挂代码常用；注意权限和 SELinux（:z 标志）
- tmpfs mount：内存挂载，敏感临时数据
- 容器/镜像里改挂载点的行为差异、volume 备份方法（--rm -v 挂进临时容器打 tar）

**一句话答：** 容器可写层随删除蒸发，持久化靠 volume 和 bind mount 两条路：volume 是 docker 自己管理的卷，生命周期独立，生产首选；bind mount 直接挂宿主目录，开发环境挂代码方便但要小心权限和 SELinux。数据库类容器必须用卷，否则重启数据就没。

### 10. 容器内 root 用户和宿主机 root 用户有什么关系？

**要点：**
- 默认（无 user namespace）：**同一个 root**——uid 0 就是宿主的 root，容器内 root 写宿主挂载目录、操作宿主设备都是真 root 权限（容器逃逸的高危面）
- 安全加固：
  - **user namespace 重映射**：容器 uid 0 映射到宿主普通 uid（如 100000）——隔一层
  - **容器内降权**：USER 指令非 root 运行 + --cap-drop ALL 按需加 capability
  - **rootless Docker/Podman**：整个 daemon 非 root 跑
- K8s 对应：Pod SecurityContext（runAsNonRoot、readOnlyRootFilesystem）与 PSA 策略

**一句话答：** 默认就是同一个 root——容器里 uid 0 就是宿主 uid 0，这就是容器安全问题严重的根源。加固三招：开 user namespace 把容器 root 映射成宿主普通用户，镜像里 USER 降权加 cap-drop，或直接用 rootless 运行时。面试能说出"默认同 root"这一句就及格，能给出 user namespace 映射方案就是加分。

### 11. 如何实现跨主机的容器通信？

**要点：**
- 方案族：
  1. **Overlay 网络**（VXLAN 封装）：Docker swarm overlay、K8s Flannel VXLAN 模式——跨主机二层互通，有封装开销
  2. **路由方案**（无封装）：Calico BGP——把容器网段路由宣告到物理网络，性能接近裸机，要求网络设备支持
  3. **端口映射/主机网络**：服务级跨主机（-p + 走宿主 IP）——不解决容器 IP 直通
  4. **macvlan**：容器直接拿物理网段 IP，宿主容器间被交换机隔离的坑（父接口 ARP 问题）
- K8s 环境这层由 **CNI 插件**统一负责（Flannel/Calico/Cilium）
- 选型：简单小集群 Flannel VXLAN，性能敏感物理网络可控 Calico BGP，大规模+可观测 Cilium

**一句话答：** 主流两条路：Overlay 路线用 VXLAN 把容器报文封装在宿主 UDP 里跨网传输，Flannel 和 swarm 默认方案，简单但有封包开销；路由路线用 BGP 把容器子网宣告进物理网络，Calico 代表，性能好但要求网络可管。在 K8s 里这一层标准化成了 CNI 接口，换插件不改应用。

### 12. 容器挂载宿主机上目录后，提示权限不足怎么解决？

**要点：**
- 根因：容器内进程的 **UID 与宿主目录属主不匹配**（镜像里 app 用户 uid 1000，宿主目录属 root）——Linux 权限按 uid 判定，跟用户名无关
- 解法按优先级：
  1. `chown -R 1000:1000 /host/dir`（对齐 uid）
  2. 容器以宿主目录属主 uid 运行：`docker run --user $(id -u):$(id -g)`
  3. SELinux 系统：`-v /host/dir:/data:z`（自动打标签）或 chcon
  4. 开发环境暴力法 chmod 777（不推荐生产）
- K8s 场景：fsGroup 字段自动修正挂载卷属组

**一句话答：** 本质是 uid 不匹配——容器里的用户和宿主目录属主不是同一个数字身份。对齐 uid 是正解：chown 目录或者让容器 --user 用宿主目录属主的 uid 跑；SELinux 机器还要给挂载打 :z 标签；K8s 里用 fsGroup 自动处理属组。

### 13. 为什么建议容器运行单个应用？

**要点：**
- **生命周期一致**：容器 PID 1 挂=容器挂，单应用让"进程健康"等于"服务健康"——健康检查和重启才有意义
- **镜像职责单一**：依赖少、体积小、漏洞面小、可缓存复用
- **横向扩容按需**：一个容器一个服务，扩 Web 不用连 MQ 一起扩
- **日志与监控清晰**：一个容器一个服务日志，不出多进程日志混杂
- 反例：SSH+应用+crond 塞一容器——僵尸进程无人收（PID 1 问题）、重启粒度粗、监控失真；需要 init 进程用 tini/dumb-init 兜底

**一句话答：** 核心是让容器边界等于服务边界：PID 1 就是应用本身，进程挂容器挂，健康检查才真实；扩容按服务扩，日志按服务收。把 SSH 和 crond 都塞进来，看似省事实则重启粒度、监控、僵尸进程全是坑——真有多进程需求，用 tini 当 PID 1 管理子进程。

### 14. 容器的健康检查机制有什么作用？

**要点：**
- 作用：**让平台知道容器"活着且能服务"**——进程在≠服务正常（死锁、假死）
- Docker：HEALTHCHECK 指令（CMD 探测，healthy/unhealthy 状态展示）
- K8s 三种探针（重点）：
  - **livenessProbe**：失败就**重启容器**——清除假死
  - **readinessProbe**：失败就**摘流量**（Endpoint 移除）——没准备好不接请求（启动慢/依赖故障时关键）
  - **startupProbe**：启动期专用——慢启动应用（JVM）避免被 liveness 误杀
- 实践要点：探测端点要轻量、探针参数（initialDelay/period/failureThreshold）按应用冷启动特性调、 readiness 与 liveness 分开配——共用一个猛端点会造成重启风暴

**一句话答：** 健康检查解决"进程在但服务死了"的假活问题。K8s 里三种探针各司其职：liveness 探测失败重启容器清假死，readiness 失败只摘流量不重启——给依赖故障的应用留恢复时间，startup 保护慢启动应用不被误杀。配错了的典型事故是三个探针共用重接口，故障时触发重启风暴雪上加霜。

### 15. 容器内的时间与宿主机不一致，该如何解决？

**要点：**
- 先分清：**时钟偏移**还是**时区显示差异**
- **时区不一致**（最常见，差 8 小时）：镜像默认 UTC——挂载宿主时区文件 ` -v /etc/localtime:/etc/localtime:ro -v /etc/timezone:/etc/timezone:ro` 或容器内设 TZ 环境变量（Alpine 需装 tzdata）
- **时间真正漂移**：容器默认共享宿主内核时钟，正常不该漂；出现漂移多因宿主 NTP 异常或老内核/虚拟化环境的时钟同步问题——修宿主机时间同步（chrony）
- K8s：Pod 共享节点内核，同样优先统一节点层 chrony + 需要时挂载 localtime

**一句话答：** 大多数"时间不一致"其实是时区问题：镜像默认 UTC 比北京时间慢 8 小时，挂载 /etc/localtime 或设 TZ 环境变量即可。容器共享宿主内核时钟，真正的时间漂移很少见，出现就先查宿主机 NTP—— chrony 同步好宿主，容器自然对。

### 16. Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？

**要点：**
- **ENTRYPOINT**：容器的**固定主程序**——定义"这个容器生来干什么"
- **CMD**：默认参数/默认命令——易被 docker run 末尾的参数**整体覆盖**
- 组合拳：`ENTRYPOINT ["/app/start"]` + `CMD ["--config", "prod.conf"]`——run 时附加参数会**追加到 ENTRYPOINT 后替换 CMD**（默认参数可覆盖，主程序不可）
- 只有 CMD：run 后的参数直接替换 CMD
- shell 形式 vs exec 形式：exec 形式（JSON 数组）进程是 PID 1 收得到信号；shell 形式包一层 /bin/sh -c，信号到不了应用——**推荐 exec 形式**

**一句话答：** ENTRYPOINT 是不可变的主程序，CMD 是可被命令行替换的默认参数，两者组合实现"固定程序+可调参数"。另一个高频坑是 shell 和 exec 两种写法：JSON 数组的 exec 形式才让应用收到 SIGTERM 优雅退出，shell 形式信号全被 sh 吞了。

### 17. Dockerfile 中 COPY 和 ADD 区别是什么？

**要点：**
- **COPY**：纯复制——本地文件→镜像，语义清晰
- **ADD**：复制+附加魔法：**自动解压本地 tar 包**、src 为 **URL** 时下载（下载不解压、不推荐——不如 RUN curl）
- 最佳实践：**一律 COPY**，仅"必须自动解压 tar"这一种场景用 ADD——可预期性优先
- 二者都支持 --chown、多阶段构建中的跨阶段 COPY（--from=builder）

**一句话答：** COPY 只复制，ADD 多两个魔法：自动解压 tar 和支持 URL 下载。工程上默认用 COPY——行为可预期；只有需要自动解压 tar 包的时候才用 ADD。URL 下载的用法别用，它不会解压还留缓存垃圾，不如 RUN curl 干净。

### 18. Dockerfile 中的多阶段构建是什么意思？

**要点：**
- 一个 Dockerfile 多个 FROM：**构建阶段**（装编译器/依赖编译出产物）→ **运行阶段**（只 COPY 编译产物+运行时依赖）
- 收益：**镜像瘦身**（编译工具链不进最终镜像——Go 从 1G 级到 20M 级）、攻击面缩小、CI 缓存友好
- 示例骨架：

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN go build -o /app/server

FROM alpine:3.19
COPY --from=builder /app/server /usr/local/bin/server
ENTRYPOINT ["server"]
```

- 变体：distroless/scratch 基础镜像进一步极简

**一句话答：** 多阶段构建就是把"编译"和"运行"拆成两个镜像：第一个阶段带着完整工具链编译出二进制，第二个阶段只拷产物加轻量运行时。镜像体积从上 GB 掉到几十 MB，攻击面同步缩小，是生产镜像的标准做法。

### 19. 编写 Dockerfile 有哪些最佳实践？

**要点：**
- **层缓存优化**：变动少的层在前（依赖安装），变动多的在后（COPY 源码）——依赖描述文件先 COPY 再装依赖
- **小基础镜像**：alpine/distroless/slim；一致性考虑 pinned 版本（不用 latest）
- **合并 RUN**（`&&`）减少层数、同层清理缓存（rm -rf /var/cache）
- **.dockerignore**：排除 .git、node_modules 防止构建上下文膨胀
- **多阶段构建**产出最终镜像（见上题）
- **安全**：非 root USER 运行、不硬编码密钥（用构建参数/运行时注入）、固定镜像 digest
- **可运维性**：exec 形式 ENTRYPOINT（信号处理）、暴露 EXPOSE 声明、合理的 HEALTHCHECK

**一句话答：** 我的心法是"层可缓存、镜像最小、进程可信号"：依赖文件先拷先装吃缓存，源码最后拷；基础镜像用 slim 或 distroless 并固定版本；RUN 合并清理；配 .dockerignore；多阶段构建收尾；非 root 运行加 exec 形式的 ENTRYPOINT。每一条都对应一个具体的坑。

### 20. 一台 Docker 服务器磁盘使用率超80%，你会怎么处理？

**要点：**
- **先看 Docker 自家占用**：`docker system df`（镜像/容器/卷/build cache 四类占用明细）
- 一键清理：`docker system prune -a --volumes`（**危险**：清未使用镜像+停止容器+卷——生产先去掉 -a 和 --volumes 分级执行）
- 分项清理：
  - 悬空镜像 `docker image prune`、旧镜像 `docker image prune -a`
  - 退出的容器 `docker container prune`
  - 构建缓存 `docker builder prune`（CI 机器大头）
  - 日志膨胀：`du -sh /var/lib/docker/containers/*/*-json.log`——**json-log 无限膨胀**是经典问题，log-driver 配 max-size/max-file，或改 journald
  - 卷：`docker volume ls -f dangling=true` 确认后清
- **根治**：log rotation 配置、CI 机器定期清理任务、镜像仓库定期清旧 tag、监控磁盘水位告警

**一句话答：** 先 docker system df 看占用构成，大头通常是三个：构建缓存 builder prune、悬空和旧镜像 image prune、容器日志——/var/lib/docker 下 json-log 无限膨胀是老毛病，要配 log-opts 的 max-size。一键 prune 是止血药，生产执行前先看清 --volumes 别误删数据卷；根治靠日志轮转配置加定时清理任务。

## K8s 容器运维面试题 100 道

### 1. K8s 有哪些应用场景？

**要点：**
- **应用编排托管**：无状态服务部署/弹性伸缩/自愈（主流场景）
- **CI/CD 落地平台**：滚动更新、灰度/金丝雀、回滚
- **微服务基础设施**：服务发现、负载均衡、流量治理
- **批处理/定时任务**：Job/CronJob 替代 crontab 集群化
- **AI/大数据负载**：GPU 调度、Spark/Flink on K8s
- **边缘**：K3s/KubeEdge 管理边缘节点

**一句话答：** 核心场景是容器化应用的编排托管——自动调度、自愈、弹性伸缩；往外延伸是微服务运行底座、CI/CD 的发布平台、Job 定时任务、GPU 调度和边缘集群管理。一句话：凡是需要"一堆机器协同跑一堆服务"的地方都是它的场景。

### 2. 简述 K8s 核心组件及作用？

**要点：**
- **控制平面**：
  - **kube-apiserver**：唯一入口，认证/鉴权/准入，所有组件都跟它通信
  - **etcd**：分布式 KV，存集群全部状态（唯一有状态的核心组件）
  - **kube-scheduler**：调度——决定 Pod 落在哪个节点
  - **kube-controller-manager**：各种控制器（Deployment/Node/Job...），维持期望状态
- **节点组件**：
  - **kubelet**：节点代理，管理 Pod 生命周期、上报节点状态
  - **kube-proxy**：Service 的转发实现（iptables/IPVS 规则）
  - **容器运行时**：containerd（CRI 接口）
- 记忆法：apiserver 是大门，etcd 是账本，scheduler 是分活儿的，controller 是监工，kubelet 是工头，proxy 修路

**一句话答：** 控制面四件套：apiserver 是唯一入口做认证鉴权准入，etcd 存全部集群状态，scheduler 决定 Pod 去哪个节点，controller-manager 用各种控制器把实际状态往期望状态拉。节点上三件套：kubelet 管 Pod 生命周期，kube-proxy 实现 Service 转发，containerd 跑容器。所有组件只和 apiserver 说话，数据只有 etcd 一份。

### 3. K8s 集群如何实现高可用？

**要点：**
- **控制平面高可用**：
  - apiserver 无状态 → 多实例 + LB（VIP/SLB/keepalived）前置
  - etcd 有状态 → **3/5 节点奇数 quorum**（raft，多数派存活即可用）
  - scheduler/controller-manager 多实例选主（leader election）
- **节点高可用**：应用多副本 + 反亲和打散（podAntiAffinity/topologySpreadConstraints）+ PDB 保障滚动与驱逐的下限
- **接入高可用**：Ingress 多副本、externalTrafficPolicy 考量
- **数据高可用**：etcd 定期备份（velero/etcdctl snapshot）
- 云托管：控制面托管（ACK/EKS）天然 HA

**一句话答：** 分层做：控制面 apiserver 多实例前面挂 LB，etcd 奇数节点三或五台靠 raft 保活，scheduler 和 controller 靠选主多活；节点层应用多副本加反亲和打散跨节点；再加定期 etcd 备份兜底。记住原则：无状态组件堆副本，有状态组件靠共识协议，最后一切靠备份防极端。

### 4. Pod 解决了什么问题？

**要点：**
- Pod = **一组共享资源、强关联容器的组合**：共享网络（同一 netns，互通 localhost）、可共享存储卷、共享 IPC
- 解决的问题：
  1. **超亲密容器组合**：主容器+边车（日志收集、代理、指标导出）——同生共死、同机调度
  2. **端口冲突规避**：共享网络栈但内部各占端口
  3. 抽象出"逻辑主机"：调度、缩扩容、管理以 Pod 为单位
- pause 容器：持有 netns，让业务容器重启不丢网络
- 对照：Docker 的 --network=container 就是 Pod 原型

**一句话答：** Pod 解决"超亲密容器"的管理问题：几个容器要同生共死、共享网络和存储——比如主应用加日志边车。K8s 把它们打包成 Pod 统一调度统一管理，内部走 localhost 互通，由 pause 容器持有网络命名空间保证业务容器重启不丢 IP。

### 5. K8s 有哪些工作负载资源？

**要点：**
- **Deployment**：无状态应用，滚动更新/回滚（最常用）
- **StatefulSet**：有状态应用——稳定网络标识（pod-0/1/2）、稳定存储（PVC 模板）、有序部署扩缩
- **DaemonSet**：每个节点跑一个——日志采集、监控 agent、CNI 组件
- **Job**：一次性任务；**CronJob**：定时任务
- **ReplicaSet**：副本维持（被 Deployment 管理一般不直接用）
- 其他：ReplicationController（废弃）、裸 Pod（测试用）

**一句话答：** 按场景背：无状态服务 Deployment，有状态服务 StatefulSet，每节点一个的 agent 用 DaemonSet，跑一次的任务 Job，定时任务 CronJob。ReplicaSet 是 Deployment 底下的副本控制器，一般不直接写。

### 6. 简述创建一个 Pod 的工作流程？

**要点：**
1. kubectl 提交 Pod 清单 → **apiserver** 认证/鉴权/准入 → 写入 **etcd**
2. **Scheduler** watch 到未调度 Pod → 预选（过滤不满足的节点：资源/亲和/污点）→ 优选（打分：均衡度/镜像局部性）→ **绑定节点**（写回 apiserver）
3. 对应节点的 **kubelet** watch 到分配给自己的 Pod → 调 **CNI** 配网络 → 调 **CRI**（containerd）→ 拉镜像创建容器
4. kubelet 上报状态 → apiserver → etcd；后续探针/自愈由 kubelet 持续执行
- 全程是"**声明式 + watch/list 控制循环**"——没有组件互相调用，都 watch apiserver

**一句话答：** 流程是一条 watch 链：kubectl 提交到 apiserver 存进 etcd，scheduler 看到未绑定的 Pod 经过预选优选把它绑到节点，该节点的 kubelet 看到 Pod 后调 CNI 配网络、CRI 起容器，状态再回写 apiserver。核心设计是声明式控制循环——组件之间不直接调用，全靠 watch apiserver 各干各的。

### 7. Pod 有哪几种重启策略及应用场景？

**要点：**
- **Always**（默认）：容器退出就重启——长期运行服务（Deployment 只支持 Always）
- **OnFailure**：非 0 退出才重启——Job 任务，失败重试成功不重跑
- **Never**：不重启——调试场景、一次性任务要保留现场
- 注意：重启是 kubelet 在**节点本地重启容器**（不是重建 Pod）；容器重启有**退避延迟**（10s/20s/40s...最长 5 分钟）
- CrashLoopBackOff 就是退避机制的体现——排查看日志而不是狂删 Pod

**一句话答：** 三种：Always 服务类默认，死了就拉起；OnFailure 给 Job 用，成功退出不重跑；Never 留现场调试用。细节点：这是 kubelet 在本机重启容器，失败次数多了有指数退避——Pod 状态里的 CrashLoopBackOff 就是退避等待期，看到它应该去查容器日志而不是反复删除重建。

### 8. Pod 有哪几种探针（健康检查）及应用场景？

**要点：**
- **livenessProbe** 存活探针：失败 → **重启容器**——检测死锁/假死
- **readinessProbe** 就绪探针：失败 → **从 Service Endpoint 摘除**（不接流量）——启动预热、依赖故障时暂停接客
- **startupProbe** 启动探针：成功前**屏蔽其他探针**——慢启动应用（JVM/大镜像）防被误杀
- 探测方式：httpGet（状态码）、tcpSocket（端口通）、exec（命令退出码）、grpc
- 参数：initialDelaySeconds、periodSeconds、timeoutSeconds、failureThreshold
- 经典配置错误：探针路径太重（压垮应用）、阈值太敏感（网络抖动就重启风暴）

**一句话答：** 三种探针三件事：liveness 失败重启容器清假死，readiness 失败摘流量不重启，startup 给慢启动应用一个缓冲期屏蔽前两者。探测方式有 HTTP、TCP、exec。配探针的原则是端点必须轻量、阈值宁宽勿严——liveness 配猛了，故障时就是重启风暴。

### 9. Pod 有哪些状态及其原因？

**要点：**
- **Pending**：未调度（资源不足/亲和不满足/污点）或镜像拉取中
- **Running**：运行中（可能内部已崩，配探针才有意义）
- **Succeeded/Failed**：Job 类容器正常退出/异常退出
- **Unknown**：节点失联（kubelet 断连）
- **CrashLoopBackOff**：容器反复崩溃+退避等待——日志必查
- **ImagePullBackOff/ErrImagePull**：镜像拉取失败——名字打错/仓库认证/网络
- **Evicted**：节点资源不足被驱逐（磁盘/内存压力）
- **Terminating**：删除中——卡住查 finalizer/节点失联

**一句话答：** 高频异常五连：Pending 查调度事件——通常是资源不够或亲和冲突；ImagePullBackOff 查镜像名和仓库凭证；CrashLoopBackOff 查容器日志——应用起不来；Evicted 是节点磁盘或内存压力驱逐；Terminating 卡住查 finalizer。排障入口永远是 `kubectl describe pod` 的 Events 段。

### 10. 初始化容器有哪些应用场景？

**要点：**
- Init 容器：**按序执行、全部成功才启动主容器**的先行容器
- 场景：
  1. **等待依赖**：等 MySQL/Redis 可用（探测循环）再启动主应用
  2. **初始化数据**：改配置、下载配置文件/模型、注册服务
  3. **权限分离**：init 以 root 跑特权初始化，主容器降权——安全最佳实践
  4. 延迟启动大应用给 sidecar 时间就绪
- 特性：失败按 restartPolicy 重试；每个 init 容器必须成功结束才能下一个

**一句话答：** Init 容器是主容器的前置工序，按顺序全过了主容器才启动。三大用法：等依赖就绪——数据库没起来主应用先等着；做初始化——下配置下模型；权限隔离——root 干特权活，主容器降权跑。这比在应用代码里写"等待重试"逻辑优雅得多。

### 11. Pod 超出资源限制时，K8s 会做什么动作？

**要点：**
- 先分清 requests/limits 的语义：requests 影响调度（节点按 requests 累计分配），limits 是运行时上限（cgroup）
- **CPU 超 limit**：**不杀**，cgroup CFS 限流（throttle）——CPU 是可压缩资源，表现为延迟升高、CPU 使用率被压在 limit 上（监控指标 container_cpu_cfs_throttled）
- **内存超 limit**：**不可压缩**——超限触发 **OOMKilled**（退出码 137），容器按重启策略重启；反复 OOM = CrashLoopBackOff
- **节点内存紧张**：kube-eviction 按 QoS 等级驱逐——**Guaranteed**（requests=limits）最安全 > Burstable > **BestEffort**（不设 requests/limits）最先被杀
- 节点 OOM（内核级）也一样按 oom_score 选杀——K8s 尽量让关键进程 oom_score_adj 低

**一句话答：** CPU 和内存待遇完全不同：CPU 是可压缩资源，超 limit 只是限流变慢不杀进程；内存不可压缩，超 limit 直接 OOMKilled 退出码 137。节点整体内存紧张时按 QoS 驱逐——requests 等于 limits 的 Guaranteed 最安全，什么都不设的 BestEffort 最先牺牲。

### 12. Pod 处于 Pending 状态可能是什么原因？

**要点：**
- **调度不出去**（describe 看 FailedScheduling）：
  1. 资源不足：CPU/内存 requests 超过所有节点余量（最常见）
  2. 亲和/反亲和、nodeSelector 匹配不到节点
  3. 节点污点无容忍（如 master 打了 NoSchedule）
  4. PDB/拓扑约束限制
- **镜像拉取慢**：大镜像下载中
- **PVC 未绑定**：存储类不可用/等待 PV
- 排查入口：`kubectl describe pod xxx` 看 Events；`kubectl get events --sort-by=.lastTimestamp`

**一句话答：** Pending 就是"没跑起来"，describe 的 Events 段直接给答案：FailedScheduling 是调度失败——资源不足、亲和规则太严、污点没容忍三类；还有镜像在慢慢拉、PVC 没绑定两种。九成以上 Pending 都能在 Events 里找到明确原因。

### 13. 简述删除一个 Pod 的工作流程？

**要点：**
1. kubectl delete → apiserver 标记 Pod **deletionTimestamp**（grace period 默认 30s）
2. Endpoint controller 把 Pod **从 Service 摘除**（Endpoint 移除）
3. **kubelet** 收到删除 → 执行**优雅终止**：给容器发 **SIGTERM**（preStop hook 先执行——应用排水已有连接）
4. 等待容器退出；超时未退 → **SIGKILL** 强杀
5. 容器全退 + finalizer 清完 → 从 etcd 删除记录
- 关键点：preStop + readiness 联动实现**零流量丢失**（sleep 几秒让 LB/客户端连接池刷新）
- force delete（--grace-period=0 --force）绕过优雅期——节点失联时才用，有数据风险

**一句话答：** 删除 Pod 是优雅终止流程：apiserver 打上删除标记，先从 Service 摘除不再接新流量，kubelet 给容器发 SIGTERM 让应用排水收尾，宽限期默认 30 秒，超时 SIGKILL。生产要配 preStop sleep 几秒，让上游连接池感知摘除——这是滚动更新不丢请求的关键一环。

### 14. K8s 出现大量 Pod 处于 Evicted 状态是什么原因？

**要点：**
- Evicted = kubelet 的**节点压力驱逐**：节点资源（磁盘/内存/inode/pid）触达驱逐阈值，kubelet 按 QoS 优先级批量驱逐 Pod
- 高频根因：**磁盘写满**（容器日志、emptyDir、镜像垃圾）——大多数"突然一堆 Evicted"是磁盘；节点内存压力次之
- 特点：被驱逐的 Deployment Pod 会重建，但若节点压力没解除 → 重建后又 Evicted → **循环**；裸 Pod 不会重建
- 处理：
  1. `kubectl describe node` 看 Conditions（DiskPressure/MemoryPressure）和驱逐信号
  2. 清节点：日志清理、镜像 GC、大文件定位
  3. 给 Pod 配 requests/limits（BestEffort 最先被杀）
  4. 长期：日志轮转、emptyDir sizeLimit、节点磁盘容量规划、告警前置

**一句话答：** 大量 Evicted 基本是节点资源压力驱逐，头号元凶是磁盘——容器日志和镜像把盘写满，kubelet 触发 DiskPressure 开始清人。Deployment 的 Pod 会被重建，但压力不解除就陷入"建了又赶走"的死循环。处理先 describe node 看哪个压力信号亮了，清磁盘或清内存，再给 Pod 补上资源请求让驱逐有优先级。

### 15. Deployment 滚动更新是怎么实现的？

**要点：**
- 本质：Deployment 通过**新旧两个 ReplicaSet** 的副本数此消彼长实现滚动
- 流程（maxSurge=1, maxUnavailable=0 为例）：新建 1 个新 RS Pod → ready 后旧 RS 减 1 → 循环直到全量
- 控制参数：
  - `maxSurge`：最多**超出**期望副本数几个（控制"多开多少"）
  - `maxUnavailable`：最多**少**几个可用（控制"最少保底"）
  - 默认 25%/25%
- 版本记录：revisionHistoryLimit 保留旧 RS 用于回滚（kubectl rollout undo）
- 优雅更新的配套：readinessProbe（新 Pod 就绪才接流量）+ preStop（旧 Pod 排水）

**一句话答：** Deployment 滚动更新靠新旧两个 ReplicaSet 副本数互相拉扯：maxSurge 控制最多多开几个新 Pod，maxUnavailable 控制最少保住几个旧 Pod，一升一降直到全量替换。每一步新 Pod 必须 readiness 探针通过才继续，旧 Pod 走 preStop 排水。旧 ReplicaSet 保留着就是回滚的依据。

### 16. Deployment 如何控制滚动更新的快慢？

**要点：**
- 两个旋钮（百分比或整数）：
  - `maxSurge`：允许超出的副本数——越大，同时启动的新 Pod 越多，**越快**
  - `maxUnavailable`：允许不可用数——越大，旧 Pod 删得越狠，**越快**但可用性越低
- 快慢组合：
  - 稳妥：maxSurge=1, maxUnavailable=0（永远不降可用数，逐个替换）
  - 激进：maxSurge=100%, maxUnavailable=50%（大批量换）
- 其他影响节奏的：探针 initialDelay/period（新 Pod 就绪判定耗时）、minReadySeconds（新 Pod 需保持 ready 多久才算数）、preStop 时长
- 数据库类走 StatefulSet 的分区更新（partition）更可控

**一句话答：** 快慢由 maxSurge 和 maxUnavailable 两个参数的松紧决定：都设大更新猛但可用性波动大，maxSurge=1 配 maxUnavailable=0 就是一个一个稳着换。另外 minReadySeconds 和探针节奏也影响实际速度——新 Pod 要 ready 多久才算数。

### 17. Deployment 与 ReplicaSet 有什么联系？

**要点：**
- **ReplicaSet**：保证"指定副本数的同名 Pod 活着"——纯粹的副本控制器
- **Deployment**：**管理 ReplicaSet 的上层**——每次模板变更创建**新 RS**，通过新旧 RS 副本数调整实现滚动更新与回滚
- 关系：用户只操作 Deployment → Deployment 控制器操作 RS → RS 控制 Pod——三层控制循环
- 实践：不要手动改 RS/Pod（会被拉回期望状态）；kubectl rollout history 看到的就是 RS 列表

**一句话答：** RS 只管副本数，Deployment 在上面管 RS：每次改镜像就建一个新 RS，通过新旧 RS 的副本数增减完成滚动，旧 RS 留着当回滚点。所以运维只操作 Deployment，手动改 RS 或 Pod 会被控制循环打回原形。

### 18. Deployment 与 StatefulSet 有什么区别？

**要点：**
- **Deployment**：Pod 是**无身份 cattle**——随机名、无序、可互换；适合无状态服务
- **StatefulSet**：Pod 有**稳定身份**：
  1. **稳定网络标识**：pod-0/1/2 固定域名（配 Headless Service）——重启不换名
  2. **稳定存储**：每个 Pod 独立 PVC 模板，重建后**重新挂回原卷**——数据跟着身份走
  3. **有序性**：按序部署/删除/扩缩（pod-0 就绪才起 pod-1）
- 适用：数据库（MySQL/PX）、MQ（Kafka/ZK）、需要主从身份的服务
- 更新策略：RollingUpdate（支持 partition 灰度）/OnDelete

**一句话答：** 核心区别是"有没有身份"：Deployment 的 Pod 随生随灭可互换，StatefulSet 的 Pod 有固定名字、固定存储、有序启停。数据库和 MQ 必须用它——pod-0 是主、pod-1 是从这种拓扑依赖稳定身份，重建后数据卷还得挂回原来那个。配套一定有 Headless Service。

### 19. StatefulSet 为什么用 Headless Service？

**要点：**
- Headless Service（clusterIP: None）：**不做负载均衡、不分配 VIP**，DNS 直接解析出**每个 Pod 的独立 A 记录**
- StatefulSet 需要的是**点名访问**：mysql-0.mysql.ns.svc 是主、mysql-1 是从——客户端/组件要按名字精确连到某个 Pod
- 普通 Service 是 VIP+随机转发——"找任何一个实例"，满足不了主从拓扑
- Pod 域名格式：`<pod>.<svc>.<ns>.svc.cluster.local`
- 客户端驱动（如 Kafka/ZK/ES）都依赖这种稳定域名做节点发现

**一句话答：** Headless Service 没有 VIP，DNS 直接返回每个 Pod 各自的地址——这是为了"点名"。有状态服务需要精确连接 pod-0 还是 pod-1，主从拓扑不能被负载均衡随机转发；普通 Service 的 VIP 模式只适合"随便哪台都行"的无状态场景。

### 20. Service 有哪些功能？

**要点：**
- **服务发现**：稳定的 ClusterIP/DNS 名（svc.ns.svc.cluster.local）——屏蔽 Pod IP 动态变化
- **负载均衡**：一组 Pod 间的流量分发（kube-proxy 规则，rr 语义）
- **自动摘除**：readiness 探针失败/ Pod 删除 → Endpoint 自动更新
- **多端口/协议**：一个 Service 映射多个端口（TCP/UDP/HTTP）
- **对外暴露**：NodePort/LoadBalancer 类型（下题）
- 本质：Service 是**虚拟 IP + 转发规则的抽象**，实现在 kube-proxy（不在任何 Pod 上）

**一句话答：** Service 做三件事：给一组动态的 Pod 一个稳定的 DNS 名和虚拟 IP——服务发现；在这组 Pod 之间做负载均衡——流量分发；跟着探针和 Pod 生命周期自动增删后端——健康摘除。它是纯规则抽象，实现在 kube-proxy 的 iptables/IPVS 里，不占任何 Pod。

### 21. Service 有哪几种公开类型及应用场景？

**要点：**
- **ClusterIP**（默认）：集群内虚拟 IP——内部服务互调
- **NodePort**：每节点开端口（默认 30000-32767）——简单对外/开发测试；缺点：端口管理乱、流量二次转发
- **LoadBalancer**：云厂商 LB 直通 Service——生产对外标准方式（云上自动建 SLB/ELB）；裸机可用 MetalLB 实现
- **ExternalName**：DNS CNAME 别名——把外部服务映射成集群内名字
- **Headless**（clusterIP: None）：不分配 IP，DNS 直出 Pod——StatefulSet/客户端自均衡（gRPC）
- 演进路径：ClusterIP → NodePort（测试）→ LoadBalancer（生产）→ Ingress/Gateway（七层统一入口）

**一句话答：** 五种类型按暴露程度排：ClusterIP 只给集群内部用；NodePort 在每个节点开个高位端口，测试够用生产难管；LoadBalancer 对接云 LB 是生产对外的标准姿势；Headless 不要 VIP 直出 Pod DNS，给有状态服务用；ExternalName 就是个 DNS 别名。对外七层路由统一走 Ingress，这是另一个维度。

### 22. kube-proxy 有几种代理模式及原理？

**要点：**
- **iptables 模式**（默认）：为每个 Service 写 iptables 规则链——DNAT 随机选后端；规则线性匹配，**Service/Pod 数量大时规则更新慢、匹配开销大**
- **IPVS 模式**：内核 **LVS/IPVS** 哈希表实现——O(1) 查找、真实负载均衡算法（rr/lc/sh）、大规模集群（上千 Service）性能好；`mode: ipvs`
- **userspace**（历史）：流量进 kube-proxy 进程转发——性能差已淘汰
- **ebpf**（非 kube-proxy）：Cilium 直接 eBPF 转发，替代 kube-proxy（进阶选项）
- 验证：`kubectl get cm kube-proxy -n kube-system` 看 mode；节点 `ipvsadm -Ln` 看规则

**一句话答：** 三个模式按时代排：userspace 走进程转发早淘汰了；iptables 用规则链 DNAT，简单但规则一多线性匹配就慢；IPVS 用内核哈希表加真实 LB 算法，几千个 Service 依然稳，是大规模集群的标准选择。还有第四条路是 Cilium 直接用 eBPF 干掉 kube-proxy。

### 23. Endpoint 资源有什么作用？

**要点：**
- **Endpoint/EndpointSlice**：记录 Service 对应的**真实后端 Pod IP 列表**——Service（虚拟）与 Pod（实际）之间的桥梁
- 维护者：EndpointSlice 控制器持续对齐"selector 匹配的、**ready 的** Pod"——Pod 上下线自动增删
- 运维用途：
  - 排查 Service 不通：`kubectl get endpoints svc` 为空 = selector 不匹配/无 ready Pod（**高频坑：selector label 打错**）
  - EndpointSlice 分片（默认每片 100）优化大规模分发
- 手工 Service（无 selector）：手动维护 Endpoint 指向集群外服务

**一句话答：** Endpoint 是 Service 的"后端名单"：控制器把 selector 匹配到且探针 ready 的 Pod IP 填进去，流量按这份名单转发。排障用法很实用——Service 不通先看 endpoints 是不是空的，空了九成是 label 写错或探针全挂。

### 24. K8s 集群安装的网络插件有什么作用？

**要点：**
- K8s 不自带 Pod 网络——**CNI 插件**负责：
  1. **IP 分配**：给每个 Pod 唯一 IP（节点内网段/全局网段）
  2. **跨节点互通**：实现"所有 Pod 同一平面、直接 IP 互访"（不加 NAT）——Overlay 封装或 BGP 路由
  3. **NetworkPolicy 支持**：Pod 级访问控制（需插件实现）
- 主流：**Flannel**（简单，VXLAN）、**Calico**（BGP 路由+NetworkPolicy 强）、**Cilium**（eBPF，性能+可观测）、云上自研（Terway/VPC-CNI）
- 没装 CNI 的直接症状：所有 Pod 卡 Pending，报 "no CNI plugin"

**一句话答：** 网络插件负责 K8s 的 Pod 网络：给 Pod 分 IP、打通跨节点通信、支持 NetworkPolicy。选型梯度：Flannel 简单省心，Calico 路由方案性能好策略全，Cilium 用 eBPF 性能和可观测都最强。集群裸装后 Pod 全 Pending 报缺 CNI，就是没装它的症状。

### 25. Calico 有哪几种工作模式及原理？

**要点：**
- **BGP 模式**：每个节点当路由器，把本节点 Pod 网段通过 **BGP** 宣告给其他节点/物理网络——报文**原样路由**（无封装），性能接近物理机；要求二层可达（IPIP 关闭）或反射器
- **IPIP 模式**（Calico 默认）：跨节点报文套一层 **IP 隧道**（IP in IP）——不要求底层网络支持 BGP，有少量封装开销
- **VXLAN 模式**：标准 VXLAN 封装——兼容性最好（穿透更多网络设备）
- **混合**：同子网走 BGP 直路由，跨子网走隧道
- 附加能力：NetworkPolicy 全实现、BGP 反射器大规模组网、和物理网络路由打通（ToR）

**一句话答：** Calico 的本质是把每个节点变成 BGP 路由器：纯 BGP 模式容器流量直接路由零封装性能最好，但要求网络能学路由；IPIP 和 VXLAN 是两种隧道封装，牺牲一点性能换部署兼容性，IPIP 是默认。生产选型看网络团队配合度——能跑 BGP 就 BGP，不能就隧道。

### 26. Service 与 Ingress 有什么区别？

**要点：**
- **Service**：**四层**（TCP/UDP）流量分发，ClusterIP/NodePort/LB 三种暴露方式
- **Ingress**：**七层**（HTTP/HTTPS）路由——按域名、路径把外部流量分发到不同 Service；功能：TLS 终止、路径改写、认证、限流（取决于 Controller）
- 关系：Ingress 规则的**后端还是 Service**——Ingress 定义规则，Ingress Controller（Nginx/Envoy 实现）执行
- 对比：一个 Service = 一个 LB 太贵；Ingress 统一入口，一个 LB 带全部域名——**成本与管理的平衡**
- 演进：Ingress → **Gateway API**（更清晰的角色分离，下下题）

**一句话答：** Service 是四层抽象管 TCP 分发，Ingress 是七层路由管域名和路径——把外部 HTTP 请求按规则导到各个 Service。关系上 Ingress 只是规则，真正干活的是 Ingress Controller。用 Ingress 的现实理由：不能每个服务都开个 LoadBalancer，统一入口一次 TLS 终止全站复用。

### 27. Ingress 与 Ingress Controller 的关系？

**要点：**
- **Ingress**：K8s 的**规则资源**（CRD 定义的路由表）——只是数据，不干活
- **Ingress Controller**：**执行者**——watch Ingress 资源，翻译成实际代理配置（Nginx conf/Envoy 配置）并重载生效
- 常见 Controller：**ingress-nginx**（Nginx）、HAProxy、**Traefik**、**Envoy Gateway**、云厂商 ALB Ingress
- 类比：Ingress 是 nginx.conf 里的 server 块，Controller 是"读配置+reload nginx"的程序
- 没装 Controller：Ingress 创建了也没用（常见新手坑）
- Controller 自身部署：DaemonSet（hostNetwork）或 Deployment+LB——它就是全站入口，要高可用

**一句话答：** Ingress 是路由规则资源，Ingress Controller 是执行规则的代理程序——前者是配置数据，后者是 watch 这些数据并生成 Nginx/Envoy 实际配置的进程。只建 Ingress 不装 Controller 等于没人看地图。Controller 本身是全站入口，必须自己先做到高可用。

### 28. Ingress 暴露的应用无法访问如何排查？

**要点：**
- 由外向内逐层：
  1. **DNS**：域名解析到哪了（dig）——对不对 Controller 的 LB IP
  2. **LB/防火墙**：LB 监听端口、安全组、证书
  3. **Ingress 资源**：`kubectl get ingress` 看 ADDRESS 是否有值（没值=Controller 没认领）、host/path 规则、TLS 段
  4. **Controller**：Pod 状态、日志（有没有"同步失败/证书错误"）、Service 暴露方式
  5. **后端 Service**：endpoints 是否为空（selector/探针）
  6. **网络策略**：NetworkPolicy 是否拦了 Controller → Pod
- 404 vs 502 vs 503 的指向不同：404=规则没匹配（host/path 写错）、502/503=后端问题、默认后端=规则缺失
- curl -H "Host: xxx" 直打 Controller IP 排除 DNS 因素

**一句话答：** 从外往里剥：DNS 解析对不对，LB 和安全组放没放行，Ingress 的 ADDRESS 有没有被 Controller 认领，规则里 host 和 path 写没写对，后端 Service 的 endpoints 空不空。用 curl 带 Host 头直打 Controller IP 能跳过 DNS 单测路由层。状态码也有指纹：404 是规则没命中，502 503 是后端的问题。

### 29. Ingress 后端应用无法获取客户端 IP 如何解决？

**要点：**
- 原因：流量经过多层代理，后端看到的 RemoteAddr 是**上一跳（Ingress）的 IP**
- 解法（nginx ingress 为例）：
  1. Controller 已默认注入 **X-Forwarded-For**（XFF）——应用从 XFF 取真实 IP；多级代理取 XFF 第一位
  2. `use-forwarded-headers` / `compute-full-forwarded-for` 配置链路信任
  3. 应用框架配置信任代理数（Spring 的 server.forward-headers-strategy、Express 的 trust proxy）
- **externalTrafficPolicy: Local**：NodePort/LB 场景不做 SNAT，保留源 IP 直达节点上的 Pod——代价是流量只落在有 Pod 的节点（需配合 LB 健康检查）
- 云上 Terway/VPC-CNI 直接挂 Pod IP 的方案无此问题

**一句话答：** 因为请求被代理过，后端 socket 里看到的永远是上一跳的 IP。两条路：标准做法是应用读 X-Forwarded-For 头并把框架配置成信任代理；进阶做法是 Service 设 externalTrafficPolicy 为 Local 让 kube-proxy 不做 SNAT——代价是流量只会打到有 Pod 的节点。

### 30. Ingress 环境提示上传文件过大怎么解决？

**要点：**
- 报错 413——默认 client_max_body_size 1m（ingress-nginx 默认 1m）
- ingress-nginx 解法：
  - 全局：ConfigMap（kube-system/nginx-configuration）加 `proxy-body-size: "100m"`
  - 单个 Ingress 注解：`nginx.ingress.kubernetes.io/proxy-body-size: "100m"`
- 全链路核对：应用框架（Spring max-file-size）→ Ingress → LB（云 SLB 自身体积上限）→ WAF——**每一层都要放开**
- 大文件配套：proxy_read_timeout 调大防上传中途超时

**一句话答：** 413 是 body 超 proxy-body-size，ingress-nginx 默认只有 1M，用注解 nginx.ingress.kubernetes.io/proxy-body-size 调大，或改全局 ConfigMap。别忘云 LB 和应用框架还有自己的上限，要整条链路一起核对，大文件再把超时也放宽。

### 31. 如何将 Pod 分配到指定节点上？

**要点：**
- 四种手段（按推荐度）：
  1. **nodeSelector**：简单 label 匹配（disk: ssd）
  2. **nodeAffinity**：表达式更强——required（硬性）/preferred（软性加权），支持 In/NotIn/Exists
  3. **污点与容忍**：节点"排斥"（taint）+ Pod 声明容忍——反向控制，适合专用节点
  4. **nodeName**：直接指定（绕过调度器，一般不用）
- 配套：Pod 间反亲和（podAntiAffinity）把副本打散、topologySpreadConstraints 拓扑均衡
- 原则：优先用亲和性软约束，nodeName 硬指定是调试手段

**一句话答：** 给 Pod 选节点四招：nodeSelector 最简单按 label 选；nodeAffinity 支持表达式还有软硬之分——required 强制、preferred 尽量；taint/toleration 反着来，节点设污点排斥，Pod 带容忍才能进，适合 GPU 专用节点；nodeName 直接点名不推荐。副本打散还要配反亲和。

### 32. K8s 调度器有哪些调度算法？

**要点：**
- 两阶段：
- **预选（Filter）**：硬性过滤——资源够不够（requests）、端口冲突、污点容忍、亲和规则、PV 拓扑、节点状况——淘汰不合格节点
- **优选（Score）**：对幸存节点**打分排序**——资源均衡度（LeastRequested/BalancedAllocation）、镜像本地性（ImageLocality）、Pod 拓扑分散、亲和偏好、自定义插件权重
- 高分节点胜出；同分随机
- 扩展机制：**调度框架（Scheduling Framework）**——自定义插件插进各阶段（如 GPU 拓扑感知调度）
- 特殊场景：抢占（低优先级 Pod 让位）、亲和互斥的批调度

**一句话答：** 调度分两步：预选是硬过滤——资源、污点、亲和不过关的直接出局；优选是打分——在合格节点里比资源均衡、镜像缓存、拓扑分散这些因素，分高者得。想定制行为走调度框架写插件，比如 GPU 机器的拓扑感知调度。

### 33. 什么情况下会用到污点与容忍？

**要点：**
- 污点（taint）= 节点的"排斥声明"；容忍（toleration）= Pod 的"通行证"
- 典型场景：
  1. **专用节点**：GPU 节点打污点——只有声明容忍的 GPU 任务能上（防普通任务抢占）
  2. **保护控制平面**：master 自动带 node-role.kubernetes.io/master:NoSchedule——默认不让业务 Pod 上
  3. **故障隔离**：节点硬件异常人工打污点疏散负载
  4. **节点退役**：NoExecute 污点快速驱逐存量 Pod
- 三种效应：**NoSchedule**（不排新）、**PreferNoSchedule**（尽量别来）、**NoExecute**（不排新+驱逐存量）
- 对照：亲和是 Pod 挑节点（吸引），污点是节点挑 Pod（排斥）

**一句话答：** 污点容忍解决"专属与隔离"：GPU 节点打 NoSchedule 污点只让带容忍的 AI 任务上，master 自带的污点保护控制面，节点故障时打 NoExecute 直接驱逐存量负载。记住三种效应的区别，NoExecute 最狠——新 Pod 进不来、旧的也赶走。

### 34. PVC 和 PV 是什么？解决了什么问题？

**要点：**
- **PV**（PersistentVolume）：集群里的**实际存储资源**（NFS/Ceph/云盘）——管理员/StorageClass 供应
- **PVC**（PersistentVolumeClaim）：用户的**存储申请单**（要 10G、ReadWriteOnce）——与 PV 绑定后作为卷挂进 Pod
- 解决的问题：**存储解耦**——应用团队提"需求"（PVC），存储团队/平台供"资源"（PV）；Pod 不感知存储细节，迁移、换后端不动应用
- 绑定规则：容量、访问模式、StorageClass、selector 匹配
- 访问模式：RWO（单节点读写）/ROX/ RWX（多节点读写，需文件存储）/RWOP（单 Pod）

**一句话答：** PV 是实际的存储资源，PVC 是用户对存储的申请单，两者按容量和访问模式撮合绑定。它解决的是存储与应用解耦：Pod 只管挂 PVC，底下是 NFS 还是云盘、以后换不换后端，应用完全无感。访问模式要记 RWO 和 RWX 的区别——块存储只能单节点挂，共享文件系统才能多节点读写。

### 35. StorageClass 是什么？

**要点：**
- StorageClass = **存储的"规格模板/供应策略"**——定义用什么 provisioner、参数（盘类型/性能/IOPS）、回收策略
- 核心价值：**动态供应（Dynamic Provisioning）**——PVC 里写 storageClassName，集群**自动创建 PV**（调云 API 开盘/创建 Ceph 卷），无需管理员手动建
- 参数：provisioner（csi 驱动）、parameters（云盘类型 ssd/hdd）、reclaimPolicy（Delete/Retain）、allowVolumeExpansion（允许在线扩容）
- 默认 StorageClass：PVC 不指定类时自动用它
- 对照：无 SC 的时代要管理员手动建 PV 等 PVC 来绑（静态供应）

**一句话答：** StorageClass 是动态供应的模板：定义了用什么 CSI 驱动、开什么规格的盘、删了之后是 Retain 还是 Delete。用户 PVC 里引用它，集群自动把真盘建出来——存储从"管理员手工预建"变成"按需自动开通"，这是 K8s 存储体验的关键一步。

### 36. PV 的生命周期是怎样的？

**要点：**
- 阶段流转：**Available**（未被绑定）→ **Bound**（已绑 PVC）→ **Released**（PVC 已删，资源未回收）→ **Failed**（回收失败）
- 回收策略（persistentVolumeReclaimPolicy）：
  - **Delete**（StorageClass 默认）：PVC 删→PV 及后端存储**自动删除**（动态供应标配）
  - **Retain**：PVC 删→PV 进 Released **保留数据**，人工处理（生产重要数据用）
  - Recycle（废弃）
- 保护机制：**PVC 保护 finalizer**——Pod 还在用 PVC 时删 PVC 会卡 Terminating，防误删正在用的存储
- 运维要点：Released 状态的 PV 想复用要清 claimRef 或改策略

**一句话答：** PV 一生四态：Available 等绑定，Bound 服务中，PVC 删掉后进 Released——此时按回收策略分岔：Delete 自动销毁后端存储，Retain 留着数据等人工处理。生产重要数据一律 Retain。还有个保护设计：Pod 还在用的时候删 PVC 会被 finalizer 卡住，防止活着的存储被误删。

### 37. CSI（容器存储接口）有什么作用？

**要点：**
- CSI = **容器存储统一接口标准**：存储厂商实现 CSI 驱动（sidecar+gRPC），K8s 通过标准调用——**厂商逻辑出树外，K8s 核心不带存储代码**
- 解决的问题：以前每种存储支持要改 K8s 内置代码（in-tree）——升级慢、耦合重；CSI 后驱动独立发版独立升级
- 组成：Node 插件（DaemonSet，挂卷到节点）+ Controller 插件（Deployment，创建/删除/attach 卷）
- 能力：动态供应、快照（VolumeSnapshot）、在线扩容、拓扑感知调度
- 类比三件套：CRI（运行时）、CNI（网络）、CSI（存储）

**一句话答：** CSI 是存储界的标准接口：存储厂商按规范提供独立驱动，K8s 通过统一 gRPC 调用创建、挂载、快照、扩容——存储逻辑彻底从 K8s 核心里拆出来。好处是厂商驱动独立迭代，K8s 升级不再被存储代码绑架。记忆口诀：CRI 管容器、CNI 管网络、CSI 管存储。

### 38. 误删除 PVC，怎么恢复？

**要点：**
- 先分清三个层面：
  1. **PVC 对象删了、PV 还在**（Retain 策略）：PV 处于 Released——**数据还在**！恢复：新建 PVC，通过 `claimRef` 指向该 PV（kubectl patch 清掉/改写 claimRef），PV 回到 Bound
  2. **Delete 策略**：PV 和**后端存储已被销毁**——K8s 层无力回天，转向**底层恢复**：云盘快照（ECS 回滚/新盘从快照创建）、Ceph 快照、备份系统（Velero）
  3. **有 Velero/备份系统**：直接按备份点恢复 PVC+PV+数据
- 预防：重要 StorageClass 设 reclaimPolicy=Retain、开启 PVC 保护、定期快照、生产库别直接删 PVC
- 排查动作：先 `kubectl get pv` 看对应 PV 状态——Released 还是没了，决定走哪条路

**一句话答：** 第一步看 PV 状态：如果回收策略是 Retain，PV 会卡在 Released，数据还在，新建 PVC 用 claimRef 指回这个 PV 就能接上；如果是 Delete 策略，K8s 层已经无能为力，只能靠云盘快照、Ceph 快照或 Velero 这类底层备份恢复。这事的教育意义是：重要数据的 StorageClass 必须 Retain 加定期快照。

### 39. emptyDir 和 hostPath 卷的应用场景？

**要点：**
- **emptyDir**：Pod 级临时空目录（首次挂载为空），Pod 删除即消失——
  - 场景：同 Pod 容器间共享临时数据、**scratch 空间**（排序/压缩缓存）、checkpoint；`medium: Memory` 变 tmpfs（快、不落盘、占内存）
  - 注意：可设 sizeLimit，超限驱逐策略各版本有差异
- **hostPath**：挂**节点目录**进容器——
  - 场景：DaemonSet 类组件访问节点资源（日志 /var/log、cgroup、docker.sock）
  - 风险：破坏隔离（可碰节点文件）、**调度无感知**（换节点数据不在）、安全敏感——必须限定 type（Directory/File）并慎用
- 对照：要持久且跨 Pod 用 PVC；临时共享 emptyDir；碰节点资源 hostPath（最小权限）

**一句话答：** emptyDir 是 Pod 的临时草稿纸：容器间共享中间数据，Pod 没了就清空，适合缓存和临时文件。hostPath 是给节点开的后门：DaemonSet 采集节点日志、监控读 cgroup 用它，但风险大——能穿透到节点文件系统且 Pod 漂移到别的节点数据就没了，必须限制 type 和路径。

### 40. Secret 有哪些应用场景？

**要点：**
- 用途：存放**敏感数据**——密码、Token、证书、SSH key、镜像仓库凭证
- 常见类型：
  - **Opaque**（通用键值，base64 编码——**不是加密**！）
  - **docker-registry**（imagePullSecrets 拉私有仓库）
  - **tls**（Ingress 证书）
  - **service-account-token**（SA 令牌自动挂载）
- 使用方式：env 注入 / volume 挂载（文件形式，可热更新）/ 镜像拉取凭证
- **安全短板与现实**：默认仅 base64 + etcd 明文——生产必须：etcd 加密（EncryptionConfiguration）、RBAC 收紧 get/list 权限、敏感项对接 **Vault/Sealed Secrets/External Secrets Operator**
- 对照 ConfigMap：非敏感配置走 ConfigMap，Secret 语义化但安全靠额外加固

**一句话答：** Secret 管敏感数据：数据库密码、镜像仓库凭证、TLS 证书三类高频。必须说破的一个真相是它默认只是 base64 编码不是加密，etcd 里是明文——所以生产要做三件事：etcd 层开加密、RBAC 限制谁能读、真正的密钥对接 Vault 或 External Secrets。使用上有 env 注入和文件挂载两种，文件挂载支持热更新。

### 41. RBAC 中 Role 和 ClusterRole 区别？

**要点：**
- **Role**：**命名空间内**授权（default ns 的 Pod get/list...）
- **ClusterRole**：**集群级**授权——两类用途：跨 namespace 的集群资源（nodes、namespaces、PV）、给所有 ns 复用的权限模板
- 绑定对应：**RoleBinding** 把 Role/ClusterRole 授予某 ns 内主体；**ClusterRoleBinding** 集群全局生效
- 经典组合：ClusterRole（定义权限集）+ 每个 namespace 的 RoleBinding（限定范围）——复用+隔离
- 主体：User/Group/**ServiceAccount**；权限动词：get/list/watch/create/update/patch/delete
- 排查：`kubectl auth can-i --list --as=system:serviceaccount:ns:sa`

**一句话答：** Role 限定在单个命名空间，ClusterRole 作用于整个集群——节点、PV 这类集群资源只能用它。绑定侧 RoleBinding 和 ClusterRoleBinding 分别对应范围。常用套路是 ClusterRole 定义权限模板加各命名空间 RoleBinding 授权，复用又隔离。验证权限用 kubectl auth can-i。

### 42. RBAC 中 ServiceAccount 有什么作用？

**要点：**
- SA = **Pod 的程序身份**（区别于 User 的"人"的身份）：Pod 指定 SA → API 调用时用 SA 的 Token 认证
- 用途：
  1. **Pod 访问 API**：controller 类应用（operator、CI runner）操作 K8s 资源——按需绑 Role
  2. **云厂商凭证联动**：IRSA/Workload Identity——SA 映射云 IAM 角色（免 AK 明文）
  3. **镜像拉取**：SA 关联 imagePullSecrets
- 安全实践：默认 SA 权限最小化、**每个应用独立 SA**（别全用 default）、禁用不必要 token 自动挂载（automountServiceAccountToken: false）、Token 过期机制（1.24+ TokenRequest）
- 排查：Pod 里 `kubectl auth can-i --list` 看实际权限

**一句话答：** ServiceAccount 是给程序用的身份：Pod 里的应用要调 API 或者拉私有镜像，都靠绑定的 SA 说话。安全要点三条：别让所有 Pod 共用 default 账号、不需要 API 权限的应用关掉 token 自动挂载、权限按应用单独授——这和"人不共享 root 密码"是同一个道理。

### 43. 如何提高 K8s 集群安全性？

**要点：**
- **API 访问层**：RBAC 最小权限、禁匿名、审计日志、认证（OIDC/证书）、apiserver 不暴露公网
- **工作负载层**：Pod Security Standards（restricted）、SecurityContext（非 root、只读根文件系统、drop capabilities）、**NetworkPolicy** 默认拒绝+白名单
- **供应链**：镜像扫描（Trivy）、镜像签名与准入校验（Cosign/Kyverno）、可信仓库、基镜像 pinned
- **运行时**：策略引擎（OPA Gatekeeper/Kyverno）准入拦截、运行时检测（Falco）、audit 告警
- **基础设施**：etcd 加密+TLS+备份、节点加固（最小化、patch）、密钥管理（Vault/KMS）
- 优先级建议：RBAC+NetworkPolicy+镜像扫描是性价比前三

**一句话答：** 分层设防：API 层 RBAC 最小权限加审计日志；负载层 Pod 安全标准——非 root、只读文件系统、NetworkPolicy 默认拒绝；供应链上镜像扫描加签名准入；再配策略引擎做准入拦截和 Falco 做运行时告警。落地优先级我建议先 RBAC、NetworkPolicy、镜像扫描三件套，覆盖了 80% 的常见风险。

### 44. Metrics Server 有什么作用？

**要点：**
- 集群的**资源指标聚合器**：采集 kubelet 内嵌 **cAdvisor** 的 CPU/内存数据 → 聚合 → 通过 **Metrics API**（metrics.k8s.io）暴露
- 消费者：
  - **HPA**（基于 CPU/内存的自动扩缩容依赖它）
  - `kubectl top nodes/pods` 命令
  - VPA、调度器插件
- 特点：**只存短期内存数据**（非时序库）——历史监控还得靠 Prometheus
- 关系澄清：Prometheus 走 exporter 体系采集，与 Metrics Server 并行不悖；HPA 用哪个取决于 resource metrics 还是 custom metrics
- 未安装的症状：kubectl top 报 "Metrics API not available"

**一句话答：** Metrics Server 是 kubectl top 和资源型 HPA 的数据源：它从各节点 kubelet 的 cAdvisor 收 CPU 内存瞬时值，聚合成 Metrics API。注意它只在内存里存短期数据，历史曲线还得靠 Prometheus——两者是并行的两套采集，一个喂调度决策一个喂监控告警。

### 45. 简述 HPA 的工作原理？

**要点：**
- HPA = Horizontal Pod Autoscaler，**水平自动扩缩容**
- 控制循环：HPA 控制器周期（默认 15s）取指标 → 与目标值比较 → 计算期望副本数（**期望副本 = 当前副本 × 当前指标/目标指标**）→ 调整 Deployment 副本数
- 指标源三类：
  1. resource：CPU/内存（Metrics Server）
  2. custom：自定义指标（Prometheus Adapter/Prometheus Adapter API）
  3. external：外部指标（队列长度等）
- 行为控制：behavior 的 scaleUp/scaleDown 策略（稳定窗口 stabilizationWindow 防抖动、扩快缩慢）
- 边界：minReplicas/maxReplicas；**缺 requests 的 Pod 不参与资源 HPA**；多个指标取最大需求
- 不缩容条件：挂了 PDB 之外，副本里有未完成 drain 等场景

**一句话答：** HPA 每 15 秒拉一次指标，按"期望副本数等于当前副本乘以实际指标除以目标指标"的公式算出该扩几个，然后改 Deployment 副本数。指标可以是 CPU 内存，也可以通过 Prometheus Adapter 接自定义指标。防抖是关键配置：稳定窗口让缩容慢于扩容，避免流量抖动引起副本数震荡。

### 46. 简述你对 Operator 的理解？

**要点：**
- Operator = **CRD + 自定义控制器**：把某个有状态软件的**运维知识编码成代码**——部署、扩容、备份、故障处理全自动
- 控制循环哲学：观察（watch CR 实际状态）→ 对比（期望状态）→ 行动（创建 Pod/改配置/切主从）——"智能化的人肉运维替代"
- 价值场景：数据库主从切换、Kafka 扩分区、ETCD 修复——复杂操作流程固化、可重复、免人为失误
- 生态：Prometheus Operator、ETCD Operator、各种数据库 Operator（MySQL/PG/Redis）
- 对比：Helm 管"装"，Operator 管"住"（全生命周期）

**一句话答：** Operator 就是把运维手册翻译成控制循环：用 CRD 定义这个软件的期望状态，控制器持续 watch 并执行部署、扩容、备份、故障切换这些原本靠人肉 SOP 的动作。Helm 解决装得上，Operator 解决管得好——特别是数据库这类有复杂运维流程的有状态服务，Operator 是它们上 K8s 的前提。

### 47. 节点处于 NotReady 状态如何解决？

**要点：**
- 先看节点侧：`kubectl describe node` Conditions（MemoryPressure/DiskPressure/网络失联）、Taints（NoExecute 被打上）
- 登节点排查：
  1. kubelet 活着吗：`systemctl status kubelet` + 日志（证书过期、CNI 报错高频）
  2. 容器运行时：`systemctl status containerd`
  3. 网络：节点到 apiserver 通不通（证书/token、LB）
  4. 资源：磁盘满（kubelet 直接罢工）、内存压力
- 常见根因清单：kubelet 挂了、**kubelet 证书过期**、磁盘写满、CNI 异常、容器运行时挂、内核/硬件故障
- 恢复后：Pod 重建（超过 pod-eviction-timeout 后节点上 Pod 被驱逐重建）；不可修复节点 drain 后移除
- 预防：证书轮转自动化、磁盘告警、节点监控

**一句话答：** 先 describe node 看 Conditions 和污点，然后登节点三连查：kubelet 状态和日志、容器运行时、磁盘水位。实战高频根因是 kubelet 挂了、证书过期和磁盘写满——磁盘满会让 kubelet 直接罢工。节点上 Pod 在失联超时后会被自动驱逐到其他节点，节点修不好就 drain 掉移出集群。

### 48. 创建 1 万个 Pod 时，可能会遇到哪些问题？

**要点：**
- **调度瓶颈**：调度器默认吞吐有限（可调并发、开启 profile 优化）；大批量 Pending
- **apiserver/etcd 压力**：万级对象 watch/list 风暴——etcd 大对象写入、apiserver QPS 限流（429）
- **网络瓶颈**：Pod IP 规划够不够（CIDR 耗尽）、iptables 模式 kube-proxy 规则爆炸（万级 Service/Endpoint）→ 必须上 **IPVS/eBPF**
- **节点资源**：单节点 Pod 密度上限（kubelet maxPods 默认 110）——需要几百节点；IP 地址池
- **存储**：大镜像批量拉取打爆仓库与网络——镜像预热（DaemonSet 预拉）
- **控制面容量**：生产建议控制面扩容、K8s 版本的 SLI（官方支持 5000 节点/15 万 Pod 量级）
- 优化清单：分批创建、HPA 代替一次性拉满、压缩对象、etcd 专属盘、监控 apiserver P99

**一句话答：** 万级 Pod 会在五个地方撞墙：etcd 和 apiserver 的写入与 watch 风暴、调度器吞吐、kube-proxy 的 iptables 规则量——必须换 IPVS、Pod IP 网段容量、以及镜像仓库被批量拉取打爆。应对是分批创建、控制面扩容、IPVS 模式、镜像预热，容量规划提前做而不是撞了再说。

### 49. 微服务迁移 K8s 主要做哪些工作？会遇到什么难点？

**要点：**
- 迁移工作清单：
  1. **容器化改造**：Dockerfile、配置外部化（环境变量/ConfigMap）、日志输出 stdout、无状态化（session 外移）
  2. **依赖梳理**：数据库/缓存/MQ 地址改 Service/DNS、连接池参数适配（滚动重启）
  3. **K8s 资源设计**：Deployment/Service/HPA/资源 requests-limits、探针三件套、preStop 优雅停机
  4. **配套体系**：日志采集（DaemonSet）、监控（exporter）、CI/CD 对接、配置中心
  5. **流量切换**：LB/域名指向 Ingress、灰度双跑
- 难点：
  - **有状态改造**：本地缓存/本地文件/session 的外移
  - **网络模型差异**：源 IP 保留、连接数模型、跨机房延迟
  - **性能基线**：容器 CPU 限流导致的性能抖动（throttling）
  - 团队习惯：从"登机器看日志"到"平台化运维"的转变

**一句话答：** 迁移五大块：应用容器化加配置外部化、依赖地址换成 Service DNS、K8s 资源设计含探针和优雅停机、日志监控 CI 对接、最后流量灰度切换。难点集中在三处：有状态部分的外移改造、网络模型差异——特别是源 IP 和限流抖动、以及团队从登机器到平台化的习惯转变。

### 50. 你在 K8s 运维中遇到过哪些问题？

**要点：**（面试话术，给典型素材库）
- 高频问题素材（选有细节的 2-3 个讲）：
  1. **OOMKilled 循环**：limit 给太小/内存泄漏——监控 container_memory_working_set 与 limit 的比值，调 limit+修泄漏
  2. **滚动更新丢请求**：没配 preStop/readiness——preStop sleep + 探针改造，LB 排水
  3. **节点磁盘满触发 Evicted 风暴**：容器日志无轮转——logrotate+emptyDir sizeLimit+告警
  4. **CrashLoopBackOff 排查路径**：describe events → logs → 常见是配置错/依赖不通/权限
  5. **DNS 5 秒延迟**：conntrack 冲突（老内核 UDP）——NodeLocal DNSCache/内核升级
  6. **证书过期**：kubelet 证书/Ingress 证书告警自动化
- 讲法模板：现象 → 定位过程（用了什么命令/监控）→ 根因 → 修复 → 防复发机制

**一句话答：**（示范框架）挑一个有深度的讲：比如一次滚动更新持续丢请求，排查发现是旧 Pod 收到 SIGTERM 立即退出而 LB 还在往它发流量——改造是 preStop 加 sleep 5 秒给上游连接池排水时间，配合 readiness 探针，更新期间错误率归零。重点展示定位思路和"修复加防复发"的闭环。

### 51. K8s 如何实现灰度发布？

**要点：**
- **按比例**：Deployment 双版本（v1/v2 两个 Deployment）+ Service selector 同时选中 + 副本数比例控制流量比（粗粒度）
- **Ingress 级**：nginx ingress 的 canary 注解——weight（按比例）、header/cookie（按用户）：

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
```

- **Istio/服务网格**：VirtualService 精确权重路由、按 header/uid 分流——最精细，支持全链路灰度
- **Argo Rollouts/Flagger**：自动化灰度——渐进放量+指标自动分析+自动回滚
- 配套纪律：灰度期监控对比（错误率/RT）、数据库 schema 向后兼容、一键回滚路径预置

**一句话答：** 从粗到细四种：双 Deployment 控副本比例最简单；Ingress 的 canary 注解支持按权重或按 header 精确分流；Istio 的 VirtualService 能做全链路染色灰度；Argo Rollouts 这类工具把放量加指标分析自动化，指标劣化自动回滚。无论哪种，schema 兼容和监控对比是底线。

### 52. K8s 集群节点需要关机维护，怎么操作？

**要点：**
- 标准流程：
  1. **cordon**：`kubectl cordon node`——标记不可调度（新 Pod 不来）
  2. **drain**：`kubectl drain node --ignore-daemonsets --delete-emptydir-data`——驱逐存量 Pod（优雅迁移到其他节点）
  3. 确认 Pod 已迁走（有状态 Pod 注意 PDB 保护——防一次性全下线）
  4. 关机/维护
  5. 开机后 `kubectl uncordon node` 恢复调度
- 注意点：
  - DaemonSet 的 Pod 不被 drain（--ignore-daemonsets）
  - 有本地存储/hostPath 的 Pod 迁移会丢数据——提前评估
  - 一次 drain 一台，等集群稳定再下一台
  - 云上托管节点池直接走平台功能

**一句话答：** 流程是 cordon 停止调度，drain 驱逐存量 Pod 让它们优雅搬家，维护完 uncordon 恢复。命令必带 --ignore-daemonsets，有本地数据的 Pod 先评估。纪律是一次只动一台节点，有状态服务配 PDB 防止副本同时全下线。

### 53. Etcd 集群某节点故障怎么恢复？

**要点：**
- 先评估影响：3 节点挂 1 个 = **quorum 仍在，集群可读写**（先别慌）；挂 2 个 = 丢失多数派，**只读不可写**——紧急处理
- 单节点恢复路径：
  1. 快速修：节点重启后 etcd 自动重加入（数据目录完整时）
  2. **成员替换**（数据盘坏）：`etcdctl member remove` 移除成员 → 修好/换机器 → `member add` 加入 → etcdctl snapshot restore 或从 leader 同步数据重新初始化 → 改 apiserver 的 etcd servers 配置
  3. 静态集群要更新所有成员的 initial-cluster 配置
- **多数派丢失**：从**最新 snapshot** restore 到新集群（注意 restore 会覆盖到快照时间点，期间数据丢失要评估）→ 指回 apiserver
- 预防：定期 snapshot（cron + 异地）、etcd 独立盘（SSD）、监控 member 状态与 lag

**一句话答：** 先看挂了几个：三节点挂一个 quorum 还在，集群照常读写，从容做成员替换——member remove 再 add，新节点 restore 或同步数据；如果挂到多数派丢失，集群只读，必须从最近的 snapshot restore 重建集群再指回 apiserver。日常的 etcd snapshot 定时备份就是为这一刻准备的。

### 54. K8s 集群怎么备份？

**要点：**
- 分层备份：
  1. **etcd 快照**（集群配置的核心）：`etcdctl snapshot save`——定期 cron + 异地存储；恢复=restore 全部成员+重建控制面
  2. **Velero**（标准方案）：备份 K8s **对象资源**（yaml 级）+ **PV 数据**（走CSI/插件快照到对象存储）——支持按 namespace 选择性备份、**跨集群迁移/容灾恢复**、定时计划
  3. **应用层数据**：数据库有自己的备份体系（mysqldump/xtrabackup）——不依赖 K8s 层
  4. **配置即代码**：Git 里的 manifests/Helm/ArgoCD——集群炸了按 Git 重建（GitOps 天然备份）
- 演练：备份必须定期做**恢复演练**——没验证过的备份=没备份
- 策略建议：etcd 每日快照+Velero 每日全量按 ns+Git 管清单，三层兜底

**一句话答：** 我按四层做：etcd 快照保集群状态，Velero 备份资源对象和 PV 数据到对象存储还能跨集群恢复，数据库这类应用数据走自己的专业备份，最后 Git 里的所有 manifest 本身就是一份可重建的清单。核心纪律还是恢复演练——每个季度真跑一次恢复，备份的可信度靠演练证明。

### 55. Etcd 有哪些参数可以优化？

**要点：**
- **硬件层**（影响最大）：SSD/NVMe 独立盘（fdatasync 延迟是命门）、低延迟网络、独占部署（不和 apiserver 混部抢资源）
- **存储参数**：`--quota-backend-bytes`（默认 2GB，建议 8GB+，配合压缩）、定期 **compaction**（--auto-compaction-mode=periodic/revision）
- **快照与磁盘**：snapshot-count 调优；监控 `etcd_disk_wal_fsync_duration`（>10ms 告警）、`etcd_server_slow_apply`
- **心跳与选举**：--heartbeat-interval（100ms 内网可调低）、--election-timeout（跨机房调大防误选举）
- **客户端限流**：--max-concurrent-streams、max-request-bytes（大对象限制——ConfigMap 别塞大文件）
- 数据治理：控制对象数量与大小（Event 自动清理、大 ConfigMap 拆分）

**一句话答：** etcd 优化的第一定律是给它独占的 SSD 和低延迟网络——fdatasync 延迟决定集群写入上限。参数层面：调大 quota-backend-bytes 配合定期 compaction 防 DB 空间满，跨机房环境调大选举超时防误切换。更重要的运维习惯是别把 etcd 当数据库用——大 ConfigMap、海量 Event 都是压垮它的常见操作。

### 56. K8s 证书过期怎么续签？

**要点：**
- **kubeadm 集群**：
  - 检查：`kubeadm certs check-expiration`
  - 续签全部：`kubeadm certs renew all`（apiserver/etcd/SA 等控制面证书，1 年期）
  - 续签后**重启控制面组件**（apiserver/kubelet 交互的 kubeconfig 也是证书——kubelet.conf 等要重新分发）
  - kubelet 客户端证书：`/var/lib/kubelet/pki`，轮转依赖 --rotate-certificates（默认开）
- 手动单证书：renew apiserver 等；自签 CA 一般不动（CA 过期是大手术）
- 托管集群：控制面证书云厂商管，用户只管应用证书
- Ingress/应用证书：cert-manager 自动续期（Let's Encrypt/私有 CA）
- **预防**：证书到期监控告警（30/15/7 天分级）、续期演练文档化

**一句话答：** kubeadm 集群用 kubeadm certs check-expiration 查到期时间，renew all 一键续，重点是续完必须重启控制面组件才生效。节点侧 kubelet 证书默认自动轮转。应用层证书交给 cert-manager 自动化。最关键的运维动作是把证书到期做成监控告警——证书过期导致的 apiserver 拒连是完全可以预防的事故。

### 57. 微服务在升级过程中出现 500 错误是什么原因？

**要点：**
- **新旧版本兼容性问题**（高频）：
  1. **接口不兼容**：新版服务调用旧版下游的字段/语义变了（向后兼容没做）
  2. **数据 schema 不兼容**：新代码读旧数据结构（缺字段/格式变）
  3. 配置项变更：新版本需要的配置没同步（ConfigMap 旧值）
- **滚动更新窗口期**：新旧 Pod 并存，流量打到不同版本——行为不一致
- **依赖未就绪**：新版本启动慢，探针/流量先到——连接池/缓存未初始化
- **优雅停机缺失**：旧 Pod 被 SIGTERM 立即杀，处理中的请求中断
- 排查顺序：错误日志堆栈 → 版本关联（错误集中在 v2 Pod？）→ 最近 diff → 配置 diff

**一句话答：** 升级期 500 的根源基本是"新旧并存期的不一致"：接口和数据结构没做向后兼容、新版本配置没同步、新 Pod 还没热身就接流量、旧 Pod 被杀得太急。排查时先看错误是否集中在某个版本 Pod 上，再做代码和配置 diff。预防靠兼容性纪律：接口永远向后兼容、配置变更和代码发布解耦。

### 58. 设计 500 台 K8s 集群重点考虑哪些问题？

**要点：**
- **规模上限评估**：500 节点在单集群舒适区边缘（官方 SLI 5000 节点）——可行，但要做控制面容量设计
- **控制面**：apiserver 3-5 副本+负载均衡、etcd 专用 SSD 独立 5 节点、大并发 watch 优化（list-watch 分页/压缩）
- **网络**：必须 IPVS/eBPF（iptables 撑不住万级 Service）、Pod CIDR 规划（/16 起步）、云上 VPC 路由容量
- **多集群 vs 单集群**：按业务域/故障域拆多集群 + 统一管理（Karmada/Clusternet）往往优于单集群无限膨胀
- **运维体系**：节点自动扩缩（autoscaler）、节点池分组（业务隔离/特殊硬件）、灰度升级机制、堡垒与权限体系
- **配套**：监控采集分片（Prometheus 联邦/Thanos）、日志量评估、镜像仓库带宽
- **成本**：节点池混部、竞价实例策略、资源超卖比

**一句话答：** 500 台的核心是控制面容量和网络选型：apiserver 和 etcd 按规模配副本上独占硬件，kube-proxy 必须换 IPVS，IP 网段一次规划到位。更重要的架构决策是想清楚要不要拆多集群——按业务域拆多集群加统一管理平台，比把所有鸡蛋放一个巨型集群更健康。监控和日志的采集端也要分片设计。

### 59. 怎么保障应用升级过程中不丢失流量？

**要点：**
- 流量丢失三场景对三招：
  1. **新 Pod 未就绪接流量** → readinessProbe 严格配置——没 ready 不进 Endpoint
  2. **旧 Pod 杀得太急** → preStop hook（sleep 5-10s 排水）+ terminationGracePeriodSeconds 足够长 + 应用处理 SIGTERM 优雅退出
  3. **连接池/长连接未感知** → preStop 给上游刷新时间；gRPC 长连接场景旧 Pod 先摘 Endpoint 再 sleep
- 配置组合拳：

```yaml
lifecycle:
  preStop:
    exec: { command: ["sh","-c","sleep 5"] }
```

- **滚动参数**：maxUnavailable=0（永不降可用数）
- **更上层**：LB 健康检查联动、连接排空（云 LB connection draining）
- 验证手段：滚动期间压测看错误率、watch Endpoint 变化
- StatefulSet/DB 类：分区更新+人工确认

**一句话答：** 不丢流量的关键是让"摘流量"和"停进程"两个动作错开：readiness 保证新 Pod 真正能服务才接单，preStop 的 sleep 让旧 Pod 先从 Endpoint 摘除、给上游连接池几秒感知时间，然后才 SIGTERM 优雅退出。再配 maxUnavailable=0 保证集群容量不下滑。这套组合拳跑通后，滚动更新期间的错误率应该是零。

### 60. K8s 应该监控哪些关键指标？

**要点：**
- **集群层（USE 方法）**：节点 CPU/内存/磁盘 IO/网络、Pod 密度、apiserver 延迟与错误率、etcd（fsync 延迟/慢查询/quorum）、scheduler 吞吐、kubelet 状态
- **控制面健康**：apiserver P99、etcd disk 延迟（>10ms 告警）、证书有效期、leader 选举
- **工作负载层（RED 方法）**：每服务的 Rate（QPS）/Errors/Duration——kube-state-metrics（副本状态、Pod 重启次数、Pending 数）+ cAdvisor 资源
- **容量层**：节点资源分配率（requests 超卖比）、PV 使用率、IP 池余量
- **业务层**：业务指标（订单/QPS）——最灵敏的探针
- 工具链：Prometheus + node-exporter + kube-state-metrics + cAdvisor + Grafana + 告警分级

**一句话答：** 四层指标体系：集群层盯节点资源和 apiserver、etcd 的健康——etcd 磁盘延迟是最灵敏的集群哨兵；负载层按 RED 方法看每个服务的 QPS、错误率、延迟，加 kube-state-metrics 的副本与重启状态；容量层盯资源分配率和 IP 池；最上层永远留业务指标，用户比监控先发现问题就是监控失职。

### 61. K8s 巡检都会做哪些项目？

**要点：**
- **控制面**：组件存活（apiserver/scheduler/etcd）、etcd 空间与延迟、证书有效期、集群版本与 kubeadm 配置漂移
- **节点**：NotReady 节点、资源水位（CPU/内存/磁盘/inode/pid）、污点异常、内核版本、运行时状态
- **工作负载**：异常状态 Pod（Pending/CrashLoop/Evicted）、重启次数异常、副本数不齐、探针失败率、HPA 处于边界、资源 requests/limits 缺失
- **存储**：PV/PVC 绑定状态、容量使用率、StorageClass 回收策略
- **网络**：DNS 解析延迟（CoreDNS）、NetworkPolicy 变更、Service Endpoint 空列表
- **安全**：RBAC 变更审计、镜像漏洞高危、Secret 到期、SA 滥用
- **备份**：快照任务成功率、最近恢复演练时间
- 落地：巡检脚本化/平台化（Prometheus 规则替代人眼），输出报告+跟进闭环

**一句话答：** 巡检清单六大块：控制面组件和证书、节点资源水位、异常状态 Pod、存储绑定与容量、DNS 和网络健康、安全合规加备份任务成功率。成熟的团队会把巡检从人眼变成 Prometheus 规则加自动化报告，人只处理巡检发现的异常项——每项异常都要有跟进闭环。

### 62. KubeVirt 了解过吗？

**要点：**
- KubeVirt = **在 K8s 上跑虚拟机**：以 CRD（VirtualMachine/VMI）声明 VM，由 virt-controller/virt-handler/virt-launcher 驱动 **libvirt/QEMU** 创建真 VM
- 定位：VM 和容器**统一编排**——VM 也是 K8s 资源，共享网络（CNI）、存储（PVC）、调度、监控体系
- 场景：
  1. **遗留 VM 应用渐进迁移**：先搬进 K8s 集群（不改造），再逐步容器化
  2. 强隔离需求：VM 边界（多租户）
  3. Windows/特殊内核应用
- 关键能力：热迁移（live migration）、快照、GPU 直通、VNC console
- 对照：和 OpenStack 关系——轻量 VM 层挂进 K8s 生态，而非完整 IaaS

**一句话答：** KubeVirt 把虚拟机变成 K8s 的一种资源：用 CRD 声明 VM，底层还是 QEMU/KVM 跑，但调度、网络、存储、监控全部复用 K8s 体系。典型用途是遗留 VM 应用的迁移中转站——先原样搬进来统一管理，再慢慢容器化，以及需要强隔离的场景。它有热迁移和 GPU 直通这些完整 VM 能力。

### 63. K8s 多集群统一管理怎么做？

**要点：**
- 为什么多集群：故障域隔离、地域就近、多租户强隔离、合规、规模上限
- 统一管理方案：
  1. **Karmada**（华为开源）：多集群编排——应用分发策略（按资源/地域/权重）、故障迁移、聚合 API
  2. **Clusternet**、**OCM**（Open Cluster Management）
  3. **GitOps 面**：ArgoCD ApplicationSet——Git 一份 manifest 分发到多集群（配置统一，调度策略弱）
  4. 云厂商托管：ACK Fleet/EKS 多集群
- 配套统一层：多集群监控（Thanos/Mimir 全局视图）、统一网关（全局负载均衡/GSLB）、统一权限与审计
- 流量跨集群：全局 Ingress/DNS 智能解析、服务网格多集群（Istio 多主/multi-network）
- 选型直觉：配置分发 GitOps 起步；需要调度策略与故障切换上 Karmada

**一句话答：** 多集群的动机是故障域和合规隔离，管理方案两条路线：GitOps 派用 ArgoCD 的 ApplicationSet 把一份 manifest 分发到各集群，简单但只有分发没有调度；编排派用 Karmada 这类项目做跨集群的应用分发、按权重调度和故障迁移。配套还要统一监控视图和全局流量入口，否则"管理"只是登录多个 dashboard。

### 64. Cilium 网络组件有什么优势？

**要点：**
- 基于 **eBPF**：数据面在内核直接完成——高性能（绕过 iptables 线性匹配）、低开销
- **kube-proxy 替代**：Service 负载均衡由 eBPF map 实现，大规模下性能碾压 iptables/IPVS
- **L7 感知策略**：NetworkPolicy 能按 HTTP path/method、Kafka topic、gRPC 方法定义——比四层策略细一个维度
- **可观测性（Hubble）**：服务间流量可视化、依赖拓扑、丢包原因——网络问题从"抓包猜"变成"界面看"
- 透明加密（WireGuard/IPSec）、带宽管理、服务网格替代（sidecar-less）
- 代价：内核版本要求高（5.10+ 推荐）、复杂度与排障门槛（eBPF 栈深）

**一句话答：** Cilium 的杀手锏是 eBPF 数据面：Service 转发在内核态完成，大规模集群性能远超 iptables；NetworkPolicy 细到 HTTP 路径和 gRPC 方法；Hubble 还把服务间流量变成可视化拓扑。代价是内核版本要求和更深的排障门槛。追求大规模和高性能时它是现在的首选网络方案。

### 65. Cilium 有哪几种工作模式及原理？

**要点：**
- **隧道模式**（默认 VXLAN/Geneve）：跨节点报文封装——兼容性好，不依赖底层网络
- **原生路由模式**（native-routing）：直接路由（BGP/静态）——无封装性能最好，要求网络可达 Pod CIDR
- 数据面细节：
  - Pod 出流量：bpf 程序挂在 veth/TC 上完成策略判断和转发
  - Service：bpf map 哈希表 DNAT（kube-proxy free）
  - NodePort 也在 eBPF 层实现
- **加密模式**：WireGuard（推荐，内核态）/IPSec
- 策略执行：bpf map 存 identity（label 派生）——L3/L4/L7 分层策略，L7 走 Envoy proxy 端口
- 选型：物理网络可控用 native routing，复杂环境 VXLAN 兜底

**一句话答：** Cilium 的封装层有两种选择：VXLAN 或 Geneve 隧道模式兼容一切环境，native routing 直接走 BGP 路由性能最好但要求底层网络配合。数据面上所有转发和 Service DNAT 都在 eBPF 完成，七层策略借 Envoy 实现。加密推荐 WireGuard 内核态方案。

### 66. 数据库是否适合部署在 K8s 上？

**要点：**
- 争议本质：K8s 擅长**无状态**调度 vs 数据库需要**稳定存储+低延迟 IO+复杂运维**
- **适合的场景**：
  - 有成熟 Operator（MySQL Operator/Vitess/PG Operator/Cassandra Operator）
  - 云盘/本地盘 IO 足够、测试环境、中小规模
  - 团队有 K8s 存储与 Operator 运维能力
- **不适合/谨慎**：
  - 核心大库对 IO 极敏感（本地 NVMe + 专用主机更稳）
  - 缺乏 Operator 时主从切换、备份、扩容全要手工——比虚拟机还累
  - 共享存储 IO 争抢（跨节点挂载延迟）
- 折中方案：**Operator+本地 PV（Local PV）**、K8s 管编排+DBA 平台管数据、云 RDS 托管
- 判断标准：**Operator 成熟度 + 存储性能 + 团队能力**三要素齐才上

**一句话答：** 我的答案是"看 Operator 成熟度和存储能力"：有靠谱 Operator 加足够 IO 的存储，中小规模数据库上 K8s 收益明显——自动化切换备份扩容；但核心大库对 IO 和稳定性极端敏感，本地 NVMe 加专用主机或直接云 RDS 更稳妥。数据库上不上 K8s 不是信仰问题，是 Operator 和存储撑不撑得住的问题。

### 67. K8s 有哪些常见的存储方案？

**要点：**
- **临时卷**：emptyDir（Pod 级临时）、ConfigMap/Secret（配置注入）
- **节点卷**：hostPath（节点目录，谨慎）
- **网络存储（PV 后端）**：
  - 块存储：云盘（EBS/云硬盘）、Ceph RBD——RWO 高性能
  - 文件存储：NFS、云 NAS（OSS 挂载不算块）、CephFS——RWX 共享
  - 对象存储：S3/OSS——通过 s3fs/专用挂载，静态资源场景
- **分布式方案**：Ceph（RBD+FS+对象一体）、Longhorn（轻量 K8s 原生）、OpenEBS、GlusterFS（维护模式）
- **本地盘**：Local PV（节点 NVMe 直通——高 IO 数据库首选，调度要感知拓扑）
- 选型维度：读写模式（RWO/RWX）、性能、备份快照能力、运维复杂度

**一句话答：** 按场景分：要高性能数据库用 Local PV 或云盘这类块存储；要多 Pod 共享文件用 NFS 或 CephFS 这类文件存储；静态资源用对象存储；轻量自建集群 Longhorn 开箱即用，重度使用上 Ceph 全家桶。选型先问三个问题：读写模式、性能要求、谁来做备份。

### 68. kube-proxy iptables 模式如何实现的负载均衡？

**要点：**
- 实现：kube-proxy watch Service/Endpoint 变化 → 生成 **iptables 规则**（NAT 表）
- 流量路径：Pod 访问 ClusterIP → PREROUTING → KUBE-SERVICES 链匹配 → KUBE-SVC-xxx 链 → **概率跳转**（-m statistic --mode random --probability）实现近似轮询 → KUBE-SEP-xxx 链 **DNAT 到具体 Pod IP** → POSTROUTING
- 特点：
  - 规则数与 Service×Endpoint 数线性增长——线性匹配性能随规模下降（O(n)）
  - 随机选择而非真实 LB 算法；无连接级一致性
  - 更新=全量刷规则，大规模下更新风暴
- 对照 IPVS：哈希表 O(1)、真实算法（rr/lc/sh）、连接跟踪复用
- 排查：`iptables-save | grep KUBE-SVC` 看规则、conntrack 表

**一句话答：** iptables 模式就是把每个 Service 和后端翻译成 NAT 规则链：请求命中 KUBE-SVC 链后，按概率规则在多个后端间分流，最后 DNAT 到具体 Pod IP。弱点在规模——规则线性匹配 O(n)，几千个 Service 后性能和更新速度都崩，所以大规模集群换 IPVS 的哈希表加真实调度算法。

### 69. Gateway 是什么？如何迁移现有 Ingress？

**要点：**
- **Gateway API**：Ingress 的下一代标准（K8s 官方，CRD 实现）——解决 Ingress 的注解泛滥与角色混乱
- 核心资源：
  - **GatewayClass**：定义"由哪个 Controller 实现"（基础设施方管理）
  - **Gateway**：实例化的监听器（端口/证书/TLS）——平台方管理
  - **HTTPRoute**：路由规则（域名/路径/Header 匹配、权重分流）——应用方管理
- 优势：**角色分离**（平台与应用分层授权）、跨厂商一致语义、原生支持权重灰度/Header 路由（不用注解）、TCP/UDP/gRPC 统一
- 迁移路径：
  1. 部署支持 Gateway API 的实现（Envoy Gateway/Cilium/Kong/istio）
  2. **并存阶段**：同一 Controller 可同时服务 Ingress 与 Gateway——新旧流量并行
  3. 逐个应用建 HTTPRoute（工具可自动转换：ingress2gateway）
  4. 验证后摘除旧 Ingress
- 注意点：注解功能的等价映射清单、TLS 证书迁移、LB 复用（避免新购 LB 成本）

**一句话答：** Gateway API 是官方对 Ingress 的翻新：拆成 GatewayClass、Gateway、HTTPRoute 三层资源，让平台团队管入口、应用团队管路由，权限和职责分清，灰度权重和 Header 路由原生支持不再靠注解。迁移可以平滑做：新 Controller 同时支持两种资源，用 ingress2gateway 转换规则，新旧并行验证后逐个切换。

### 70. K8s 容器运行时怎么选择？

**要点：**
- CRI 标准（1.24 移除 dockershim 后）：
  - **containerd**（事实标准）：Docker 内核组件独立化，K8s 原生 CRI、稳定高效、生态最广——**默认推荐**
  - **CRI-O**：RedHat 主推，纯 K8s 定制，轻量
  - **Docker Engine**（via cri-dockerd）：兼容存量场景，新集群不推荐
- 选择考量：镜像生态（containerd 完全兼容 Docker 镜像）、工具链（ctr/crictl/nerdctl）、安全（gVisor/Kata 作为沙箱运行时补充——RuntimeClass 切换）
- 排障影响：镜像和容器排查从 docker 命令换成 **crictl**（K8s 视角）/ctr（containerd 视角）/nerdctl（docker 兼容体验）
- 安全增强：需要强隔离的业务用 RuntimeClass 指定 Kata Containers

**一句话答：** 现在的答案是 containerd：它本来就是 Docker 的内核组件，原生支持 CRI，镜像完全兼容，生态最成熟。CRI-O 是 RedHat 系的轻量替代。运维要适应的是排障命令从 docker 换成 crictl。需要强隔离的场景用 RuntimeClass 切到 Kata 这类沙箱运行时。

### 71. 简述 CRI、CNI、CSI 分别是什么，各自解决什么问题？

**要点：**
- **CRI**（Container Runtime Interface）：K8s ↔ **容器运行时**的标准接口（gRPC）——containerd/CRI-O 实现它；解决"K8s 不绑定具体运行时"，Pod 生命周期、镜像管理统一调用
- **CNI**（Container Network Interface）：**Pod 网络**标准——插件二进制约定（ADD/DEL 生命周期），Flannel/Calico/Cilium 实现；解决"网络方案可插拔"——IP 分配、跨节点互通
- **CSI**（Container Storage Interface）：**存储**标准——厂商驱动实现创建/挂载/快照/扩容；解决"存储厂商解耦"，动态供应
- 共同哲学：**标准化接口 + 可插拔实现**——K8s 核心只做编排，生态各司其职
- 对应组件：kubelet→CRI（containerd）、各节点→CNI 二进制、CSI 驱动 Pod

**一句话答：** 三个接口一个思想：CRI 让 K8s 和容器运行时解耦——containerd 和 CRI-O 随便换；CNI 让网络方案可插拔——Flannel 换 Cilium 不动应用；CSI 让存储厂商独立交付——驱动自己升级。K8s 核心通过这三大标准接口把运行时、网络、存储全下放到生态，自己专注编排。

### 72. 简述 Operator 具体开发流程？

**要点：**
- 流程（以 Kubebuilder/Operator SDK 为例）：
  1. **建模**：设计 CRD——字段即运维意图（spec：副本/版本/备份策略；status：实际状态/条件）
  2. **脚手架**：kubebuilder init/create api 生成项目骨架（controller-runtime）
  3. **实现 Reconcile**：核心控制循环——读 CR → 比对实际状态 → 创建/更新资源（Deployment/PVC/Service...）→ 写回 status；**幂等**是铁律
  4. **状态与事件**：status conditions、EventRecorder 记录动作
  5. **高级能力**：OwnerReference 级联删除、finalizer 清理逻辑、webhook 准入校验（默认值/合法性）
  6. **测试**：envtest（本地 apiserver）集成测试、红绿场景
  7. **发布**：构建镜像 → Helm/OLM 打包分发
- 设计原则：水平触发（可重入）、乐观锁（resourceVersion）、错误重试（Requeue）
- 典型代码结构：Reconcile 里按子步骤函数化（ensureDeployment/ensureService/ensurePVC）

**一句话答：** 用 Kubebuilder 起步：先设计 CRD 把运维意图翻译成字段，然后实现 Reconcile 函数——读期望状态、对比实际、补齐差异，核心纪律是幂等和可重入，因为控制循环会被各种事件反复触发。进阶功能是 finalizer 处理删除、webhook 做准入校验，最后 envtest 测试加 Helm 打包发布。

### 73. K8s CRD 是什么？怎么定义？

**要点：**
- CRD（Custom Resource Definition）：**向集群注册新资源类型**——让 apiserver 接受自定义 API（如 Database/MyApp），无代码扩展 API
- 定义示例：

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  names: { kind: Database, plural: databases, shortNames: [db] }
  scope: Namespaced
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas: { type: integer }
              version: { type: string }
```

- 组成要点：group+version 构成 API 路径、scope 决定 Namespaced/Cluster、**OpenAPI v3 schema 校验**字段合法性
- CRD vs 内置资源：CRD 只是"类型定义"，**行为要靠控制器实现**（无控制器=存数据而已）
- 进阶：多版本转换（webhook conversion）、subresources（status/scale）

**一句话答：** CRD 是给 apiserver 注册自定义资源类型的声明：定义 group、kind、作用域和字段 schema，之后就能像操作 Pod 一样 kubectl 操作自己的资源。关键认知是 CRD 只定义了数据结构，行为的实现要配套自定义控制器——这也是 Operator 的由来。

### 74. K8s 节点磁盘不足，怎么定位到大文件？

**要点：**
- 定位流程：
  1. 哪块盘满：`df -h` / `df -i`（区分空间和 inode）
  2. 逐层下钻：`du -xsh /* 2>/dev/null | sort -rh` 递归深入（-x 防跨文件系统）
  3. K8s 高发目录：
     - `/var/lib/docker|containerd`：镜像层、容器可写层（`docker system df` / `crictl stats`）
     - `/var/log/pods`、`/var/log/containers`：**容器日志无轮转**（头号元凶）
     - `/var/lib/kubelet`：emptyDir 体积
     - `journal`：`journalctl --disk-usage`
  4. 已删除未释放：`lsof +L1`（进程占句柄）——truncate 处理
- 容器侧对应：Pod 内 `du`、kubectl exec 进容器看
- 清理与根治：crictl rmi --prune、日志轮转（containerd max-size）、emptyDir sizeLimit、告警阈值 70%

**一句话答：** 用 du -x 从根逐层下钻找大头，K8s 节点上重点怀疑四个地方：/var/log/pods 的容器日志、containerd 的镜像和容器层、kubelet 的 emptyDir、journal 日志。还有个经典隐藏项是文件删了进程还握着句柄——lsof +L1 能抓到。根治靠日志轮转配置和镜像定期清理，而不是每次人工救火。

### 75. Pod 处于 Terminating 无法删除，如何强制清理？

**要点：**
- 先**理解为什么卡**（别上来就强删）：
  1. **finalizer 未完成**：资源声明了 finalizer，控制器没执行清理（常见：有状态应用等待数据卸载、旧版本控制器逻辑 bug）
  2. 节点失联：kubelet 无法确认容器停止（NotReady 节点上的 Pod）
  3. 存储卸载卡住：卷 detach 失败
- 正规处理：修节点/修控制器让 finalizer 完成
- 强制手段（按强度递增）：
  1. `kubectl delete pod xxx --force --grace-period=0`
  2. 清 finalizer：`kubectl patch pod xxx -p '{"metadata":{"finalizers":[]}}' --type=merge`（**有数据风险**——存储未卸载时强清可能双挂载）
  3. 节点失联场景：先删 Node 对象（VM 已确认销毁时）
- 风险提示：强删后若真实容器还在跑 → 脑裂风险（StatefulSet 双主）——确认节点/容器真死再强删

**一句话答：** Terminating 卡住八成是 finalizer 在等清理完成——存储卸载失败或节点失联。正确姿势是先修根因，确实要强删时先 --force --grace-period=0，再不行就 patch 清掉 finalizer。但必须先确认节点上的容器真死了，否则强删后 StatefulSet 会在新节点拉起同名 Pod，出现双主脑裂。

### 76. 开发人员反馈 K8s 中应用访问慢，该如何排查？

**要点：**
- 分层定位（结合 RED 指标）：
  1. **确认范围**：所有用户还是个别人？所有接口还是特定接口？——定位入口
  2. **入口链路**：Ingress Controller 指标与日志（$request_time vs $upstream_response_time 分段）——网关慢还是后端慢
  3. **服务自身**：HPA 是否顶着 maxReplicas、CPU 限流（**throttled 指标**——requests 给太低的典型）、线程池/GC
  4. **依赖**：数据库慢查询、Redis 命中率、下游服务 RT
  5. **基础设施**：节点 CPU 争抢（混部节点）、网络策略/网络插件延迟、DNS 解析慢（CoreDNS 压力、ndots 引起的多余查询）
- K8s 特有嫌疑：**CPU limit 限流**（监控 container_cpu_cfs_throttled_periods_ratio）、DNS ndots:5 造成的解析放大、节点亲和导致的热点
- 工具：链路追踪（traceID 逐段看）、kubectl top、Prometheus 对比变更时间线

**一句话答：** 先缩小范围再分层排查：Ingress 日志里 request_time 和 upstream_response_time 一对比就切开网关和后端；K8s 特有的两个嫌疑要优先查——CPU limit 限流导致的性能虚低（看 throttled 指标），和 DNS ndots 配置引起的解析放大。全链路追踪有 traceID 的话一段一段看 span 最快。

### 77. 业务 Pod 频繁重启，该如何排查？

**要点：**
- 先分类重启原因：
  1. `kubectl describe pod` 看 **Last State**：
     - **OOMKilled（exit 137）**：内存 limit 不够或泄漏——监控 working set 与 limit 差值
     - **Error/非零退出**：应用异常——看日志
     - **探针失败 kill**：liveness 太严（超时短/阈值低）或应用冷启动慢——调 startupProbe
  2. 日志三处：`kubectl logs --previous`（上一次崩溃日志）、应用日志、节点 journal
- 常见根因榜单：内存 limit 过小 → OOM；liveness 配置过猛 → 重启风暴；依赖连不上启动失败 → CrashLoopBackOff；节点驱逐/抢占
- 修复配套：OOM 调 limit 时同步看 requests（影响调度和 QoS）、探针参数按 P99 启动时间设计、HPA 配合限流保护

**一句话答：** describe 的 Last State 直接分类：OOMKilled 就是内存不够或泄漏，exit 非零看 logs --previous 的崩溃现场，探针失败则查 liveness 是不是配太严。经验数据：一半以上的频繁重启是 limit 给小了和探针太敏感，改这两处前先看监控里内存水位和应用 P99 启动时间再动手。

### 78. 静态 Pod 是什么？有什么作用？

**要点：**
- 静态 Pod = **kubelet 直接管理、不经过 apiserver** 的 Pod：清单文件放 `/etc/kubernetes/manifests/`（或 --pod-manifest-path），kubelet 定期扫描自动创建/更新
- 特点：kubelet 单向管理（apiserver 里能看到**只读镜像**，但不能 kubectl 删改）；文件删=Pod 删
- 核心作用：**控制面自举**——kubeadm 集群的 apiserver/etcd/scheduler/controller-manager 全是静态 Pod：控制面组件自己故障时没有更高层管理，静态文件就是最后的兜底
- 运维：改控制面配置=改 manifest 文件（kubelet 自动应用）；排查时注意它和普通 Pod 的管理差异

**一句话答：** 静态 Pod 是 kubelet 绕过 apiserver 直接从本地清单文件拉起的 Pod，kubeadm 集群的 apiserver、etcd、scheduler 全都是——因为控制面自己挂了以后没有别的组件能救它，只能靠 kubelet 读文件这个最原始的机制兜底。改控制面配置就是改 /etc/kubernetes/manifests 下的 yaml。

### 79. Pod 中 pause 容器有什么作用？

**要点：**
- pause（infra 容器）：Pod 里**最先启动、默默无闻的基础容器**
- 两大作用：
  1. **持有网络命名空间**：Pod 所有容器共享 pause 的 netns（IP/端口）——业务容器崩溃重启不影响网络栈，IP 保持稳定（容器重启网络不抖）
  2. **充当 PID 1 收尸**：共享 PID namespace 时（默认 1.29+ 开启），pause 以 PID 1 运行回收孤儿进程——**防僵尸进程**
- 底层逻辑：Pod 的"共享环境"必须有个载体先活着——pause 就是那个载体（体积 ~300KB、永久睡眠）
- 排查视角：节点上 `crictl ps` 看到的 pause 容器是正常的，不是异常进程

**一句话答：** pause 是 Pod 的地基容器：它先启动并持有网络命名空间，其他容器加入它的网络栈——所以业务容器崩溃重启 IP 不会变；在共享 PID 模式下它还以 PID 1 身份负责回收孤儿进程。它就是一个睡大觉的小程序，但 Pod 的"共享"二字全靠它承载。

### 80. Kubernetes 准入控制器有什么用？

**要点：**
- 位置：API 请求过认证鉴权后、写入 etcd 前——**最后一道关卡**（可修改/可拒绝请求）
- 两类：
  - **MutatingAdmissionWebhook**：修改请求（注入 sidecar——Istio 的实现方式、默认值填充）
  - **ValidatingAdmissionWebhook**：校验并拒绝（策略引擎 OPA Gatekeeper/Kyverno 的执行点）
- 内置例子：NamespaceLifecycle（往不存在的 ns 建对象会被拒）、ResourceQuota（超 quota 拒绝）、ServiceAccount（自动挂 token）、LimitRanger
- 应用场景：强制镜像来自可信仓库、强制标签/资源限制、注入 sidecar/代理、禁止特权容器、配置审计标签
- 运维注意：webhook 故障=API 阻塞（failurePolicy 要区分 Fail/Open）、webhook 自身高可用（别让"守门人"单点）

**一句话答：** 准入控制器是请求进 etcd 前的最后一关，分两类：mutating 类改请求——Istio 注入 sidecar 就是这么实现的；validating 类拒请求——Gatekeeper 和 Kyverno 的策略都在这执行。运维要记住的关键点是 webhook 本身必须高可用，failurePolicy 设成 Fail 后 webhook 挂了全集群 API 都会阻塞。

### 81. kube-proxy 主要功能有哪些？

**要点：**
- 核心职责：**Service 的数据面实现**——把"虚拟 IP"变成真实转发
- 具体功能：
  1. watch Service/Endpoint 变化 → 生成转发规则（iptables/IPVS 模式）
  2. ClusterIP 转发：ClusterIP:Port → 随机/算法选 Pod → DNAT
  3. NodePort/LoadBalancer：节点端口监听 + 外部流量转发
  4. 会话保持（SessionAffinity ClientIP）
- 不做的事：七层路由（Ingress 的活）、健康检查主动探测（靠 readiness+Endpoint 更新——被动配合）
- 部署形态：DaemonSet 每节点一个；模式选择对大规模集群至关重要（IPVS）

**一句话答：** kube-proxy 就是 Service 的"路由器固件"：watch 到 Service 和 Endpoint 变化后，在节点上生成 iptables 或 IPVS 规则，把 ClusterIP、NodePort 的流量 DNAT 到真实 Pod。它只管四层，七层是 Ingress 的事；健康检查也不主动做，靠 readiness 驱动 Endpoint 列表更新。

### 82. kubectl top 命令的数据来源是哪里？

**要点：**
- 链路：**kubelet 内嵌 cAdvisor**（采集容器资源）→ **Metrics Server** 聚合（内存态短期数据）→ **Metrics API**（metrics.k8s.io）→ kubectl top 读取
- 指标口径：CPU = 窗口平均使用率；内存 = **working set**（含 page cache 中活跃部分，接近真实占用、大于 RSS）
- 与监控系统的关系：Prometheus 是独立采集（cadvisor/kube-state-metrics 的 exporter），**不经过 Metrics Server**——两者数字可能有差异（采集窗口不同）
- 未装 Metrics Server：top 报 error: Metrics API not available

**一句话答：** kubectl top 的数据链是：kubelet 里的 cAdvisor 采集、Metrics Server 聚合成 metrics.k8s.io API、kubectl 读取展示。注意内存指标口径是 working set 不是 RSS，和 Prometheus 采集的数字有窗口差异是正常的。Metrics Server 没装的话 top 命令直接报 API 不可用。

### 83. Pod 内存溢出，节点 OOM，如何排查？

**要点：**
- 区分两层 OOM：
  - **容器级 OOMKilled**：超 **cgroup limit**——exit code 137，describe 看 Last State；dmesg 里 "Memory cgroup out of memory"
  - **节点级 OOM**：整机内存耗尽，**内核 OOM Killer** 选进程杀——`dmesg | grep -i "out of memory"`、`journalctl -k`；K8s 里对应 kubelet 驱逐或 oom_score_adj 保护机制
- 排查步骤：
  1. 确认层级：容器 OOM 看监控的 container_memory_working_set vs limit 曲线——顶到 limit 就是它
  2. 泄漏还是突发：内存曲线缓慢爬升不回落=泄漏（pprof/jmap）；瞬时尖峰=大请求/批量加载
  3. 节点级：`kubectl top nodes`、节点 available 内存、有没有 BestEffort Pod 无节制
- 修复：容器 OOM→调 limit 或修泄漏；节点 OOM→配 requests/limits、QoS 分级、NodeOOM 时关键服务 oom_score_adj 保护
- 预防：VPA 建议、内存告警在 80% limit

**一句话答：** 先分清是容器超了自己的 cgroup limit 被杀，还是整机内存爆了内核 OOM Killer 出手——dmesg 里两种日志关键词不同。容器级看监控里 working set 贴没贴 limit、判断泄漏还是突发；节点级查谁没配 limit 在裸奔。修复对应：调 limit 修泄漏、补全 requests 让 QoS 分级保护关键服务。

### 84. kubectl debug 命令有什么作用？

**要点：**
- 官方排障工具（1.18+ alpha，1.25 beta）——**不改业务镜像**就能调试：
  1. **加容器调试**：`kubectl debug -it pod --image=busybox --target=app`——往运行中 Pod 注入排障容器（共享 PID/网络）；基础镜像太精简（distroless）时的救命稻草
  2. **复制 Pod 调试**：`kubectl debug pod/xxx -it --copy-to=debug-pod --container=app -- sh`——复制一份改命令（改 entrypoint 为 shell）在不影响原 Pod 下调试
  3. **节点调试**：`kubectl debug node/nodename -it --image=busybox`——起特权 Pod 挂载节点根文件系统（/host）查节点问题
- 价值：生产环境镜像极简（无 shell/工具）成趋势，debug 命令补上"临时工具"缺口
- 注意：注入的容器要控制权限（别默认 privileged）、用完即删

**一句话答：** kubectl debug 解决"生产镜像是 distroless 连 shell 都没有"的排障难题：可以往运行中的 Pod 注入一个带工具的排障容器共享进程和网络命名空间，或者复制一个 Pod 副本安全调试，还能对节点本身起特权调试容器挂载宿主文件系统。三种模式覆盖 Pod 内、副本、节点三层排障场景。

### 85. ResourceQuota 和 LimitRange 有什么区别？

**要点：**
- **ResourceQuota**：**命名空间总量配额**——限制"整个 ns 最多用多少"：CPU/内存 requests/limits 总量、PVC 数量与容量、对象数（Pod/Service 最多几个）
  - 例：prod ns 最多 100 个 Pod、总 CPU requests 200 核
- **LimitRange**：**单个对象的默认与边界**——给没写 resources 的 Pod 注入**默认值**、限制单个容器/PVC 的 min/max
  - 例：ns 里每个容器默认 requests 100m，max 4 核
- 配合关系：Quota 管"总盘子"，LimitRange 管"单个规格"+兜底默认值；**没有 LimitRange 的默认值，Quota 要求 Pod 必须显式声明 resources 才能创建**（配额计算需要）
- 排障：超 Quota 的报错在 create 的 error 里；Pod 卡 Pending 也可能因为 Quota 已满

**一句话答：** ResourceQuota 管命名空间的总配额——CPU 总量、Pod 总数、存储总量；LimitRange 管单个对象的规格——给不写资源的 Pod 自动补默认值、限制单个容器的上限。两者必须配套用：Quota 需要每个 Pod 声明资源才能计数，LimitRange 恰好提供这个默认值。

### 86. Kubelet 与 API Server 通信失败时，Pod 还能运行吗？

**要点：**
- **能继续运行**：kubelet 的 Pod 管理是**本地自治**的——已创建的 Pod 继续跑（探针、重启、本地生命周期照常）；这正是**节点自治**设计（网络分区时节点上业务不中断）
- 但会有这些影响：
  1. 节点状态上报中断 → apiserver 侧超时后节点变 **NotReady** → 打 NoExecute 污点 → **该节点 Pod 被驱逐重建到其他节点**（注意：kubelet 恢复后可能出现**双活冲突**风险窗口——kubelet 可能还没收到删除指令）
  2. 新 Pod 调度到该节点的指令收不到
  3. 日志/事件上报断
- 通信失败的常见原因：证书过期、网络/LB 故障、apiserver 过载
- 设计启示：不要在节点上放"强依赖 apiserver"的业务逻辑；StatefulSet 在脑裂场景要靠应用侧仲裁（DB 之类 raft/主从协议）

**一句话答：** 能跑——kubelet 对存量 Pod 是本地自治的，探针重启这些照常工作，这就是节点自治设计。但 apiserver 超时后节点会被标记 NotReady 并驱逐 Pod，引发重建；kubelet 恢复期间还可能出现旧 Pod 还在跑、新 Pod 已建的双活风险，所以有状态服务必须靠应用层仲裁机制防脑裂，不能指望 K8s 层。

### 87. PriorityClass 是什么？什么场景下使用？

**要点：**
- PriorityClass = **集群级优先级定义**（数值 -2^31~2^31-1，越大越优先）→ Pod 绑定 priorityClassName
- 两层作用：
  1. **调度排序**：Pending 队列里高优先级优先调度
  2. **抢占（Preemption）**：资源不够时，高优先级 Pod 可以**驱逐低优先级 Pod** 腾位子（被抢占者进 Pending 队列等位）
- 典型场景：
  - **系统组件保护**：kube-system 内置 system-cluster-critical/system-node-critical（coredns、kube-proxy）——资源紧张时不被业务挤死
  - **业务分级**：核心交易链路 > 辅助功能 > 离线任务/批处理
  - 资源回收：离线任务设低优先级+可抢占，实现在线业务的弹性借力
- 配套：preemptionPolicy（Never 可禁抢占）、PodDisruptionBudget 不影响抢占（管的是自愿驱逐）

**一句话答：** PriorityClass 给 Pod 分三六九等：调度时高优先级插队，资源不足时还能直接抢占低优先级的资源把对方赶回 Pending。典型用法是保护系统组件、核心交易服务设高优先级、离线任务设低优先级当"弹性垫背"——高峰期在线业务抢回资源，平时离线任务填满机器。

### 88. HPA 如何基于自定义指标实现扩缩容？

**要点：**
- 内置 resource 指标只有 CPU/内存；业务相关指标（QPS/队列长度/连接数）走 **custom.metrics.k8s.io API**
- 实现链路：
  1. 指标采集：Prometheus 抓应用/中间件指标
  2. **Prometheus Adapter**（或 KEDA）：把 Prometheus 查询映射成 custom.metrics API——HPA 就能读
  3. HPA 引用：

```yaml
metrics:
- type: Pods
  pods:
    metric: { name: http_requests_per_second }
    target: { type: AverageValue, averageValue: "1000" }
```

- **KEDA 方案**（更主流的新选择）：内置大量 scaler（Kafka lag、Redis 长度、云队列），支持**缩容到 0**；以 ScaledObject 生成 HPA
- 多指标并存：resource+custom 同时列，取最大需求
- 坑：指标抖动→副本震荡（配 stabilizationWindow）；指标断供→HPA 停摆（保底 minReplicas）

**一句话答：** 自定义指标扩缩容的标准链路是：Prometheus 采集业务指标，经 Prometheus Adapter 转换成 custom.metrics.k8s.io API，HPA 配置 type 为 Pods 的指标引用它按目标值扩缩。现在更推荐 KEDA——自带 Kafka 队列深度、Redis 长度这些现成 scaler，还支持缩容到零。多指标同时配时按最大需求算，稳定窗口防抖动。

### 89. K8s 审计日志如何启用？有什么作用？

**要点：**
- 启用：apiserver 配置：
  1. 审计策略文件（--audit-policy-file）：按级别过滤——**None/Metadata/Request/RequestResponse**（资源消耗递增）
  2. 后端：--audit-log-path（文件+轮转）或 --audit-webhook（外发到日志系统）
- 策略示例：敏感资源（secrets）记 Metadata 不记 body（防泄漏+省空间）、写操作记 Request、读操作 Metadata、健康检查 None
- 作用：
  - **安全溯源**：谁在什么时候从哪删了 Deployment/改了 RBAC/读了 Secret
  - **合规审计**：等保/SOC2 要求的操作留痕
  - **故障排查**：变更时间线还原（配合监控系统对比）
  - 告警联动：高危操作（删 namespace、改 RBAC、exec 进生产容器）实时告警
- 存储：外发到 ELK/Loki 持久化——文件方式会滚动丢失

**一句话答：** 审计日志在 apiserver 层记录所有 API 请求：谁、何时、从哪、对什么资源做了什么。启用分两步：写策略文件定义哪些操作记到什么级别——Secret 这类只记元数据不记内容，然后输出到文件或 webhook 外发到 ELK。它的价值是安全溯源和合规留痕，配合告警还能对删 RBAC、进容器这类高危操作实时报警。

### 90. 什么是 K8s 的 Finalizer？有什么作用？

**要点：**
- Finalizer = 对象 metadata.finalizers 数组里的**删除前钩子**：有 finalizer 的对象删了只会打 deletionTimestamp，**控制器完成清理并移除 finalizer 后才真正删除**
- 作用：
  - **级联清理**：确保"关联资源先清理"——namespace 的 deletion 依赖各资源 finalizer；PVC 保护（还在被 Pod 用时不让删）
  - **外部资源回收**：删 K8s 对象时同步删外部资源（云 LB、云盘、DNS 记录）——service.kubernetes.io/load-balancer-cleanup
  - 防误删：数据类资源强制走确认流程
- 经典运维场景：**Terminating 卡死**——finalizer 的控制器没了/bug 了，没人移除钩子 → 手动 patch 清 finalizer（确认清理逻辑已无意义时）
- 设计注意：finalizer 逻辑必须幂等、控制器必须可靠——否则就是卡删除制造机

**一句话答：** Finalizer 是对象的删除守门员：打了 finalizer 的资源收到删除只先标 Terminating，等控制器做完级联清理——卸载存储、释放云 LB——把 finalizer 从列表移除才真正消失。它的价值是保证删 K8s 对象时外部资源不遗留；反过来控制器挂了它就是 Terminating 卡死的元凶，这也是运维手动清 finalizer 的经典场景。

### 91. PV 中数据如何定时备份？

**要点：**
- 方案矩阵：
  1. **Velero + 存储快照插件**（K8s 原生生态标准）：Schedule 资源定时备份（对象+PV 数据走 CSI VolumeSnapshot 到对象存储）
  2. **CSI VolumeSnapshot + CronJob**：K8s 原生快照资源（VolumeSnapshotClass），CronJob 定时触发快照——只快照不搬运，恢复快；依赖后端存储支持（云盘/Ceph）
  3. **应用层备份**（最可靠）：数据库自带工具（mysqldump/xtrabackup/pg_dump）跑在 CronJob 里，备到对象存储——**与存储层解耦，可跨平台恢复**
  4. 文件级：Restic/Kanister 挂载卷打包上传
- 策略：RPO 定频率、保留策略（7 日+4 周+12 月）、**异地副本**
- 铁律：**恢复演练**定期做——没恢复过的备份不叫备份
- 一致性提醒：块快照对数据库要配合应用冻结（或依赖 crash-consistent+binlog 补齐）

**一句话答：** 主流三招：Velero 做 K8s 层定时备份，对象加数据一起到对象存储；CSI 快照加 CronJob 做存储层快照，快但依赖后端能力；最可靠的是应用层备份——数据库自己的备份工具跑在 CronJob 里。无论选哪个，恢复演练是必须的验收标准，而且块快照对数据库要注意一致性，最好配合 binlog 补齐。

### 92. K8s 中如何管理有状态的中间件（如 Redis、Kafka）？

**要点：**
- 资源选型：**StatefulSet**（稳定身份+有序+独立 PVC）+ **Headless Service**（点名访问）
- Operator 化管理（强烈建议）：**Strimzi**（Kafka）、Redis Operator/RedisEnterprise——把扩缩容、主从切换、故障恢复、配置变更编码成控制器，别裸管 StatefulSet
- 存储设计：Local PV/云盘（IO 敏感）、每副本独立 PVC、**回收策略 Retain**（防误删数据）
- 网络设计：Headless Service 点名 + 普通 Service 做客户端接入；反亲和把副本打散到不同节点/机架
- 运维纪律：
  - 扩缩容方向谨慎（Kafka 缩容要动 partition 迁移）
  - 滚动更新用 partition 控制、PDB 保证 quorum 不破
  - 监控：主从延迟、分区均衡、磁盘水位
  - 备份：应用层备份为主，快照为辅
- 什么时候不用 K8s 管：超大规模核心 Kafka 集群（专用集群/云托管 MSK 更稳）

**一句话答：** 标准姿势是 StatefulSet 加 Headless Service 给稳定身份和存储，然后一定要配 Operator——Strimzi 管 Kafka、各家 Redis Operator——把主从切换扩缩容这些复杂运维编码掉。纪律三条：存储 Retain 防误删、PDB 保证副本数底线、反亲和打散副本。超大规模核心集群也可以直接考虑云托管服务，不逞强。

### 93. 本地存储（Local PV）有什么优缺点？

**要点：**
- Local PV = 挂载**节点本地磁盘/NVMe** 的 PV（CSI local 卷或 local-path-provisioner）
- **优点**：
  - **性能最强**：本地盘无网络开销，延迟最低——数据库/Kafka 高 IO 场景首选
  - 成本低（不买云盘/共享存储）
- **缺点**：
  - **节点绑定**：Pod 只能调度到磁盘所在节点——节点挂=数据不可用（单点），故障恢复=数据迁移
  - **无高可用**：需应用层副本机制（数据库主从/RAID）补足
  - 扩容不便：加盘要动节点；容量受单机限制
  - 节点维护影响大（drain 要考虑数据）
- 配套要求：**调度感知**（volumeNodeAffinity、拓扑）、标签管理磁盘、监控盘水位、数据层做副本
- 适合：性能敏感 + 应用自带副本（ETCD/Kafka/Cassandra）；不适合：单副本重要数据

**一句话答：** Local PV 的卖点是性能——本地 NVMe 无网络开销，数据库和消息队列的 IO 首选；代价是数据被钉死在节点上——节点挂数据不可用，没有任何高可用。所以它必须搭配应用层副本机制使用，比如 Kafka 自身的多副本。用它的团队还要把调度感知和盘位管理做好。

### 94. Pod 之间如何实现的网络通信？

**要点：**
- 模型约定：**所有 Pod 直接 IP 互访、无 NAT**（跨节点也是）——扁平网络
- 同节点：veth pair 都挂在 **cni0/cbr0 网桥**——二层直接通
- 跨节点（按 CNI 实现）：
  - **Overlay**（Flannel VXLAN/Calico IPIP）：报文封装在宿主 UDP/IP 隧道里传输
  - **路由**（Calico BGP）：宿主机当路由器直接路由 Pod 网段
- Pod → Service：走 kube-proxy 规则 DNAT（见 68 题）
- 出集群：SNAT 走节点 IP
- 安全控制：NetworkPolicy（CNI 实现）按 label 控制访问——默认全通，策略显式限制

**一句话答：** K8s 承诺所有 Pod 一个扁平 IP 网络互通无 NAT：同节点走网桥二层直达，跨节点由 CNI 解决——要么 VXLAN 隧道封装，要么 BGP 路由直发。访问 Service 再叠加 kube-proxy 的 DNAT。安全隔离靠 NetworkPolicy，这也是选 CNI 时必须确认的能力项。

### 95. K8s 多租户隔离有哪些主流实现方案？

**要点：**
- 分层隔离（软到硬）：
  1. **命名空间 + RBAC + Quota**（软隔离/信任团队）：ns 分租户、RoleBinding 限权限、ResourceQuota/LimitRange 限资源——成本最低，适合内部多团队
  2. **NetworkPolicy + PSA**（Pod Security Admission）：网络隔离+安全基线（restricted profile）
  3. **节点池隔离**：租户专属节点池+亲和绑定——资源物理区分
  4. **Namespace 独立节点+污点**（中强度）：专用硬件、GPU 场景
  5. **集群级硬隔离**：每租户独立集群+统一管理（Karmada/ArgoCD）——最强，成本最高
- 数据面：存储配额、PVC 计费标签
- 控制面：审计按租户切分、准入策略（Gatekeeper 强制命名规范/资源上限）
- 选型直觉：内部信任环境 ns 级起步；对外/合规场景上集群级

**一句话答：** 隔离强度从软到硬一套阶梯：命名空间加 RBAC 加 Quota 是起步套餐，适合内部团队；再叠 NetworkPolicy 和 Pod 安全准入做网络与安全基线；需要资源独占就上专属节点池；合规或不可信租户直接独立集群统一管理。选型跟着信任等级走——租户越不可信，隔离边界越往基础设施层下沉。

### 96. Pod 安全上下文（SecurityContext）有哪些应用场景？

**要点：**
- Pod/容器级安全配置：
  - **runAsNonRoot/runAsUser**：强制非 root 运行——镜像被入侵后权限受限
  - **readOnlyRootFilesystem**：根文件系统只读——防篡改（配合 emptyDir 写临时数据）
  - **allowPrivilegeEscalation: false**：禁 setuid 提权
  - **capabilities drop ALL + 按需 add**：最小权限（如 NET_BIND_SERVICE 绑低端口）
  - **fsGroup**：挂载卷属组修正（解决 PVC 权限）
  - seccompProfile / seLinuxOptions：系统调用过滤
- 集群级配合：Pod Security Admission（namespace 打 restricted label 强制基线）、Gatekeeper/Kyverno 统一策略
- 典型场景：生产工作负载基线（非 root+只读根+drop all）、需要绑 80 端口的容器用 capability 代替 root、数据库类配 fsGroup

**一句话答：** SecurityContext 是给容器上安全锁：非 root 运行、根文件系统只读、禁提权、capability 全删按需加、修正挂载卷属组。实践上生产基线就是"非 root 加只读根加 drop ALL"，个别需要绑低端口的服务用 capability 补而不是开 root。集群层面用 Pod Security Admission 把这套基线变成强制标准。

### 97. Pod 如何自定义内核参数？

**要点：**
- 内核参数分两层（sysctl）：
  - **安全（Namespaced）参数**：net.*（ip_forward、somaxconn、tcp_tw_reuse 等）——Pod 隔离的，可 Pod 级自定义
  - **非安全（Non-namespaced）**：vm.swappiness、kernel.*——节点全局，**Pod 不许改**
- Pod 级设置（Namespaced）：

```yaml
securityContext:
  sysctls:
  - name: net.core.somaxconn
    value: "65535"
```

- kubelet 需放开白名单：`--allowed-unsafe-sysctls`（unsafe 参数）
- 非安全参数的正确姿势：**DaemonSet 特权容器改节点**（nsenter/sysctl -w）、镜像构建时改、或 init 容器 + privileged
- 替代思路：net 类需求尽量用 K8s 能力替代（如端口用 Service 而不是改 ip_forward）

**一句话答：** 内核参数分两类：带 namespace 的 net 类可以在 Pod 的 securityContext 里直接配， kubelet 白名单要放行；vm、kernel 这类全局参数 Pod 无权改，只能用特权 init 容器或 DaemonSet 在节点层设置。设计上优先用 K8s 自身能力解决问题，少动内核参数——动得越少，节点越一致。

### 98. K8s 的 kubeconfig 文件有什么作用？

**要点：**
- kubeconfig = **kubectl/apiserver 客户端的连接配置**：集群（地址+CA）、用户（证书/token/凭证）、上下文（cluster+user+namespace 组合）
- 多集群切换：一个文件多 context，`kubectl config use-context prod` / `kubectl config get-contexts`
- 默认路径 ~/.kube/config；KUBECONFIG 环境变量可叠加多文件
- 安全管理：
  - 权限即风险：文件=登录凭证，chmod 600、不进 Git
  - **最小化签发**：按人/按服务签 SA token/证书，短期凭证优先（OIDC/TokenRequest）
  - 审计与吊销：配合 RBAC 与证书吊销机制
- 排障：KUBECONFIG 冲突、current-context 指错集群——"删错集群"事故的经典根源，操作前 kubectl config current-context 确认

**一句话答：** kubeconfig 是 kubectl 的登录配置文件：记录连哪个集群、用什么身份、默认在哪个命名空间，多环境靠 context 切换。安全上它就是钥匙——600 权限、绝不进 Git、按人签发最小权限凭证。运维保命习惯：执行高危操作前先 kubectl config current-context 确认自己连的是哪个集群。

### 99. 网络策略（NetworkPolicy）是如何实现 Pod 间的访问控制？

**要点：**
- 机制：**CNI 插件在数据面实现**（iptables/eBPF）——K8s 只定义规则 API，插件执行
- 规则语义：
  - **默认全通**；Pod 被任何 policy 选中 → **白名单模式**（未明确允许的都拒绝）
  - 三要素选择：podSelector（管谁）、ingress/egress 规则（放行谁：podSelector/namespaceSelector/ipBlock）、端口协议
- 示例（只允许 frontend 访问 db 的 5432）：

```yaml
kind: NetworkPolicy
spec:
  podSelector: { matchLabels: { app: db } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: frontend } }
    ports: [{ port: 5432 }]
```

- 前提：CNI 必须支持（**Flannel 不支持**——规则写了没人执行，假安全！）；Cilium/Calico 全支持
- 进阶：namespaceSelector 跨 ns 控制、egress 限制出网（防数据外带）、默认拒绝全命名空间做基线

**一句话答：** NetworkPolicy 是白名单式访问控制：Pod 一旦被策略选中，没显式放行的流量全部拒绝。规则用 label 选源和目标加端口，K8s 只管定义，真正执行的是 CNI 插件——所以最大的坑是用了不支持 NetworkPolicy 的插件，规则看着写了实际没人执行，是假安全。落地建议从"默认拒绝、按需放行"的命名空间基线开始。

### 100. 自建 K8s 集群与云托管K8s（ACK/EKS）对比，各自优缺点？

**要点：**
- **云托管（ACK/EKS/GKE）**：
  - 优：控制面托管免运维（HA/证书/etcd）、与云资源深度集成（LB/存储/网络开箱即用）、弹性节点池/autoscaler 成熟、SLA 保障
  - 缺：费用（控制面费+云资源溢价）、版本升级节奏受厂商、深度定制受限（kubelet 参数/内核）、锁定风险
- **自建（kubeadm/rancher）**：
  - 优：全栈可控（定制内核/网络/存储）、成本可能更低（包年物理机/私有化合规）、可迁移性强
  - 缺：控制面全部自己背（etcd 运维、证书、HA）、版本升级与安全补丁全人工、需要专业团队（2-3 人起）
- 混合形态：**托管控制面+自管节点**（ACK 专有/自建节点池）、K3s 边缘自建+云上托管混合
- 决策因子：团队能力、合规要求、成本结构、规模与稳定性诉求——**团队能力不足时托管是性价比最高的选择**

**一句话答：** 云托管买到的是省心：控制面高可用证书升级全托管，云上 LB 存储开箱即用，代价是费用和厂商绑定；自建换来的是完全可控和潜在成本优势，代价是 etcd 证书升级这些脏活全自己扛、需要成建制的团队。我的建议按团队能力决策：没有专人维护控制面就上托管，把精力留给业务编排。

### 101. 简述 K8s 控制器的工作流程？

**要点：**
- **声明式控制循环（Reconcile Loop）**——K8s 的灵魂设计：
  1. **Informer 机制**：ListWatch——启动全量 list 拉现状 + 持续 watch 增量事件；本地缓存 + **DeltaFIFO 队列**
  2. 事件入 **Workqueue**（限速/去重）
  3. **Reconcile**：worker 从队列取 key → **对比期望状态（Spec）与实际状态（Status）** → 执行补齐动作（建/删/改资源）→ 失败重新入队（限速重试）
- 关键特性：
  - **水平触发而非边沿触发**：Reconcile 只看"当前差什么"，不关心"发生过什么"——错过事件也能自愈
  - **幂等**：重复执行结果一致（重试安全）
  - **最终一致**：不追求瞬时，收敛即正确
- 例：Deployment 控制器发现实际副本 3、期望 5 → 建 2 个 Pod；Node 控制器发现节点超时 NotReady → 驱逐 Pod
- 你自己写的 Operator 就是用同一套 controller-runtime 框架实现这个循环

**一句话答：** 所有控制器跑同一个模式：Informer 通过 ListWatch 维护本地缓存把变更事件丢进队列，worker 取出后执行 Reconcile——对比期望状态和实际状态，差什么补什么，失败限速重试。两大设计支柱是水平触发加幂等：控制器不关心事件历史只对齐当下，所以丢事件、组件重启都能自愈，这正是声明式架构的精髓。

## 云原生面试题

### 1. 云原生是什么？你是什么理解的？

**要点：**
- CNCF 官方定义：云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中，构建和运行**可弹性扩展**的应用。
- 代表技术：**容器、服务网格、微服务、不可变基础设施、声明式 API**
- 我的三层理解：
  1. **方法论层**：应用天生为云设计（弹性、分布式、容错），而不是把老应用搬上云
  2. **技术层**：K8s 为调度底座、容器为交付单元、声明式 API 为管理方式
  3. **组织层**：DevOps 文化配套——开发运维一体化、自动化一切

**一句话答：** 云原生不是"用了云"而是"为云而生"：应用从设计之初就基于容器、微服务、声明式 API 这些假设构建，天然具备弹性伸缩和故障自愈能力。判断标准很简单——你的应用敢不敢随时被杀掉重建，敢，就是云原生；不敢，就还是传统架构。

### 2. 传统应用与云原生应用有什么区别？

**要点：**
- **配置方式**：传统改配置文件重启；云原生配置外部化（环境变量/ConfigMap），实例可随意替换
- **状态管理**：传统本地存储/本地 session；云原生无状态+状态外置（DB/Redis）
- **部署单元**：传统安装包/手工部署；云原生容器镜像，不可变
- **扩缩容**：传统买机器手工加；云原生 HPA 自动水平伸缩
- **故障处理**：传统人工修复；云原生声明式自愈——挂了重建
- **依赖环境**：传统环境耦合（依赖装在机器上）；云原生自带依赖（镜像）

**一句话答：** 核心区别是"可替换性"：传统应用像养的宠物——起名字、生病了治好它；云原生应用像牲口——坏了直接换一头。能这样做的背后是无状态化、配置外部化、不可变镜像三个前提，换来的是弹性伸缩和故障自愈这些自动化能力。

### 3. 什么是"不可变基础设施"？

**要点：**
- 理念：服务器/容器**一旦部署就不再修改**——要变更不 patch，而是构建新镜像、重新部署、替换旧的
- 对比传统：可变基础设施=登录机器改配置打补丁——环境漂移（snowflake server）、"为什么这台和那台不一样"
- 优势：环境一致性（每个实例从同一镜像启动）、可回滚（回到旧镜像）、可重现（Git+Dockerfile 描述一切）
- 实践载体：容器 + 声明式编排（K8s 不允许"进去改一下"——改了重建就没了）

**一句话答：** 不可变基础设施就是"东西坏了换掉而不是修好"：应用打成镜像后只读，任何变更都通过构建新镜像重新部署完成。它消灭了配置漂移和雪花服务器两大运维顽疾——所有实例行为一致，回滚就是切回旧镜像，整个系统的状态都可以从 Git 和镜像仓库完整推导出来。

### 4. 云原生应用架构涉及到哪些技术？

**要点：**
- **运行底座**：容器（Docker）+ 编排（Kubernetes）
- **微服务与治理**：微服务拆分、API 网关、服务网格（Istio）、注册发现
- **交付**：CI/CD、GitOps（ArgoCD）、不可变镜像
- **可观测性**：Metrics（Prometheus）+ Logging（ELK/Loki）+ Tracing（SkyWalking/Jaeger）
- **弹性**：HPA/弹性伸缩、限流熔断降级
- **数据**：分布式存储、消息队列、缓存
- **安全**：零信任、mTLS、策略即代码（OPA）

**一句话答：** 技术版图按四层记：底座是容器加 K8s 编排，架构层是微服务加服务网格，交付层是 CI/CD 加 GitOps，运维层是三支柱可观测性加自动化弹性。每一层都有标准化的开源事实标准，云原生工程本质上是把这些组件组装成适配自己业务的一台机器。

### 5. 云原生应用如何实现弹性扩展和高可用性？

**要点：**
- **弹性扩展**：
  - 应用无状态（可水平复制的前提）
  - HPA 按 CPU/内存/自定义指标自动扩缩
  - VPA/Cluster Autoscaler 节点层弹性
  - 无状态化+异步削峰（MQ）配合
- **高可用**：
  - 多副本+反亲和打散（跨节点/跨可用区 topologySpread）
  - 健康检查+自愈（探针+控制器重建）
  - PDB 保障滚动与故障时的最低副本
  - 多可用区部署、PodDisruptionBudget、优雅终止不丢流量
- 验证：混沌工程主动注入故障验证 HA 真实有效

**一句话答：** 弹性的前提是无状态——实例可以随意增删，HPA 按指标自动调整副本数，节点不够 Cluster Autoscaler 补。高可用靠多副本加拓扑打散、探针自愈、PDB 保底和优雅终止。这些能力不能只配置不验证——定期混沌演练，才知道故障来了系统真的扛得住。

### 6. 微服务在设计时如何适配云原生环境？

**要点：**
- **无状态设计**：session/缓存/文件全部外置（Redis/OSS）——实例可随时替换
- **配置外部化**：环境变量/配置中心注入，一份镜像跑多环境
- **优雅启停**：快速启动（ readiness 探针配合）、SIGTERM 优雅退出排水、幂等重试
- **健康检查**：实现 liveness/readiness 端点——让平台接管生命周期
- **日志与追踪**：输出 stdout（不写本地文件）、全链路 traceID、结构化日志
- **弹性通信**：超时/重试/熔断内建、防雪崩
- **12-Factor**：以上原则的系统化总结（代码库/依赖/配置/后端服务/并发/易处理等）

**一句话答：** 云原生适配就是让应用学会"被平台管理"：无状态可替换、配置外部化、日志走 stdout、暴露健康检查端点、优雅启停配合平台排水、通信自带超时熔断。系统化的方法论就是 12-Factor App——十二条原则基本涵盖了云原生应用的设计契约。

### 7. 服务网格（Service Mesh）解决了什么问题？

**要点：**
- 解决：微服务通信的**治理逻辑**从业务代码中剥离——超时重试、熔断、加密、灰度路由、遥测，原来靠 SDK（Spring Cloud）侵入业务
- 架构：**Sidecar 模式**——每个 Pod 旁挂代理（Envoy），流量劫持经过代理，治理逻辑在代理层实现；控制面（Istiod）统一下发配置
- 收益：
  - **语言无关**：Go/Java/Python 统一治理，不用每语言维护 SDK
  - **升级解耦**：治理能力升级不碰业务代码
  - 统一观测：全网格流量自动埋点
- 代价：资源开销（每 Pod 一个 sidecar）、延迟增加（多两跳）、运维复杂度（网格自身要运维）
- 演进：sidecar-less（Cilium mesh）降低开销

**一句话答：** 服务网格把微服务通信治理从代码里抽出来放进 sidecar 代理：业务代码不管熔断、加密、灰度这些事，全部由 Envoy 在流量经过时执行，控制面统一指挥。最大的价值是语言无关和升级解耦——代价是每 Pod 多一个代理的资源开销和一跳延迟。库和网格的取舍本质是侵入式换非侵入式。

### 8. 服务网格如何进行流量管理？

**要点：**
- 数据面 Envoy 劫持进出流量（iptables/eBPF 重定向）→ 控制面下发路由规则
- Istio 流量管理四件套（VirtualService + DestinationRule）：
  - **路由规则**：按权重分流（灰度 90/10）、按 header/uri 匹配路由（灰度指定用户）
  - **故障注入**：主动注入延迟/错误做混沌测试
  - **超时与重试**：网格层统一配置，代码零侵入
  - **熔断**：DestinationRule 连接池+异常检测（连续错误摘除实例）
- 全链路灰度：header 染色贯穿所有服务
- 流量镜像：生产流量复制到新版本影子运行（不动真实响应）

**一句话答：** 网格的流量管理是在代理层按规则重写流量路径：VirtualService 定义"什么请求去哪"——按权重做灰度、按 header 做全链路染色；DestinationRule 定义"怎么对待后端"——连接池、熔断摘除。还能主动注入故障做混沌演练、做流量镜像。这些全部声明式下发，业务代码一行不改。

### 9. 无服务器架构（Serverless）是什么？与云原生有什么关系？

**要点：**
- Serverless = **FaaS（函数即服务）+ BaaS（后端服务托管）**：开发者只写函数，平台管资源分配、伸缩、运维——**按实际执行计费**（不是按机器时间）
- 特征：免运维、自动伸缩（含缩到 0）、事件驱动（HTTP/队列/定时触发）、毫秒级计费
- 局限：**冷启动延迟**（首请求慢）、执行时长限制、有状态难做、厂商锁定
- 典型：AWS Lambda/阿里 FC/腾讯 SCF；K8s 侧：Knative（基于 K8s 的 Serverless 平台）
- 与云原生关系：Serverless 是云原生的**延伸形态**——把 K8s 的"平台管调度"推进到"平台管一切"，开发者只管业务逻辑；BaaS（托管数据库/队列）配合构成完整无服务器体验

**一句话答：** Serverless 就是开发者只写函数、平台包办其余：自动伸缩到零、按执行时间计费、事件驱动触发。它是云原生理念的极致延伸——K8s 把运维从机器层解放到集群层，Serverless 直接把资源层也藏起来了。代价是冷启动、执行限制和厂商锁定，适合突发流量、轻量事件处理这类场景，不太适合长时稳定负载。

### 10. 限流、熔断和降级是什么意思？怎么实现的？

**要点：**
- 三兄弟分工：
  - **限流**：入口控制——超出容量的请求直接拒绝（保护自己）；算法：令牌桶、漏桶、滑动窗口计数
  - **熔断**：下游故障时的自保——错误率/慢调用超阈值就"跳闸"，一段时间内请求快速失败不再真调（防雪崩+给下游喘息）；半开探测自动恢复
  - **降级**：兜底策略——非核心功能关掉或返回预设值（关闭推荐、返回缓存数据、简化流程），保核心链路
- 实现：单机 SDK（Sentinel/Resilience4j/Hystrix）、网格层（Istio outlierDetection）、网关层（APISIX 限流）、分布式限流（Redis+Lua）
- 配置原则：阈值靠压测得出、分级预案文档化、演练验证

**一句话答：** 限流挡门外的——超过容量的请求直接拒绝保护自己；熔断管下游——对方挂了就跳闸快速失败，防止自己被拖死还给它喘息时间；降级保核心——系统吃紧时关掉推荐评论这类边缘功能，把资源让给交易主链路。三者合起来就是一套"过载生存策略"，关键是阈值用压测数据定、预案要演练。

### 11. 什么是 有状态 / 无状态应用？

**要点：**
- **无状态**：实例不保存会话/数据——任何实例可处理任何请求，随意增删替换（Web/API 层典型）
- **有状态**：实例保存状态并依赖它——本地存储（数据库数据）、身份（Kafka broker 的分区归属、ZK 节点编号）、集群拓扑（主从关系）
- 判断方法：**杀掉一个实例再拉一个新的，业务无感知=无状态**；新实例需要"继承"旧实例的数据/身份才能工作=有状态
- 云原生处理：无状态用 Deployment 随意伸缩；有状态用 StatefulSet（稳定身份+独立存储）+ Operator（复杂运维）
- 架构方向：尽量把应用做成无状态，状态推给专业的状态系统（DB/缓存/MQ）

**一句话答：** 判断标准就一条：杀掉实例换新的，业务有没有感知。无状态实例像标准件随便换，天生适合弹性伸缩；有状态实例有身份有数据，需要 StatefulSet 给稳定身份和存储，还得靠 Operator 管复杂运维。架构设计上永远把状态往外推——推给数据库和缓存，让应用自己保持无状态。

### 12. GitOps 的核心理念是什么？

**要点：**
- 四原则（OpenGitOps）：
  1. **声明式**：整个系统状态用声明式描述（YAML/HCL）
  2. **版本化+不可变**：状态存 Git，Git 历史即变更历史——Git 就是唯一事实源（single source of truth）
  3. **自动拉取（Pull 模型）**：集群内 agent（ArgoCD/Flux）主动拉取 Git 并对齐实际状态——而不是 CI 推到集群
  4. **持续调和**：实际状态漂移（有人手改集群）→ 自动拉回 Git 声明的状态（或告警）
- 收益：变更可审计（PR 评审）、可回滚（git revert）、可恢复（Git 重建集群）、环境一致性
- 文化含义：运维变更也走 PR——像代码一样评审

**一句话答：** GitOps 的核心是"Git 是唯一事实源"：集群期望状态全部声明式地存在 Git 里，集群内的 agent 持续对比并自动对齐，任何人手改集群都会被拉回去或告警。由此带来四个能力：变更走 PR 有评审、回滚就是 git revert、灾难恢复从 Git 重建、整个系统状态可审计。

### 13. CI/CD 与 GitOps 有什么区别？

**要点：**
- **CI/CD**：持续集成+持续交付/部署——流水线自动化"构建-测试-发布"过程；传统模式是 **Push**：CI 跑完把制品/配置推到环境
- **GitOps**：持续**部署**的一种实现模式——**Pull** 模型：集群内 agent 从 Git 拉取期望状态对齐；CI 只负责构建镜像和更新 Git（部署动作由 agent 完成）
- 关系：GitOps 是 CD 的演进形态，不替代 CI——典型组合：CI（Jenkins/GitLab CI）构建镜像 → 改 Git 里的 manifest → **ArgoCD** 同步到集群
- 对比点：
  - 凭证安全：Push 需 CI 持有集群凭证（攻击面）；Pull 集群自主拉取，CI 不碰集群
  - 状态管理：Push 部署完就不管了；Pull 持续调和防漂移
  - 可审计：GitOps 天然 Git 全历史

**一句话答：** 区别在部署动作的方向：传统 CI/CD 是 push——流水线推着部署，部署完与源不再同步；GitOps 是 pull——CI 只负责构建镜像并更新 Git，集群内 agent 持续拉取对齐。GitOps 不取代 CI 而是升级 CD：凭证不出集群更安全，漂移自动修正，变更历史天然在 Git。

### 14. Argo CD 如何实现 K8s 应用的持续部署？

**要点：**
- 架构：ArgoCD 跑在集群内，watch Git 仓库（声明式 manifest/Helm/Kustomize）→ 对比集群实际状态 → **同步（Sync）**使一致
- 工作流：开发提交镜像版本变更到 Git → ArgoCD 检测漂移 → 自动或手动（审批）sync → 应用更新
- 核心概念：
  - **Application**：Git 路径+目标集群+目标 ns 的三元组
  - **Sync 策略**：manual（人工确认）/auto（自动+prune+selfHeal）
  - **健康状态**：内置资源健康评估，对接通知（钉钉/Slack）
- 进阶能力：**App of Apps** 管理大量应用、ApplicationSet 多集群分发、Sync Waves 编排部署顺序（先 DB 后应用）、Rollback 一键回 Git 版本
- 漂移处理：手改集群会被纠正（selfHeal）或标记 OutOfSync 告警——纪律：改 Git 不改集群

**一句话答：** ArgoCD 就是在集群里跑的 GitOps agent：watch Git 里的声明式配置，持续对比集群实际状态，不一致就同步对齐——自动模式配合 selfHeal 连手工改动都会纠正回来。工程上靠 Application 管应用、Sync Wave 控部署顺序、ApplicationSet 铺多集群，回滚就是 revert Git 提交。

### 15. 什么是可观测性（Observability）？

**要点：**
- 定义：从系统**外部输出**推断系统内部状态的能力——不只是"看得见"，是"问得出来"
- 可观测 vs 监控：监控是"预设指标是否越线"（已知问题）；可观测是"面对未知问题能提出任意查询定位"（未知问题）——分布式系统故障形态爆炸，监控覆盖不了所有
- 三大支柱：
  - **Metrics**：聚合数值（QPS/延迟/错误率）——快、便宜、适合告警与趋势
  - **Logging**：离散事件详情——信息最全、成本高
  - **Tracing**：请求在分布式系统的完整路径——定位跨服务慢/错
- 关联：三者通过 traceID/exemplar 关联——从指标异常跳到 trace 再跳到日志

**一句话答：** 可观测性是"从外部输出推断内部状态"的能力，比传统监控更进一步：监控回答预设问题"CPU 高不高"，可观测回答任意问题"为什么这个用户这笔请求慢了"。实现靠三支柱——指标管趋势和告警、日志管细节、链路管路径，三者用 traceID 串起来，从一个异常能一路查到根因。

### 16. 传统监控与云原生可观测性有什么区别？

**要点：**
- 传统监控：
  - 对象是**静态主机/网络设备**（IP 固定、长期存活）
  - 手段：SNMP/Agent、阈值告警、Zabbix 代表
  - 问题域：资源是否够、设备是否死
- 云原生可观测：
  - 对象**动态 ephemeral**（Pod 秒级生死、IP 随机、服务常变）
  - 手段：标签维度（label-driven）的多维数据、聚合分析、分布式追踪、服务拓扑自动发现
  - 问题域：哪个服务哪个接口哪个版本的哪次请求出的问题
- 关键差异：静态阈值→动态基线；单机视角→拓扑视角；已知故障→未知探索；事后→事前（SLO/错误预算）

**一句话答：** 根本差异是监控对象从静态变成动态：传统监控盯固定 IP 的主机设备，云原生盯秒生秒死的 Pod——所以必须转向基于标签的多维数据模型和自动服务发现。另一个跃迁是目的升级：传统监控回答"资源够不够"，可观测性要回答"哪个服务的哪条链路出了什么问题"——没有追踪和标签维度根本无解。

### 17. 云原生可观测性的三大核心支柱（Metrics + Tracing + Logging）如何实现？

**要点：**
- **Metrics**：Prometheus（拉模型+PromQL）+ Grafana 可视化 + Alertmanager 告警；大规模用 Thanos/Mimir 长期存储与联邦
- **Tracing**：应用埋点 SDK/OpenTelemetry SDK → Collector → 后端（Jaeger/Tempo/SkyWalking）；上下文通过 HTTP header（W3C TraceContext）跨服务传播
- **Logging**：采集（Filebeat/Fluent Bit DaemonSet）→ 传输 → 存储（ES/Loki）→ 检索；K8s 场景日志走 stdout 由节点统一收集
- **关联三者**（关键工程点）：
  - 日志注入 traceID
  - Prometheus exemplar 关联 trace
  - Grafana 统一面板跳转：指标异常→查同时间 trace→跳具体日志
- 成本治理：指标降采样、日志分级保留、采样率调整（头部采样/尾部采样）

**一句话答：** 实现上三支柱各选主流组件：Prometheus 加 Grafana 管指标，OTel SDK 加 Jaeger 管链路，Fluent Bit 加 Loki 管日志。真正的工程难点在关联——把 traceID 写进日志、指标挂 exemplar，做到在 Grafana 里从一条异常曲线点进对应链路再跳到具体日志，这个跳转链通了，排障效率是数量级的提升。

### 18. OpenTelemetry 是什么？

**要点：**
- OTel = CNCF 的**可观测数据采集标准**——合并了 OpenTracing 和 OpenCensus
- 组成：
  - **OTel SDK/API**：应用埋点（生成 traces/metrics/logs），多语言
  - **OTel Collector**：统一采集处理管道——接收（OTLP 协议）→ 处理（采样/脱敏/富化）→ 导出（Prometheus/Jaeger/ES/商业 APM）
- 价值：
  - **厂商中立**：埋点一次，后端随便换——摆脱 APM 厂商锁定
  - **统一标准**：三类信号一个规范、一个协议（OTLP）
  - 自动埋点：Java agent/零代码接入
- 现状：事实标准，各大 APM 原生支持 OTLP

**一句话答：** OpenTelemetry 是可观测领域的统一标准：SDK 负责应用埋点生成指标、链路、日志三类信号，Collector 做统一接收、处理和分发。核心价值是厂商中立——埋点代码写一次，后端从 Jaeger 换到商业 APM 不用动应用。它是把 OpenTracing 和 OpenCensus 合并后的 CNCF 官方答案。

### 19. 你用过哪些链路追踪系统？

**要点：**
- **SkyWalking**：国产，Java agent 零侵入接入，APM 功能全（拓扑/告警/性能剖析），国内主流
- **Jaeger**：CNCF 元老，云原生标配，配合 Istio/K8s 生态自然
- **Zipkin**：老牌，Twitter 出品，生态广但功能相对简单
- **Tempo**：Grafana 系，对象存储后端成本低，与 Loki/Mimir/Grafana 一体化
- 关键工程点：
  - 上下文传播标准（W3C traceparent）——跨语言/跨系统才不断链
  - 采样策略：全量成本高——头部采样（入口定生死）/尾部采样（保留慢的错的）
  - traceID 贯穿日志——三支柱关联
- 选型：Java 团队 SkyWalking 上手最快；多语言+Grafana 栈选 Tempo/OTel

**一句话答：** 常见四家：SkyWalking 靠 Java agent 零侵入在国内占主流，Jaeger 是云原生元老，Zipkin 老牌轻量，Tempo 用对象存储把成本打下来。实践比选型更重要的三件事：统一 W3C 传播标准防止跨服务断链、设计合理的采样策略控制成本、traceID 落日志实现三支柱关联。

### 20. 容器运行时安全性怎么做？

**要点：**
- **镜像供应链**：最小基础镜像（distroless）、漏洞扫描（Trivy/Grype 进 CI）、镜像签名与准入校验（Cosign+Kyverno）、固定 digest、SBOM
- **运行时配置**：非 root、只读根文件系统、drop capabilities、禁 privilege/敏感 hostPath、seccomp/AppArmor
- **准入控制**：Pod Security Admission / Kyverno 强制基线
- **运行时检测**：Falco/Tetragon（eBPF）——异常进程、异常 syscall、容器逃逸特征实时告警
- **隔离增强**：多租户/不可信负载用 RuntimeClass（gVisor/Kata Containers）沙箱隔离
- **纵深**：NetworkPolicy 限横向、Secret 管理、节点最小化（COS/Bottlerocket 类专用 OS）

**一句话答：** 容器安全是纵深防御：入口管供应链——镜像扫描加签名准入；配置管基线——非 root、只读根、最小 capability，用准入策略强制；运行中靠 Falco 这类 eBPF 工具抓异常行为；不可信负载上 gVisor 或 Kata 沙箱硬隔离。单点都不完美，层层设防才有效。

### 21. 云原生可观测性第一步你认为该怎么做？

**要点：**
- 我的观点：**先把 Metrics 层做扎实，但第一步是统一数据模型**
- 落地顺序：
  1. **统一指标采集**：Prometheus + node-exporter + kube-state-metrics + 应用暴露 /metrics——一个标签规范（app/version/env）定好
  2. **核心面板与黄金指标**：RED（Rate/Error/Duration）+ USE，按服务建面板
  3. **告警治理**：从"资源阈值"升级到"面向 SLO 的告警"（错误率/延迟）
  4. 再上 Tracing（OTel）和 Logging（Loki），打通 traceID 关联
- 反模式警告：一上来三支柱齐上=烂尾；没有标签规范的指标=数据泥潭
- 度量：MTTD（发现时间）和 MTTR 缩短为最终目标

**一句话答：** 第一步不是三支柱齐上，而是把 Metrics 层按统一标签规范打扎实：Prometheus 采集加 kube-state-metrics，应用统一暴露 /metrics，标签约定 app、version、env。然后建 RED 黄金指标面板、把告警从资源阈值升级到面向 SLO。指标体系是地基——地基不牢，后面链路和日志接进来也是数据泥潭。

## 公有云平台运维面试题

### 1. 简述云计算的三种服务模式（IaaS、PaaS、SaaS）？

**要点：**
- **IaaS**（基础设施即服务）：提供虚拟机/网络/存储——用户管 OS 及以上（ECS/EC2）
- **PaaS**（平台即服务）：提供运行平台/中间件——用户只管代码和数据（RDS/容器服务/Tomcat 云托管）
- **SaaS**（软件即服务）：提供完整应用——用户直接用（钉钉/Office 365）
- 管理责任递减：IaaS 管到 OS，PaaS 管到应用，SaaS 全托管
- 运维视角：IaaS 自由度最大但活最多；PaaS 效率高但受限；选型按团队能力和控制诉求平衡

**一句话答：** 按托管程度递进：IaaS 给你虚拟机管到硬件为止，OS 以上自己搞；PaaS 给你现成平台，只管代码；SaaS 给你完整应用，打开就用。运维的自由度和工作量成反比——IaaS 最自由也最累，PaaS 省心但受平台约束，按团队能力选平衡点。

### 2. 公有云、私有云和混合云有什么区别？

**要点：**
- **公有云**：厂商运营，多租户共享——弹性好、免维护、按量计费（阿里云/AWS）
- **私有云**：自建专用——数据主权、合规可控（OpenStack/VMware/ZStack）；成本与人力自担
- **混合云**：两者结合——敏感业务在私有云，弹性/互联网业务在公有云，专线打通；常见于金融政企
- 决策因素：合规与数据主权（监管行业必须私有/混合）、成本结构、弹性需求、团队云能力

**一句话答：** 公有云是租房——弹性好免维护，按量付费；私有云是自建房——数据主权和合规可控，但要自己投入建设和人力；混合云是两者兼得——核心敏感业务留在私有云，弹性互联网业务上公有云，专线打通。监管行业基本没有选择，一定是私有或混合。

### 3. 怎么理解公有云的地域和可用区？

**要点：**
- **Region（地域）**：物理数据中心集群的地理区域（cn-hangzhou）——**不同 Region 内网不通**（走公网/专线），资源跨 Region 独立
- **AZ（可用区）**：Region 内**电力网络独立**的物理隔离单元——同 Region 内低延迟内网互联；一个 AZ 故障不影响其他 AZ
- 设计应用：
  - 高可用：业务跨 **AZ** 部署（同 Region，延迟低）——防机房级故障
  - 容灾：核心业务跨 **Region** 备份/双活——防区域级灾难
  - 延迟敏感就近选 Region；合规要求数据不出境选指定 Region
- 记忆：AZ 防机房事故，Region 防城市级灾难

**一句话答：** Region 是地理区域，AZ 是 Region 内电力网络物理隔离的机房单元——同一 Region 内 AZ 之间内网低延迟互联，跨 Region 则是独立网络。高可用用多 AZ，延迟小成本低；真容灾才跨 Region。理解了这对概念，云上架构的可用性设计就有了坐标系。

### 4. 你都用过阿里云哪些产品及应用场景？

**要点：**（按真实经验组织，以下是运维高频产品清单）
- 计算：ECS（云服务器）、ACK（容器服务）、弹性伸缩 ESS
- 网络：VPC、SLB/ALB（负载均衡）、NAT 网关、EIP、云企业网 CEN（跨 VPC）、安全组
- 存储：OSS（对象存储/静态资源/备份）、NAS（共享文件）、云盘 ESSD
- 数据库：RDS（MySQL/PG）、Redis、MongoDB、PolarDB
- 中间件：消息队列 RocketMQ、Kafka
- 运维：云监控 CMS、日志服务 SLS、堡垒机、RAM、KMS、Terway/VPC-CNI
- 安全：WAF、DDoS 防护、云防火墙
- 讲法建议：挑 5-6 个真用过的按"产品-场景-踩过的坑"讲

**一句话答：**（示范框架）按使用场景串：计算用 ECS 和 ACK 跑容器，入口 SLB 加 VPC 网络，静态资源和备份放 OSS，数据库 RDS 加 Redis，运维侧云监控加日志服务 SLS 加堡垒机，权限全部走 RAM 最小化。面试时挑自己真用过的讲深一个，比罗列二十个产品名更有说服力。

### 5. 公有云上如何设计容灾架构？

**要点：**
- 容灾等级（从低到高）：
  - **同 Region 多 AZ**：热备/双活——防机房级故障，RTO≈0，成本中——**必做的底线**
  - **同城双 Region**（如杭州+上海）：同城灾备——防 Region 级故障
  - **两地三中心**：同 Region 双 AZ + 异地 Region——金融级标准
  - **跨 Region 双活**：两地同时承载流量（GSLB/DNS 智能解析切流）
- 数据层：RDS 跨 Region 同步（DTS）、OSS 跨 Region 复制、快照异地
- 关键指标：**RTO**（恢复时间目标）与 **RPO**（数据丢失容忍）——倒推架构与成本
- 必备件：切换预案文档化+演练（不演练的容灾是摆设）、DNS/全局负载均衡切流能力

**一句话答：** 容灾从底线往上做：同 Region 多 AZ 双活防机房故障，这是所有生产业务的起步配置；再按业务价值升级——两地三中心或跨 Region 双活防区域灾难，数据层用 DTS 和 OSS 复制做异地同步。设计从 RTO 和 RPO 两个指标倒推，最后强调一句：切换预案不演练等于没有容灾。

### 6. 阿里云 SLB 有哪几种产品形态及应用场景？

**要点：**
- **CLB（经典负载均衡）**：老产品，四层/七层，逐步被 ALB/NLB 取代——存量迁移
- **ALB（应用型负载均衡）**：**七层**——HTTP/HTTPS 路由、证书、WAF 联动、配合 ACK Ingress；Web/API 入口首选
- **NLB（网络型负载均衡）**：**四层**——超高性能（亿级并发）、TCP/UDP、大流量直连（游戏/视频/数据库入口）
- 选型：七层路由和证书卸载选 ALB；纯四层极致性能选 NLB；存量 CLB 迁移到前两者
- ACK 集成：Service type=LoadBalancer 自动创建，annotation 控制

**一句话答：** 现在主推两款：ALB 管七层——HTTP 路由、证书、和 ACK 的 Ingress 生态深度集成，Web 入口用它；NLB 管四层——亿级并发的高性能 TCP/UDP 转发，游戏视频这类大流量用它。CLB 是老产品不建议新用，存量逐步迁移。

### 7. 阿里云 K8s 容器服务有哪些产品形态及应用场景？

**要点：**
- **ACK 托管集群**（Pro）：控制面托管（免 etcd/apiserver 运维）+ 用户管 worker 节点——**默认选择**
- **ACK Serverless**：无节点模式——Pod 直接弹性（ECI），按 Pod 计费——突发流量/Job/CI 场景，无节点运维
- **ACK 专有版**：控制面在用户 ECS 上——需要完全控制（合规/特殊场景）
- **注册集群**：自建/他云集群接入阿里云管理体系——统一治理
- **ACK Edge**：边缘场景
- 节点付费：包年包月（稳态）vs 抢占式实例（弹性/离线）混合降本
- 选型：常规业务托管版，突发弹性 Serverless，特殊合规专有版

**一句话答：** 四种形态按控制权递增：托管 Pro 版控制面云上管、只管 worker 节点，是默认选择；Serverless 版连节点都不要，Pod 直接跑在 ECI 上按量计费，适合突发和 Job；专有版控制面落在自己 ECS 上给特殊合规场景；注册集群是把已有的自建集群纳管进来统一治理。

### 8. 如何保证云资源的安全性？

**要点：**
- **身份权限**：RAM 最小权限、**子账号+SSO**（不用主账号日常操作）、MFA 多因素、AccessKey 定期轮换+不进代码（KMS/STS 临时凭证）
- **网络边界**：VPC 隔离、安全组最小开放（禁 0.0.0.0/0 的 22/3389）、堡垒机统一入口、私网优先（SLB 挂内网）
- **数据安全**：云盘/OSS 加密（KMS）、数据库透明加密、备份加密、传输 TLS
- **平台能力**：云安全中心（主机入侵检测）、配置审计（违规资源告警）、操作审计 ActionTrail（API 全记录）
- **流程**：安全组变更审批、AK 泄漏应急（禁用+轮换）、定期漏洞扫描与基线核查

**一句话答：** 四条主线：身份上 RAM 最小权限加子账号加 MFA，根上杜绝主账号 AK 写代码；网络上安全组最小开放加堡垒机；数据上 KMS 加密加传输 TLS；治理上用配置审计和操作审计兜底，让每个资源每个 API 调用都可追溯。云安全的一半是平台能力，另一半是权限纪律。

### 9. 如何将业务系统在线迁移到公有云？

**要点：**
- 方法论：**评估→上云→数据同步→割接→回退预案**
- 步骤：
  1. **评估**：应用依赖梳理、改造点（IP 硬编码/许可/内核）、带宽与成本测算
  2. **搭建**：VPC 网络规划（与 IDC 网段不冲突）、专线/VPN 打通混合云
  3. **迁移**：应用镜像/镜像导入（VM 迁移工具）、数据同步（DTS 数据传输——不停库同步到 RDS）
  4. **验证**：云端预发验证功能与性能
  5. **割接**：低峰 DNS/SLB 切流——灰度按比例切
  6. **观察回退**：旧环境保留 1-2 周可回切，稳定后下线
- 关键点：数据同步的**双向切换**与回切方案、割接演练、监控对齐
- 工具：DTS、SMC（服务器迁移中心）、OSS 迁移服务

**一句话答：** 标准打法是评估、搭桥、同步、割接、留后路：先梳理依赖和网络规划，专线打通混合云环境，应用镜像化搬过去，数据库用 DTS 做不停机同步，低峰期 DNS 灰度切流。成败关键在两处：割接前全链路演练，旧环境保留回切能力——没有回退方案的迁移不能上生产。

### 10. VPC 是什么？为什么要用？

**要点：**
- VPC（专有网络）= 云上**逻辑隔离的私有网络**：自定义网段（CIDR）、子网（vSwitch）、路由表——你专属的二层三层网络
- 为什么用：
  1. **网络隔离**：资源不暴露公网、租户间二层隔离
  2. **地址自主**：自定义网段，可与 IDC 对接（专线/VPN 打通混合云）
  3. **访问控制**：安全组（实例级）+ACL（子网级）精细管控
  4. **合规**：内网通信、数据不出边界
- 关键组件：vSwitch（子网，按 AZ）、路由表、NAT 网关（出网）、EIP、对等连接/云企业网（VPC 互通）
- 规划要点：网段预留（防与 IDC 冲突）、生产测试分 VPC、按业务域划分子网

**一句话答：** VPC 是云上的私有网络沙箱：自定义网段子网路由表，资源默认与公网和别的租户隔离。用它的理由有三：安全边界、地址自主规划可与机房专线打通、精细化访问控制。规划要一次到位——生产测试分开、网段给 IDC 留余地，VPC 网段冲突是事后最难改的坑。

### 11. 如何将机房数据库在线同步到RDS？

**要点：**
- 标准工具：**DTS（数据传输服务）**——结构+全量+增量一体化
- 流程：
  1. 前置检查：版本兼容（MySQL 5.7→8.0 参数差异）、字符集、账号权限（DTS 需要 REPLICATION SLAVE）
  2. 创建迁移任务：结构迁移 → **全量迁移** → **增量同步**（拉取 binlog 持续追平）
  3. 验证：数据校验（DTS 自带/工具比对）、业务预发连 RDS 测试
  4. **割接**：低峰停写 → 等增量追平（延迟为 0）→ 业务连接串切到 RDS → 观察回退预案
- 注意点：同步延迟监控（DTS 延迟指标告警）、大事务/DDL 的兼容问题（增量阶段慎 DDL）、外键与触发器的处理、带宽（binlog 量大）
- 回退方案：RDS→IDC 反向同步通道预建（万一要回切）

**一句话答：** 用 DTS 走三段式：全量迁移打底，增量同步拉 binlog 追平，最后低峰停写、等同步延迟归零、切连接串完成割接。三个细节决定成败：同步延迟要有告警、增量阶段避免大 DDL、割接前必须建好反向同步通道——这样万一回切数据也不丢。

### 12. 简述阿里云 RAM 权限管理核心组成？

**要点：**
- RAM = Resource Access Management（资源访问控制）
- 核心组成：
  - **RAM 用户/用户组**：子账号（人/程序身份），分组批量授权
  - **角色（Role）**：可被**临时扮演**的身份——STS 临时凭证（跨账号授权、程序免 AK）、服务关联角色（云产品自动授权）
  - **权限策略（Policy）**：JSON 声明——系统策略（粗）/自定义策略（细粒度：资源 ARN + Action + Condition）
  - **授权关系**：给用户/组/角色绑定策略
- 最佳实践：主账号不日常使用、最小权限、SSO 对接企业 IdP、AK 轮换、STS 替代长期 AK、操作审计配合

**一句话答：** RAM 四件套：用户管人和程序的静态身份，角色管可临时扮演的身份配 STS 临时凭证，策略用 JSON 定义细到资源级别的权限，最后绑定关系生效。纪律就一条——最小权限：主账号封存不用，日常操作子账号加 MFA，程序用角色临时凭证而不是长期 AK。

### 13. 如何有效降低公有云成本？

**要点：**
- **计费模式优化**：稳态资源包年包月（约省一半）、弹性/离线用抢占式实例（90% off，接受回收）、混合策略
- **资源治理**：
  - 闲置资源清理：空载 ECS、未挂载云盘/EIP、过期快照——定期账单分析+标签体系（部门/项目标签账单归集）
  - 规格右尺寸（right-sizing）：按监控利用率降配（大量机器 CPU 10% 以下）
  - 自动伸缩：非工作时段缩容测试环境（定时开关机）
- **架构优化**：OSS 冷热分层+生命周期（转低频/归档）、CDN 替代源站带宽、Spot 干离线任务
- **治理机制**：预算告警、成本分摊到团队、FinOps 例会——成本是持续治理不是一次性运动

**一句话答：** 成本优化三板斧：计费模式上稳态包年弹性竞价，混合付费能省一半；资源治理上定期清理闲置、按利用率右尺寸、测试环境定时关机，配套标签体系把账单归到团队；架构上用生命周期管理存储分层、CDN 分流带宽。最后必须有预算告警机制——成本是持续运营的结果，不是一次优化的成果。

### 14. 阿里云 NAT 网关有哪些应用场景？

**要点：**
- NAT 网关 = VPC 内**私网资源统一出公网/入公网代理**：
  - **SNAT**：无公网 IP 的 ECS 统一经网关出网——出口 IP 可控（对方白名单好配）、隐藏内部结构；多 EIP 池分散出口风险
  - **DNAT**：把公网 IP:端口映射到内网 ECS——替代给实例绑 EIP（少占公网 IP）
- 典型场景：内网服务器批量出网（yum/pip/调三方 API）、微服务集群统一出口、等保合规不允许实例直挂公网
- 对比：EIP 直绑实例（简单但 IP 分散难管理）、公网带宽按实例买（贵）；NAT 网关集中管控+按量
- 运维注意：SNAT 出口 IP 告知三方加白名单、连接数监控（SNAT 连接数规格）

**一句话答：** NAT 网关解决"私网机器怎么上网"：SNAT 让没有公网 IP 的实例统一从一个受控出口出去——三方白名单好配，内部拓扑也不暴露；DNAT 反过来把公网端口映射进来，省得逐台绑 EIP。它本质是把"公网接入"从实例级收拢到网关级，集中管控、集中计费、集中审计。

### 15. 跨地域之间 VPC 如何实现互通？

**要点：**
- 方案对比：
  - **云企业网 CEN**（推荐）：中心化转发网络——多 Region 多 VPC 一张网，带宽共享、路由自动学习；计费按带宽包；管理和扩展性最好
  - **对等连接 Peering**：两两 VPC 直连——低延迟专线路径；但 **N 条 VPC 需要 N×(N-1)/2 条连接**，规模大了管理爆炸；跨地域按流量双向计费
  - **VPN 网关**：IPSec 隧道走公网——便宜、快速搭建；性能与稳定性受公网限制——测试/备份用途
  - **物理专线**：跨地域 IDC 互联场景，最贵最稳
- 选型：超过 2-3 个 VPC 直接 CEN；临时联通 VPN 起步；金融合规专线
- 通用注意：**网段规划不冲突**（OverLAP 是大坑）、路由表与安全组放行、带宽监控

**一句话答：** 两个 VPC 用对等连接直连最快，三个以上就上云企业网 CEN——中心化一张网自动学路由，管理成本最低；临时或测试环境用 VPN 隧道走公网省钱。所有方案的共同前提是网段规划不能重叠——跨地域组网里网段冲突是最难返工的错误。

### 16. 阿里云 OSS 有哪些产品形态？

**要点：**
- 按性能类型：
  - **标准型**：高频访问（网站静态资源、图片）
  - **低频访问型**：月访问 1-2 次（月度备份、日志归档）——存储费低取回费高
  - **归档/冷归档型**：极少访问（合规留存）——取回需解冻等待
- 按场景形态：
  - **Bucket 存储桶**：基础容器+权限（公共读/私有）+生命周期规则
  - **静态网站托管**：Bucket 直托管前端+CDN 加速
  - **图片处理服务**：内置缩放/水印/格式转换（URL 参数触发）
  - **OSS Select**：SQL 过滤取 CSV/JSON 部分
  - **版本控制+跨区域复制**：容灾与防误删
- 成本治理：生命周期自动沉降（30 天转低频/90 天转归档）、按量计费项（存储/流量/请求）要分别看账单——**外网流出流量是大头**，用 CDN 分流

**一句话答：** OSS 的形态按访问频率分层：标准型扛热数据，低频型放月度备份，归档型存合规留存——配合生命周期规则自动沉降，成本逐级下降。功能上有静态网站托管、内置图片处理、版本控制和跨区域复制。成本监控要盯外网流出流量，那是账单大头，正确姿势是前面加 CDN。

## 边缘计算运维面试题

### 1. 什么是边缘计算？它与云计算的核心区别是什么？

**要点：**
- 边缘计算：把计算/存储**下沉到数据产生源附近**（基站/门店/工厂/园区），就近处理
- 核心区别：
  - **位置**：云在远端集中机房；边在数据源近端分布式部署
  - **延迟**：云几十毫秒以上；边 1-10ms 级
  - **带宽**：边只回传结果/摘要（省回传带宽）
  - **规模形态**：云是少数大机房；边是海量小节点（成百上千）
  - **环境**：云机房可控恒温；边节点环境差、网络不稳、无人值守
- 协同：边云协同——边缘做实时处理，云做全局管理与数据汇聚

**一句话答：** 边缘计算是把算力从集中机房下沉到数据产生的地方。核心区别四个字：近、快、多、散——距离近延迟低到毫秒级，回传只送结果省带宽，节点数量多但每个都很小，环境分散且不可控。云管全局边管实时，两者是协同不是替代。

### 2. 边缘计算的核心思想是什么？

**要点：**
- 核心思想：**让数据和计算靠近**——就近处理、就近返回
- 三大驱动力：
  1. **时延敏感**：自动驾驶/工业控制/云游戏等毫秒级场景等不起往返云端
  2. **带宽经济**：摄像头 4K 视频全量上云带宽爆炸——边缘预处理只回传结构化结果
  3. **数据主权与合规**：敏感数据本地处理不出园区
- 架构关键词：分布式、自治（断网也能跑）、云边协同、轻量化运行时

**一句话答：** 核心思想一句话：数据在哪，计算就在哪。背后是三个压力——毫秒级时延的应用需求、全量上云撑不住的带宽成本、数据不出园区的合规要求。由此衍生出边缘系统的设计关键词：轻量化、自治运行、云边协同管理。

### 3. 边缘计算适用于哪些业务场景？

**要点：**
- **视频类**：智能安防（园区摄像头人脸/行为分析）、视频直播推流预处理
- **工业**：产线质检（视觉 AI）、PLC 数据实时采集与控制
- **交通**：车路协同、路口信号优化、自动驾驶辅助
- **零售**：门店收银系统、客流分析、电子价签
- **CDN/云游戏**：内容就近分发、游戏渲染下沉
- **物联网**：智能家居网关、农业传感
- 共同特征筛选：**低时延 + 大带宽回传压力 + 本地数据敏感** 至少占一条

**一句话答：** 场景规律就是三条需求打头：时延敏感的——自动驾驶和工业控制；回传带宽爆炸的——万级摄像头视频分析；数据不能出本地的——园区安防和工厂产线。凡是命中这三条的业务都是边缘计算的菜，纯报表类业务放云端更划算。

### 4. 当边缘节点数量达到数千台时，如何实现统一管理与自动化运维？

**要点：**
- **不可人工登录**——一切靠平台：
  1. **统一纳管**：K3s/KubeEdge 集群化纳管边缘节点，云端控制面统一 API
  2. **配置即代码**：应用/配置从云端 Git/仓库统一分发（声明式），禁止单点手改
  3. **镜像分发**：边缘镜像仓库（就近拉取/云端推送），分层+预下载
  4. **监控告警中心化**：边缘侧轻量采集（prometheus agent/edge-side 本地聚合），断网缓存、联网续传；告警统一云端 rule
  5. **日志**：边缘本地存储+按需上传（全量上传带宽不可行）
  6. **批量操作平台**：脚本/命令的灰度批量下发（分批+超时+回滚）
  7. **自动化装机**：Kickstart/IPXE 云端自动装机注册，开机即入集群
- 度量：万节点运维团队只需几人——靠的是"一切皆代码+自动恢复"

**一句话答：** 数千节点管理的第一原则是把人从 SSH 里解放出来：节点用 K3s 或 KubeEdge 统一纳管，应用和配置全部云端声明式分发，装机自动化到开机即注册，监控断网本地缓存联网续传。人只处理告警和写自动化脚本，任何手改单节点配置的操作都会在规模下失控。

### 5. 边缘节点断网后如何保证业务连续性？

**要点：**
- 设计原则：**边缘自治（Edge Autonomy）**——断网即"孤岛求生"
- 关键机制：
  1. **本地决策**：边缘节点缓存本节点应运行的工作负载（K3s 本地元数据/KubeEdge 的 metaManager）——断网后照常运行、重启也能拉起
  2. **本地闭环**：业务逻辑闭环在边缘（本地 DB/缓存），云端只是汇聚——断网只影响上报不影响现场业务
  3. **数据缓存续传**：监控/日志/业务数据断网期本地存储，恢复后增量上传
  4. **安全兜底**：本地认证降级方案、断网期告警本地化（蜂鸣/本地面板）
- 测试：断网演练是边缘运维必修课——拔网线验证业务是否如预期自治

**一句话答：** 断网生存靠"边缘自治"设计：节点在本地缓存自己该跑什么、怎么跑，断网后照常运行重启自愈；业务数据本地闭环，云端只做汇聚；监控日志断网期落盘、恢复后续传。判断架构合格与否的标准很简单——拔掉网线，现场业务必须无感知。

### 6. 边缘计算环境中如何实现应用的高可用部署？

**要点：**
- 分场景 HA 策略（与云端不同——**同站点资源有限**）：
  1. **单节点应用**：靠自愈（健康检查+自动重启+开机自启）+数据持久化到本地可靠存储——大部分边缘应用的现实选择
  2. **站点级 HA**：重要站点 2 台节点+双活/主备（K3s 双节点+VIP/keepalived）
  3. **跨节点业务冗余**：无状态服务在相邻节点各跑一份（资源允许时）
  4. **云端兜底**：边缘不可用时业务降级到云端（可降级的功能设计）
- 依赖治理：应用间依赖尽量本地化（本地 DB/缓存），不强依赖云端
- 演练：节点断电、拔盘、断网三类故障的自动化恢复演练

**一句话答：** 边缘 HA 的现实做法分三档：普通应用靠自愈——健康检查加自动重启加开机自启；关键站点双节点做主备加 VIP；核心业务在云端留降级兜底。和云上的区别是资源买不起冗余堆叠，所以重点投入在故障后的自动恢复速度上，断电断网拔盘三类演练必须常态化。

### 7. K3s 是什么？有什么特点？

**要点：**
- K3s = Rancher 出品的**轻量级 K8s 发行版**（"5 个轻 8 个重"的梗：删掉了 alpha/beta/非默认特性、云厂商驱动、内置 containerd/flannel/sqlite 替代 etcd）
- 特点：
  - **单二进制 ~70MB**、内存占用 <512MB、秒级安装
  - 内置：containerd、Flannel、CoreDNS、本地存储（local-path）、嵌入式 etcd/SQLite（数据存储可选）
  - 兼容 K8s API——kubectl/Helm 照用
  - 离线安装支持（airgap）
- 场景：边缘节点、IoT、CI 临时集群、开发环境、ARM 设备

**一句话答：** K3s 是把 K8s 瘦身到单二进制的发行版：内置了 containerd、Flannel、CoreDNS 和轻量数据存储，70MB 大小、512MB 内存就能跑，但 API 完全兼容标准 K8s。它是边缘和资源受限环境跑 K8s 的事实标准——本质没阉割能力，只是砍掉了边缘用不到的东西。

### 8. KubeEdge 是什么？

**要点：**
- KubeEdge = CNCF 孵化项目，**云边协同**的 K8s 延伸：
  - **云端 CloudCore**：扩展 apiserver（边缘同步/元数据）+ 云边通道
  - **边缘 EdgeCore**：轻量运行时（可用 KubeEdge 内置 edgeworker/或对接 K3s 类）+ **MetaManager（本地元数据存储）+ EdgeHub（云边通信）**
- 核心能力：
  - **云边协同管理**：云端统一编排，边缘执行
  - **边缘自治**：断网后边缘本地元数据驱动继续运行/重启恢复
  - **云边消息通道**：基于 WebSocket 的单向连出（边缘 NAT 后可被管理）
  - **设备管理**：通过 CRD（Device）管理 IoT 设备（Modbus/OPC-UA/MQTT 映射）
- 与 K3s 区别：K3s 是"小 K8s"（独立完整集群）；KubeEdge 是"K8s 的云边延伸"（一个 K8s 管到边缘）

**一句话答：** KubeEdge 是 K8s 向边缘的延伸而非缩小版：云端 CloudCore 扩展 apiserver 管理边缘，边缘 EdgeCore 带本地元数据存储实现断网自治，还有一个特色能力是通过 Device CRD 直接管理 IoT 设备。选型逻辑：每个站点想要独立小集群选 K3s，想用一个 K8s 集群管所有边缘节点选 KubeEdge。

### 9. K3s 与 KubeEdge 在边缘计算场景中各自角色？

**要点：**
- **K3s**：**每个边缘站点一个独立迷你集群**——站点内自治完整（自己的控制面），云端通过 Rancher 统一管理多集群
  - 适合：站点有一定算力、需要站点级自治、运维团队按站点管理的模式
- **KubeEdge**：**云端一个 K8s 集群把边缘节点当作普通 Node 纳管**——统一 API、单集群视角
  - 适合：海量小节点（每个站点单节点或少量节点）、需要云边一体化编排、IoT 设备管理
- 混合架构：站点内有小算力用 K3s 做本地集群，海量微节点用 KubeEdge 纳管；Rancher 管多 K3s 集群
- 选型对比：管理模型（多集群 vs 单集群）、断网自治实现（完整 vs 元数据）、设备管理（无 vs 原生）、资源占用（几十 MB vs 更小）

**一句话答：** 角色区分一句话：K3s 是每站点一个小 K8s 集群，靠 Rancher 管多集群；KubeEdge 是一个大 K8s 直接把边缘节点纳管成普通 Node。站点算力足、要站点级完整自治用 K3s；海量小节点要统一编排加 IoT 设备管理用 KubeEdge，两者还能混着用。

### 10. 边缘节点分布在全国各地，如何进行远程运维和故障排查？

**要点：**
- **绝不依赖"登上去看看"**：
  1. **统一接入**：边缘到云端**反向连接**（出站 WebSocket/隧道）——节点无公网 IP 也能被管理（SSH over 隧道：frp/rathole/cloudflared）
  2. **监控先行**：云端统一监控大盘（节点资源/应用状态/网络质量），告警精准到节点+组件
  3. **日志策略**：边缘本地留存+错误日志上传，云端可检索
  4. **远程诊断包**：一键下发诊断脚本（采集进程/网络/磁盘/日志打包回传）——标准化
  5. **安全远程访问**：堡垒机代理（经隧道）+操作审计，或 Web 终端
  6. **现场兜底**：现场人员 SOP（重启/换机/插网线）+ 远程协作工具
- 关键认知：边缘运维的成本大头在现场人力——自动化解决 95%，现场处理 5%

**一句话答：** 远程运维的基建是反向隧道：边缘节点主动连出建立管理通道，云端就能穿透 NAT 做 SSH 和监控。日常靠云端统一监控加错误日志上传发现问题，诊断靠一键下发的标准脚本包回传数据，真的需要进节点走堡垒机代理加全程审计。目标是把现场人力压缩到换机器和插网线。

### 11. 边缘节点没有固定公网IP，如何实现云端对边缘节点的主动管控与指令下发？

**要点：**
- 核心模式：**反向连接（Edge-initiated）**——边缘主动连云端长连接，云端指令走该通道下发
  - KubeEdge：EdgeHub 主动 WebSocket 连 CloudCore——指令下发/状态回传走同一条
  - 自研：WebSocket/gRPC/MQTT 长连出站
  - SSH 场景：反向隧道（frp/autossh）——边缘连云端中转，云端经中转 SSH
- 补充手段：
  - **MQTT 消息通道**：低带宽IoT场景，发布订阅下发指令
  - **轮询拉取**：节点定时拉云端配置/任务队列（最简单，实时性差）
- 安全设计：双向认证（mTLS/证书）、指令签名防伪造、通道加密
- 状态回传：心跳上报（在线/版本/资源），断联判定与告警

**一句话答：** 没有公网 IP 就用反向连接：边缘节点主动向云端建立 WebSocket 或 gRPC 长连接，云端的所有指令都顺着这条出站通道下发，KubeEdge 的 EdgeHub 就是标准实现。SSH 管理走 frp 这类反向隧道。安全上必须双向证书认证加指令签名——通道一旦建立，它就是整台节点的控制权入口。

### 12. 当某个边缘节点出现故障时，如何排查？

**要点：**
- 远程排查流水线（能远程不现场）：
  1. **监控定位**：云端看该节点心跳断联时间/最后上报指标（CPU/内存/磁盘/网络质量曲线）——判断"挂了"还是"变慢"
  2. **网络层**：ping/路由（云端→站点出口）、隧道状态、运营商问题排查（多点对比：同站点其他节点正常吗）
  3. **系统层**（若 SSH 可达）：dmesg（硬件/OOM）、磁盘水位、进程状态、journal
  4. **容器层**：K3s/KubeEdge 组件状态、容器事件日志、镜像拉取失败记录
  5. **区分故障类别**：
     - 整节点失联 → 网络/硬件/断电
     - 节点在但应用挂 → 资源/镜像/配置/依赖
     - 时好时坏 → 网络质量/资源竞争/存储老化
- **现场兜底 SOP**：远程 30 分钟无果且影响业务 → 现场重启/换机流程
- 复盘沉淀：故障模式库——高频故障自动化预防（磁盘监控、自动重启策略）

**一句话答：** 先用监控分类：整节点心跳断了大概率是断电断网硬件问题，节点活着应用挂了才往资源镜像配置方向查。远程能看的是云端指标、隧道状态和 SSH 进去后的 dmesg、磁盘、容器事件。半小时远程搞不定且业务受影响就按 SOP 让现场重启换机，事后把故障模式沉淀成自动化预防规则。

### 13. 边缘计算环境的常见安全风险有哪些？

**要点：**
- 与云端不同的风险面：
  1. **物理暴露**：节点在无人值守现场——被物理接触、拆盘、插恶意设备
  2. **网络不可信**：走公网/运营商网络，中间人、DNS 劫持风险
  3. **身份伪造**：仿冒节点接入（拿历史凭证上线恶意节点）
  4. **本地数据泄露**：节点存储的敏感数据（摄像头数据/业务数据）被窃取
  5. **固件/系统老旧**：边缘设备升级难——漏洞长期存在
  6. **侧信道**：本地局域网内横向移动跳板
- 攻击链路：物理接触→提取凭证→伪造节点→进入云端管理面（**最危险路径**）

**一句话答：** 边缘特有风险集中在"无人值守"三个字：物理上能被接触拆解提取凭证，网络上走不可信链路能被中间人，身份上要防伪造节点混入集群，数据上有本地存储被窃的风险。最危险的一条攻击链是物理拿走凭证后伪造节点反向攻入云端管理面——所以凭证保护和节点认证是边缘安全的命门。

### 14. 边缘计算环境如何安全加固？

**要点：**
- **身份与通道**：节点双向 mTLS（证书唯一身份）、一键吊销（丢机即吊）、通道全加密、指令签名
- **物理与系统**：磁盘加密（LUKS——拆盘读不出）、BIOS 密码+Secure Boot、系统最小化（只跑必要服务）、文件系统只读+完整性校验（IMA/AIDE）
- **权限最小化**：边缘节点 token 权限最小（Node 角色而非 admin）、云端管理面 MFA+审计
- **网络分段**：边缘本地网络隔离（业务/管理/OOB 分离）、出站白名单（只连云端必要端口）
- **数据保护**：本地数据脱敏/最小留存、密钥不落盘（TPM 存储根密钥）
- **检测响应**：异常行为监控（陌生外联/登录）、一键远程擦除（数据销毁）、定期固件/系统升级通道（签名校验）

**一句话答：** 加固围绕"节点终将失守"假设：身份上双向证书加一键吊销，物理上磁盘加密加 Secure Boot，权限上边缘 token 最小化，网络上出站白名单只连云端，数据上密钥放 TPM 不落盘加远程擦除能力。核心目标是就算整机被拆走，攻击者拿到的也是加密磁盘和已吊销的凭证。

### 15. 大规模边缘集群运维的核心痛点是什么？

**要点：**
- 五大痛点：
  1. **不可控环境**：断电断网硬件故障频发，现场无人——故障率远高于机房
  2. **规模与人力比**：千级节点/几个运维——必须全自动化，任何人工步骤都会成为瓶颈
  3. **网络异构与不稳定**：带宽小、时延抖、偶发断连——云边同步、镜像分发都要容忍弱网
  4. **版本一致性**：数千节点版本漂移——灰度升级+失败回滚+断点续传的发布系统
  5. **安全与合规**：物理暴露+数据合规+设备凭证生命周期管理
- 应对哲学：**假设每个节点随时会失联、随时会坏、随时会被人碰**——架构上自治、运维上自动化、安全上零信任

**一句话答：** 核心痛点是"环境不可控和人太少"的矛盾：节点故障率高但现场没人，网络弱且不稳定但云边要同步，数千节点的版本一致性靠人力根本做不动。应对哲学就三句话——架构假设节点随时失联所以自治，运维假设人不能到场所以全自动，安全假设节点会被攻破所以零信任。

### 16. 请设计一个支持10万个边缘节点的物联网平台运维架构？

**要点：**
- **分层设计**：
  1. **接入层**：多 Region 接入网关（就近接入、连接分片）——单控制面扛不住 10 万长连接，按地域/Hash 分片多个控制面集群
  2. **管理面**：KubeEdge/自研云边通道（MQTT+WebSocket 混合）——连接网关无状态化水平扩展、指令下发走消息队列削峰
  3. **节点侧**：极轻运行时（K3s/KubeEdge EdgeCore）——自治运行、本地缓存、断点续传
  4. **应用分发**：分级发布体系——灰度单元（按区域/批次 1%→10%→100%）、失败自动暂停+回滚、弱网容忍（镜像分块+断点续传+就近镜像缓存节点）
  5. **监控体系**：边缘侧聚合采样（不是全量上报）→ 区域汇聚 → 全局 TSDB 分片（Thanos 类）；告警分级（节点级/区域级/全局级）
  6. **安全体系**：零信任——节点证书+TPM、通道加密、指令签名、远程擦除
  7. **自动化**：装机注册全自动、故障自愈规则库、AI 辅助异常检测（万级节点的告警降噪）
- 关键设计决策：
  - **连接分片+控制面分片**：单 K8s 集群管理上限在几千节点——10 万必须多集群联邦（Karmada 类）
  - **数据分级上报**：全量指标上云不可行——边缘聚合、异常触发详情上传
  - **发布分批**：任何变更不能全量同时——10 万节点的批量故障就是事故
- 度量目标：发布自动化率 100%、人均管理节点 >1 万、故障自愈率 >80%

**一句话答：** 10 万节点的架构核心是"分片自治"：接入层按地域分片多集群联邦管理——单集群几千节点就到上限了；云边通道用 MQTT 加 WebSocket 混合，指令走消息队列削峰；应用发布必须分批灰度带自动回滚，因为任何全量操作在 10 万节点上都是事故；监控边缘聚合采样不全量上云；安全走零信任——TPM 证书加指令签名加远程擦除。衡量这套架构成功的标准是人均管理过万节点加八成故障自愈。
